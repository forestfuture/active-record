# Behavior contract (draft)

The public behavior agreed during design, which the tests must prove. The guide at active-record.forestfuture.dev is written from it. Terms follow `GLOSSARY.md`; the reasons for decisions are in `docs/adr/`. Each section names the modules that implement it, and its guide pages where it has them. Each is marked _Portable_, proven on every adapter by the conformance suite (`tests/conformance/`), or _D1_, proven by the D1 adapter's own tests (`tests/integration/d1/`). A bullet or sentence marked (D1) in a portable section is the D1 adapter's alone, and one marked (Postgres) is the PostgreSQL adapter's.

## Toolchain

_D1._

_Code:_ `vite.config.ts`, `package.json`, `packages/*/package.json`, `packages/*/vite.config.ts`. Below, a module's path is within `packages/`: `active-record/src/` is the core and `active-record/cli/` its command, `active-record/src/adapters/d1/` and `active-record/cli/adapters/d1/` are the D1 adapter and its plugin for the command, and `active-record/src/adapters/postgresql/` and `active-record/cli/adapters/postgresql/` are the PostgreSQL adapter and its plugin.

- Vite+ `1.0.0`, pinned exactly; upgrade with `vp upgrade`, then `vp migrate`. pnpm 12.6.0 through `devEngines`. Node 24 LTS through `.node-version`.
- One package, `@forestfuture/active-record` (`packages/active-record`, ADR-0019), in a pnpm workspace with the site; scoped, published with `access: public`, ESM-only, target ES2022, `.d.ts` emitted, attw `esm-only` profile and publint on every `vp pack`. MIT license. One build, so every entry shares the core's modules (one copy of each class).
  - Its entries: `.`, the core; `/d1` and `/postgresql`, the adapters (#301); and two unstable entries for an adapter outside the package: `/adapter`, and `/cli` for its plugin for the command. It ships the `active-record` command (also `ffar`), the agent skill, `llms-full.txt`, and `config-schema.json`, and depends on `jiti` alone, which only the command loads.
  - Each adapter's runtime is in `src/adapters/<name>/` and its plugin in `cli/adapters/<name>/`. An adapter reaches the core only through the core's public entries, by their names, and never another adapter; the core imports no adapter, but the command's registry loads each plugin with `import()` (`active-record/cli/project/adapters.ts`). Lint enforces both.
  - The adapters' drivers are optional peer dependencies, never bundled (`check:package` checks the build): `pg`, which only the `/postgresql` entry imports, and PGlite, which only its plugin loads, to read a schema. A D1 app installs neither. The plugin loads each when a command first needs it, and says what to install when it's missing (`npm install pg`, `npm install --save-dev @electric-sql/pglite`).
  - (Postgres) The PostgreSQL adapter runs on Workers through Hyperdrive and on Node. An app moves to it from D1 with its Models and code unchanged (#270): `tests/integration/pg/move-to-postgres.test.ts` takes the Getting started app across as the guide's [move-to-postgres](<../site/docs/(how-to)/move-to-postgres.mdx>) does, with only the library and `pg` installed, and after the move its Worker, on Hyperdrive, returns what it returned on D1. It types the part of `pg` it calls itself (`src/adapters/postgresql/pg-module.d.ts`), since `@types/pg` brings Node's types.
  - `@forestfuture/d1-record`, the D1 adapter's package until 0.7, is deprecated on npm, with no alias. In the repo, the package's `exports` resolve to its source (tsdown's `devExports`), so the command runs untranspiled; `publishConfig` points the published package at `dist/`.
- Each package's `src/` is type-checked with `@cloudflare/workers-types` and no Node types. `tests/tsconfig.json` adds Node types.
- Three Vitest projects. `unit` (`tests/unit/**`) is for logic that needs no database. There's no fake executor: tests that involve a database use a real one and watch queries through the public `onQuery` hook. `conformance:d1` runs the portable conformance suite (`tests/conformance/**`, #267) against D1: each file opens its database through `openHarness()` (`tests/support/harness.ts`), which the project names with `provide`, and skips the tests an adapter's allowed differences name (`tests/conformance/allowed-differences.ts`). `integration:d1` (`tests/integration/d1/**`) holds the D1 adapter's own tests. Both get a fresh in-memory Miniflare D1 per file, with the schema created from `tests/fixtures/migrations/db/0001_schema.sql` (`tests/support/d1.ts`, Miniflare 4). See ADR-0002. With `DATABASE_URL` set, two more run against that Postgres server, each file in a schema of its own: `conformance:pg`, the suite through `tests/support/harnesses/pg.ts` and the Postgres schemas in `tests/fixtures/postgres/`, and `integration:pg` (`tests/integration/pg/**`), the PostgreSQL adapter's own tests, on Node and in workerd. Without it they're left out; CI runs them against a Postgres 17 service, and a unit test fails in CI when `DATABASE_URL` is missing.
- Pre-commit hooks lint and format staged files. GitHub Actions runs `vp install`, `vp check`, `vp test` and `vp run build` on push to `main`.

## Connecting

_Portable._ A bullet or sentence marked (D1) is the D1 adapter's alone.

_Guide:_ [connecting](<../site/docs/(basics)/connecting.mdx>), [query-databases](<../site/docs/(background)/query-databases.md>), [several-databases](<../site/docs/(how-to)/several-databases.mdx>), [read-your-own-writes](<../site/docs/(how-to)/read-your-own-writes.mdx>), [d1](<../site/docs/(adapters)/d1.mdx>), [postgres](<../site/docs/(adapters)/postgres.mdx>). _Code:_ `active-record/src/database.ts`, `active-record/src/current-database.ts`, `active-record/src/executor.ts`, `active-record/src/adapters/d1/`, `active-record/src/adapters/postgresql/`.

A query finds its database one of three ways (#77):

```ts
// 1. The Model's binding, with no setup: the generated schema its base class holds names it
await User.find(id);
await User.where({ isActive: true }).active().toArray();

// 2. The request's database, for a Session, onQuery, or code outside a Worker
await withDatabase(connect(env.DB, { session: bookmark, onQuery }), () => User.find(id));

// 3. An explicit database, always its own
const db = connect(env.DB); // plain binding: every query goes to the primary
const db = connect(env.DB, { session: "first-unconstrained" | "first-primary" | bookmark });
db.bookmark(); // pass to the next request (withSession does it for you)

// A request's Session, carried from the user's last request in a cookie or a header (#220)
withSession(request, env.DB, (db) => handle(request));
withSession(request, env.DB, { header: "x-d1-bookmark", start: "first-primary", onQuery }, fn);
const users = db.model(User); // a Relation on this database
const models = db.models({ User, Post }); // convenience: models.User has the same type as db.model(User)
```

- (D1) A Database with a session sends every query through that one D1 Session: record reads and writes, uniqueness checks, association reads, preloads, statements and batches. So the request reads its own writes even when reads are served by replicas. `session` takes D1's own values: `"first-primary"`, `"first-unconstrained"`, or a bookmark. Apps that want a primary Database and a replica Database call `connect()` twice.
- (D1) `db.bookmark()` is the Session's latest bookmark (D1's `getBookmark()`), `null` before its first query. Pass it to the next request's `connect(env.DB, { session: bookmark })` to read at least as new as this request wrote. On a Database opened without a session it throws `NoSession`, since a `null` there would quietly mean "no session" next time.
- (D1) `withSession(request, env.DB, [options,] fn)` opens the request's Database with a Session, runs `fn(db)` inside `withDatabase(db, …)`, and resolves to `fn`'s Response with the Session's bookmark set on it (#220). The Session starts from the bookmark the request carries, or from `start` (`"first-unconstrained"` unless set) when it carries none. The bookmark set is `db.bookmark()`, or the request's own when `fn` sent no query; with neither, nothing is set. A request's bookmark may be forged, and D1 rejects one it can't use on the Session's first statement (`invalid commitToken bookmark`; `tests/remote/` checks garbage, a far-future bookmark shaped like D1's, and a 10,000-character value against real D1). So when it does, the Session starts again from `start`, and the rejected statement (or batch) is sent again on it, once: it never ran, and `fn` isn't run twice. First statements sent at once start it again once, and each is sent again. Once a statement succeeds, a later rejection is thrown as it is. `onQuery` hears both attempts. The bookmark set back is then the new Session's (#237). A bookmark given to `connect(binding, { session })` isn't started again: D1's error is thrown. Either way, a long bookmark in that error's message, and its cause's, is cut to 64 characters, since a request may have sent it.
  - **Where it travels:** by default a `d1-bookmark` cookie, read from the request's `Cookie` header (an empty value is none) and appended as `Set-Cookie: d1-bookmark=…; Path=/; HttpOnly; Secure; SameSite=Lax`, after any cookies `fn` set. It has no `Max-Age`, so it lasts the browser's session: an old bookmark only asks for data at least that new. `cookie` renames it. `header` carries it in that request header and response header instead (set, replacing one `fn` set), with no cookie. `cookie` and `header` together are a type error, and reject with `TypeError` before `fn` runs. The options also take `connect()`'s `onQuery`.
  - **The response:** one whose headers can't change (from `fetch()` or `Response.redirect()`) is copied, with its status and headers, before the bookmark is set; any other is returned as it is.
  - **Errors:** what `fn` throws reaches the caller unchanged, and no bookmark is set.
  - One binding per call. For several, nest calls, each with its own `cookie` or `header`: `withDatabase` adds nested databases to the outer ones.
- **Statics:** every Relation method is a static of every Model (`find`, `findBy`, `where`, `whereNot`, `order`, `first`, `count`, `pluck`, `build`, `create`, `insert`, `insertAll`, `upsert`, `updateAll`, `deleteAll`, …), as Rails delegates them to `all`, plus `Model.all()`, the Relation itself, and the Model's scopes (`User.active()`). Each is typed for the class it's called on, so on a subclass it returns that subclass's records. They query the **current database**: the request's, then the Model's binding. Building a Relation never queries, so statics can be called anywhere; running one needs a database.
- (D1) **The binding (level 1):** the generated schema a Model's base class holds names the D1 binding it queries when there's no request database, as Rails' `connects_to`; `active-record schema` writes it, per binding. It's read from `import { env } from "cloudflare:workers"`, loaded only when a query needs it, so the library imports fine in Node. That `env` object is read once and kept, so a test that mocks `cloudflare:workers` (with `@forestfuture/active-record` inlined by Vitest, `test.server.deps.inline`) assigns its bindings onto the mocked object rather than replacing it; that's how tests give each Model its own database when there are several (#227). Each binding gets one Database, holding nothing per request (no Session, no listener), shared by every request: safe across concurrent requests in one isolate.
- (Postgres) `connect(source, { onQuery })` takes a Hyperdrive binding (`env.HYPERDRIVE`), a connection string (`env.DATABASE_URL`), or the app's `pg` Pool, which the app ends. From a binding or a string, no client lives across requests: inside each `withDatabase` call, its first query opens a client that serves that call (a call nested in a running one with the same Database shares it; one that runs after the outer call returns, such as `ctx.waitUntil(withDatabase(db, …))` started inside it, opens its own), closed once the call has ended and the operations sent before then finish, in the background, so `withDatabase` (and the response) never waits for them, and one Database opened at module scope serves overlapping requests, each on a client of its own (a scope whose client loses its connection opens another for its next query, even one queued behind the query that lost it); outside a scope, before or after one, each operation opens a client and closes it when it's done, so work that outlives its scope (a save in `ctx.waitUntil`) still runs. A scope's operations take turns on its client, in the order they're sent (#288): each waits until the one before it is done, and a read batch keeps the client for all its statements, so `pg` never gets a query while another is running (`pg` 8 deprecates its own queue for those). A Pool lends a client per operation. Opening a client from a binding or a string waits up to 10 seconds for Postgres to answer, or the connection string's `connect_timeout` (a Hyperdrive binding's string isn't the app's, so it always waits the 10), read as libpq reads it (#292): whole seconds, 0 or less for no limit, and 1 counted as 2. `pg` reads it only through libpq, so the PostgreSQL adapter passes it as `connectionTimeoutMillis`. One that isn't a whole number throws `TypeError` when the Database is built, naming the parameter and its value but not the connection string. An open that takes longer fails with `Error: timeout expired` (libpq's message, and `pg`'s on Node), `pg`'s own error as its `cause`, on Workers too, where `pg` reports it as a dropped connection. An open that fails sooner keeps its own error. The parameter is read from the string's query on its own, before any `#`, its last when it's given twice, as `pg` reads its parameters, so a socket's string with no host (`postgres://app@/app?host=/tmp`) has it read too, and a limit past what a timer holds (2^31-1 ms, about 24 days) is capped there. Operations queued behind an open that times out each try again, so each waits up to the limit. A Pool keeps its own settings (`connectionTimeoutMillis`). Rails sets no limit. `withDatabase` tells each of its databases when its scope begins and ends, through the `Driver`'s optional `openScope` and `closeScope` (`/adapter`), and hands what `openScope` returned to every statement sent inside it.
- (Postgres) **The binding (level 1):** a Model whose schema names `postgresql({ binding })` reads that binding from the Worker's env, as a Hyperdrive binding or a connection string. It uses the request's database opened from the same connection string, or from a Pool built from it (`new pg.Pool({ connectionString })`; a Pool built any other way never serves statics, and a matched Pool serves the binding with all its own settings, its `options` such as a `search_path` included, as a request's database wins on D1), or else the binding's own, which holds no client between operations. Outside a Worker, statics use the request's database, as on D1. Each adapter imports `cloudflare:workers` itself, so a test mocks it with that adapter inlined, and the core's `workersEnv()` (`/adapter`) tells a Worker from Node for both.
- **The request's database (level 2):** `withDatabase(db | [db, …], fn)` runs `fn` with those databases as the request's own, through Workers' `AsyncLocalStorage`: every query started from a Model inside it, and everything it awaits, uses the one whose D1 binding is that Model's binding, with its Session and `onQuery`. Nested calls add to the outer ones, and a Database given twice (in one call, or again in a nested one) counts once. Outside a Worker (Node, scripts), where there's no binding to match, the request's database on a Model's adapter serves it if there's one, and several on that adapter are an error; one D1 database and one Postgres database each serve their own Models (#305). `AsyncLocalStorage` is loaded with `process.getBuiltinModule("node:async_hooks")` when `withDatabase` is first called, so Workers without Node.js compatibility still build; calling it there throws `NoDatabase` naming the setting (a `compatibility_date` of 2026-08-04 or later, or `nodejs_compat`).
- **An explicit database (level 3):** `db.model(X)`, `db.models({...})` and `db.batch(…)` always use `db`, whatever `withDatabase` says.
- **Errors** (`NoDatabase`, saying what to do): a Model whose base class holds no generated schema, outside `withDatabase`, which can't even compile a statement, as its schema names its adapter; a binding only available inside a Worker, queried outside one; several request databases on one adapter outside a Worker; a binding that isn't in the Worker's env (check `d1_databases`). A query at a module's top level fails with Workers' own error: D1 calls happen during a request.
- **One database per query and write (#93).** Whether two handles are one database is decided by the database each resolves to, for every operation: `merge()`, `or()` and a scope's result when the query runs; `batch`, `db.batch`, `save()` and `destroy()` before anything else runs, with no validation, callback or write when they're refused. A save, batch or destroy checks every record it will write: a save's whole autosave graph (the records built through its associations and the new records it points at through `belongsTo`, at every level), and a destroy's dependents. Records reached through an association to another database (#228, see _Associations_) are a separate write on theirs, checked on their own; a batch, which writes one database, refuses them before anything runs. So inside `withDatabase`, a loaded record's association merges with a Model's static Relation, since both resolve to the request's database. Two databases throw `IncompatibleRelation` naming where each came from ("the request's database", "the DB binding's database", "a connect() database"), and `db.batch()` names itself. A Database given to `withDatabase` is "the request's database" in errors for its life, including after `withDatabase` returns. Every record a save, destroy or batch writes keeps the database it ran on, as the record itself does.
- **`batch((b) => [...])`** writes atomically, as `db.batch` does: a Model given to `b` (`b.insert(Post, …)`) is written on the current database, and a Relation or record on the database it came from. Writes on two databases throw `IncompatibleRelation`.
- No request state is ever stored on a Model class (ADR-0012): a request's database lives only in its `AsyncLocalStorage`.
- Every record keeps the Database it was built or loaded through. Records come only from `build()`, `create()` or a query. A record constructed directly with `new User()` throws `NoDatabase` on any operation that needs D1; `User.build(…)` makes one on the current database.

## Declaring a Model

_Portable._ A bullet or sentence marked (D1) is the D1 adapter's alone.

_Guide:_ [models](<../site/docs/(basics)/models.mdx>), [untrusted-input](<../site/docs/(how-to)/untrusted-input.mdx>), [querying](<../site/docs/(basics)/querying.mdx>), [adopt-a-database](<../site/docs/(how-to)/adopt-a-database.mdx>). _Code:_ `active-record/src/model.ts`, `active-record/src/model-statics.ts`, `active-record/src/generated-model.ts`, `active-record/src/metadata.ts`, `active-record/src/spec-keys.ts`, `active-record/src/table-names.ts`, `active-record/src/verify-model.ts`, `active-record/src/permit.ts`, `active-record/src/attribute.ts`, `active-record/src/conversion.ts`, `active-record/src/attribute-conversions.ts`.

A Model extends the app's base class (`ApplicationRecord`). A **generated Model**'s attributes are its table's in the generated schema (see The generated schema): `class Post extends ApplicationRecord {}`. A **hand-declared Model** declares them in its class, with `define`:

```ts
class User extends ApplicationRecord.define({
  id: { type: "string", null: false, generateId: true },
  email: { type: "string", null: false },
  isActive: "boolean", // column: is_active
  htmlUrl: "string", // column: html_url (acronyms are handled)
  legacyId: { type: "integer", column: "person_identifier" },
  createdAt: "datetime",
  updatedAt: "datetime",
}) {
  static primaryKey = "id"; // default

  static active = this.scope((q) => q.where({ isActive: true }));
  static createdAfter = this.scope((q, since: Date) => q.where(sql`created_at > ${since}`));

  static {
    this.validates("email", { presence: true, uniqueness: true });
    this.beforeSave((u) => {
      u.email = u.email.toLowerCase();
    });
  }
}
```

- A hand-declared Model's attributes are declared once, in the object passed to `define` (`Model.define({...})`, or `ApplicationRecord.define({...})` to build on the app's base class), and TypeScript infers the instance properties from it: no `declare`, no second declaration (ADR-0007). An entry is either a type name or `{ type, column?, null?, default?, generateId?, storage? }`. Any other key in an entry is a compile error (#102).
- **Narrowing (#232).** `declare status: "draft" | "published"` in a Model's class narrows that attribute's property type, for reading and assigning it. Nothing checks the value at runtime, and `build`, `where` and the other methods that take attributes still take the column's type.
- A Model's `table` is inferred from its class name by Rails' `tableize`: `underscore`, then pluralized by Active Support's default English inflections (rules, irregulars such as `person` → `people`, uncountables such as `sheep`), ported so tables are named as in Rails: `User` → `users`, `BlogPost` → `blog_posts`, `APIKey` → `api_keys`. An explicit `static table` always wins, and is the way to name a table the rules don't (there's no inflection configuration, which would be module-level state, ADR-0012). It's inferred from the class directly below a base class (the app's, one marked `static abstract = true`, or the class `define` makes), so a subclass shares its parent's table, as in Rails. Reading `Post.table` gives it. Rails' quirks come with the rules (`Human` → `humen`, `Leaf` → `leafs`), and `static table` fixes them. A class with no name to infer from (anonymous, or `export default class`) throws `InvalidModel` when first used, unless it sets `table`. Assigning `table` (a static block, or a class field compiled without `useDefineForClassFields`) sets it as declaring it does. Like inferred foreign keys, it needs the class to keep its name when bundled (a generated Model that doesn't is caught by the schema's `models` list); a Model's own `modelName` for this is #47. When D1 reports "no such table" for an inferred name, the error is an `InvalidModel` saying where the name came from, with D1's error as its `cause`. A declared table that's missing is D1's own error.
- Attributes are camelCase and map automatically to snake_case columns (ADR-0004), using Rails' `underscore` rule, which treats a run of capitals as one word: `createdAt` → `created_at`, `externalAccountId` → `external_account_id`, `htmlURL` → `html_url`, `userID` → `user_id`, `sha256Hash` → `sha256_hash`. `column` overrides the mapping for one attribute.
- Types: `string`, `integer`, `real`, `boolean` (0/1), `datetime` (a `Date`, stored as ISO-8601 TEXT; text with no zone, such as SQLite's `CURRENT_TIMESTAMP` writes, reads as UTC in any time zone; or, with `storage`, as an integer Unix time), `json` (stored as JSON text, in a `TEXT` column as D1 recommends; adding `CHECK (json_valid(column))` makes D1 reject invalid JSON). A column declared `JSON` also works: SQLite stores number-like values in it as numbers, and they still read back as the value written.
- **`storage` (#73).** A `datetime` declared with `storage: "unixSeconds"` or `"unixMilliseconds"` is held in its column as an integer Unix time, as Drizzle's `timestamp` and `timestamp_ms` modes write it. It's still a `Date` in JavaScript, and it's cast like any `datetime` (an ISO string or a `Date`; a number is refused). It's written as an integer (seconds are floored, so a `Date` is kept to the second), read as `new Date(n * 1000)` or `new Date(n)`, and compared as integers by `where`, `gte`, `between` and `order`. `createdAt` and `updatedAt` are set through it. An assignment that stores the same integer isn't a change. `storage` on any other type, or any other value, is a compile error and an `InvalidModel`. Conditions compare the stored integer, so under `unixSeconds` a `Date` with milliseconds compares to the second. A `Date` interpolated into an `sql` fragment has no attribute, so it's written as ISO text and won't compare with the integer; use `column(attribute).value(date)` there, which writes it as the attribute stores it (#142). (D1) A column holding both `T…Z` text and SQLite's space form (Prisma's engine writes and its `CURRENT_TIMESTAMP` default) reads both as UTC but compares as text, so `order` and range conditions can misplace values within a day; the guide shows a migration that rewrites every date text form to Active Record's with `strftime` (leaving NULLs and anything it can't read), and a fragment that compares through `strftime` for a column another tool still writes (the comparison can't use the column's index) (#143). A cell in a `storage` column that isn't a Unix time (text, or past the range of a `Date`) raises `TypeError` when the record loads or `pluck` reads it, naming the Model and attribute and showing the value as an assigned one is shown, hidden for a filtered attribute. Reading is strict: an integer-storage column doesn't also read ISO text, since the tools that write epochs don't mix them (checked: Drizzle writes integers by its mode and by `unixepoch()` defaults; Prisma on D1 writes ISO text, so needs no `storage`).
- **Casting (#81).** A value is cast to its attribute's type when it's assigned (`build`, `create`, `assign`, `update`, a property setter, a default) or given to a bulk write (`insert`, `insertAll`, `upsert`, `upsertAll`, `updateAll` and their `to…` forms), so reads, validations and callbacks see the cast value. Only what's unambiguous is accepted; anything else throws `TypeError` (`Sample: "no" isn't a boolean for "enabled"`), and the attribute keeps its value. `null` is always NULL. `undefined` is refused the same way wherever an assigned value is cast (an assignment, `permit`, a bulk write, `column(attribute).value(undefined)`): `Sample: got undefined for "enabled"; use null to store NULL` (#163).
  - `boolean`: `true`/`false`, `1`/`0`, `"1"`/`"0"`, and `"true"`/`"false"` or `"on"`/`"off"` in any case.
  - `integer`: a safe integer, or a string that's wholly one (`" 42 "`, `"-7"`, `"+3"`). Not `1.7`, `"12abc"`, `"1e3"`, `""`, `NaN` or past `Number.MAX_SAFE_INTEGER`.
  - `real`: a finite number, or a string that's wholly a decimal number (`"1.5"`, `".5"`, `"-2e3"`).
  - `string`: a string only (not `5`, `true` or a `Date`).
  - `datetime`: a valid `Date`, an ISO-8601 date (`"2026-01-02"`, midnight UTC), or a date and time with `Z` or an `±HH:MM` offset (`T` or a space between them; `T` and `Z` uppercase). Not a time without an offset, a day that doesn't exist (`"2026-02-30"`, with or without a time), other formats or numbers (#73).
  - `json`: any value JSON can write, unchanged (#146).
    - A value JSON can't write (`JSON.stringify` throws, as for a BigInt or a cycle, or gives nothing, as for a function or a symbol) is `uncastable`: an assigned value throws `TypeError` (`Doc: 10 isn't a JSON value for "settings"`), a condition matches nothing, and a bulk write refuses it.
    - A value JSON writes lossily (a `Map` as `{}`, `NaN` as `null`) is kept as JSON writes it.
    - A value changed in place into one JSON can't write throws the same `TypeError`, naming the attribute, at save, `isChanged()` and `changes()`.
    - (Postgres) A `bigint` cell reads as a number, and one past `Number.MAX_SAFE_INTEGER` throws the same `TypeError`, showing its digits. Each adapter reads its database's values as the core keeps them (booleans as 1 and 0, times as ISO text, JSON as its text), the PostgreSQL adapter through type parsers given per query, so the app's own `pg` keeps its defaults.
    - A `json` cell that isn't JSON throws the same `TypeError` when the record loads (`find`, a list, `reload`, a preload) or `pluck` reads it, instead of the parser's `SyntaxError`, and fails the list it's in. The cell is shown as an assigned value is, hidden for a filtered attribute.
  - Unlike Rails, which casts `"12abc"` to `12`, `1.7` to `1`, `5` to `"5"`, any other non-blank string to `true`, and `""` to `nil`: Active Record refuses each, so a value from JSON, a form or a query string is never read as something it isn't.
  - Values inside `sql` fragments aren't cast, except one written as `column(attribute).value(v)`, which is cast as an assigned value (#142).
- **Reading a stored cell is strict (#159).** A cell the database returned is read as the attribute's type or refused: the record loads (`find`, a list, `reload`, a preload), `pluck`, and `typeForAttribute(name).deserialize` all throw the same `TypeError` (`Reading: 2 isn't a boolean for "enabled"`), naming the Model and attribute, showing the cell as an assigned value is shown, and hiding it for a filtered attribute. A list holding one fails whole. NULL is `null`, and a cell is never coerced. Proven on D1 alone (`tests/integration/d1/strict-reads.test.ts`), since its tests need columns that hold any type.
  - `boolean`: `0` and `1`. `integer`: a safe integer. `real`: a finite number. `string`: text.
  - `datetime`: text in a form an assignment accepts (a date, or a date and time with `Z` or an offset), exactly what `toISOString` writes for a year outside 0000 to 9999 (`+010000-01-01T00:00:00.000Z`), or SQLite's zone-less form (`YYYY-MM-DD HH:MM:SS`, with `T` for the space, no seconds, or a fraction), read as UTC. A day that doesn't exist (`2026-02-30 03:04:05`) and a number are refused: a number is a Unix time, which needs a `storage`.
  - `datetime` with a `storage`: a number, whole or fractional, in the range of a `Date`. Text, `""` and `true` are refused, where they were once read through `Number()`.
  - `json`: text that parses; any other cell is the value as it is (a number D1 returned for a number-like value, for one).
  - A record's snapshot and initial values are cells the library wrote, so they always read. There's no switch to turn the check off.
- Attribute properties are prototype accessors. The first time a Model is used, `db.model(X)` throws `InvalidModel` if it has no table name (an empty `table`, or no class name to infer one from), if a class field hides an accessor (e.g. `email!: string` in the class body), or if an attribute is named like a record method (`attributes`, `save`, `constructor`, …). Rename such an attribute and map it with `{ column }`.
- SQL fragments are SQL, so they use column names (``sql`created_at > ${since}` ``), or `column("createdAt")` to look the column up from the attribute (ADR-0006), and `column("createdAt").value(since)` for a value written as that attribute stores it (#142).
- `Model.typeForAttribute(name)` (#148) gives an attribute's conversions, for SQL Active Record doesn't write (a raw `env.DB.prepare(…).bind(…)`, a cache key, a row checked in a test): `cast(input)` is the JavaScript value, as assigning it would give, with nothing floored (a `Date` keeps its milliseconds under `unixSeconds`); `serialize(input)` is `input` cast, then as D1 stores it, the same value `column(name).value(input)` binds (seconds are floored); `deserialize(cell)` is a cell D1 returned as the JavaScript value. `cast` and `serialize` throw `TypeError` naming the Model and attribute for a value the attribute can't hold, and for `undefined` as assigning it does; `null` is `null`. `deserialize` reads as a record load does, so it gives `null` for NULL and `undefined`, and throws the same `TypeError` for a cell that can't be read (#159), as a load does. A filtered attribute's value is `[FILTERED]` in those errors. It needs no connection; an unknown name is `UnknownAttribute`, and a name that isn't an attribute is a compile error. The object is frozen, and each method works on its own, destructured.
- `db.model(X).build(attrs)` makes a new record without querying. Before an attribute is assigned, it reads as `null`. Defaults are evaluated at `build()` (a default returning `undefined` throws `TypeError`, as for any assignment), so app-generated keys (UUID, CUID, ULID) exist before saving.
- **Generated ids (#99).** A `string` attribute declared with `generateId: true` that isn't given gets the Model's `static generateId(attribute)`, wherever a default would run: at `build()`, and in bulk writes (`insert`, `insertAll`, `upsert`, …) for rows that leave it out. `Model.generateId` returns `crypto.randomUUID()`; an app overrides it on its base class (`static override generateId = () => uuidv7()`), or a Model on itself, and it's inherited. It gets the attribute's name, never the record. Its result is cast as an assigned value, so a non-string throws `TypeError`. An attribute with both `generateId` and a `default`, or `generateId` on a type other than `string`, is an `InvalidModel` when the Model is first used, and a compile error. `generateId` is a Model static, so no scope can use the name.
- A record built or created from a Relation starts with that Relation's single equality values: `where({ role: "admin" }).build()` has `role: "admin"`. Arrays, `whereNot`, `or` and `sql` fragments carry nothing over, and explicit attributes win. Those values, and a key copied from another record (a `hasMany` or `hasOne` build, an association's `insert`, `upsert` or `insertAll`, `belongsTo` `set()`, or the key autosave fills in once D1 generates it), are cast as a condition's value is, not as an assigned one (#94): `where({ label: 7 }).build()` has `label: "7"`, and an integer key written into a text foreign key becomes its digits. One that still can't be cast throws `TypeError`, naming the association it came through (`Counted: "abc" isn't an integer for "quantity", the key of code`). Every value the compiler writes is cast as it's bound, so no write depends on a caller casting first. Preloading (`includes`) matches each record's key to its targets the same way, so an integer key finds a text foreign key's digits.
- `record.assign(attrs)` assigns several attributes without saving. `update(attrs)` is `assign` then `save`. An unknown key throws `UnknownAttribute` and an `undefined` value throws `TypeError` (use `null` to store NULL), in `build`, `create`, `assign`, `update`, and when setting a property (`user.email = undefined`).
- **`Model.permit(input, ...names)` (#82)** keeps only the named attributes of untrusted input, as Rails' `params.permit`, so a request can't set any other attribute (mass assignment). `input` is a plain object (its prototype is `Object.prototype` or `null`; only its own keys are read, so `__proto__` never counts), `FormData` or `URLSearchParams` (a repeated key takes its last value, as in Rails); anything else, such as an array, a `Map`, `Headers` or a class instance, throws `TypeError`. A named attribute the input doesn't have is left out; a `null` is kept; every other key is dropped silently. A name that isn't an attribute throws `UnknownAttribute`, and is a compile error. Each value is cast as assigning it would be (#81), so the result, typed `Partial<Pick<attributes, names>>`, is what its type says before it's assigned, and goes straight into `build`, `create` or `update`: a value that can't be cast throws `TypeError`, and so does a file (a `Blob` from a form), which no attribute stores. It's a static, so subclasses and the app's base class have it.
- An insert writes only **assigned** attributes: given to `build`/`create`, set through a property, or filled by a `default`. Anything else is left out, so the column's database default applies. `RETURNING *` then loads what D1 actually stored, including generated keys and defaults.
- An update writes only the attributes that changed. A save with nothing changed sends no statement. Changing the primary key is allowed, and the UPDATE finds the row by the key as last loaded or saved.
- If the row is already gone (e.g. another request deleted it), `save` and `destroy` still succeed. `reload()` throws `RecordNotFound`, since there's nothing to load, and so does reloading a record that was never saved.
- Timestamps are on when `createdAt`/`updatedAt` are declared as `datetime` attributes. They're set in JavaScript (`new Date()`) just before the write is compiled: both on insert, and `updatedAt` on an update that changes something. A clean save leaves `updatedAt` alone. A timestamp assigned explicitly is kept.
- Keys that aren't declared attributes throw `UnknownAttribute` in `build`, `create`, `update` and `where`, and are compile errors where the types can see them.

## The command

_Portable._

_Guide:_ [command-line](<../site/docs/(basics)/command-line.mdx>). _Code:_ `active-record/cli/main.ts`, `active-record/cli/adapter.ts`, `active-record/cli/project/adapters.ts`, `active-record/cli/project/databases.ts`, `active-record/cli/project/config-file.ts`, `active-record/cli/migrate/`, `active-record/cli/adapters/d1/plugin.ts`, `active-record/cli/adapters/d1/databases.ts`, `active-record/cli/adapters/d1/migrate.ts`, `active-record/cli/adapters/d1/installed-wrangler.ts`, `active-record/cli/adapters/postgresql/plugin.ts`, `active-record/cli/adapters/postgresql/config.ts`, `active-record/cli/adapters/postgresql/runner.ts`.

- One command, `active-record` (also `ffar`), comes with `@forestfuture/active-record` (#278): `init`, `schema`, `g model`, `g migration`, `console` (`c`) and `migrate`. There's no `d1-record` command.
- **Finding the adapter (#301, ADR-0019):** the project's `active-record.jsonc`, or the file `--config` names, names each database's adapter: `"DB": { "adapter": "d1" }`, `"HYPERDRIVE": { "adapter": "postgresql", … }`. The command reads it and never guesses. Without the file, it says to run `npx active-record init`; a file that isn't an object, or can't be read, a file with no `databases`, an entry that isn't an object, an entry with no `adapter` (naming the ones there are), or one that isn't an adapter, is refused, naming it. **Each database uses the adapter its entry names (#305):** one project can hold a D1 database and a PostgreSQL one. The command loads the plugin of every adapter the file names (checking `unsupported` for each before anything is read) and hands each plugin only the entries for it; `schema` reads each database with its own plugin, and the generators, `migrate` and the console use the plugin of the database `--database` chooses. Every plugin's notes are printed. Two databases on different adapters whose migrations folders are one folder are refused, naming both (`DB and HYPERDRIVE both read migrations/, on different adapters (d1 and postgresql); give each its own migrations folder`, or each one's path when a link makes them one folder), since both adapters default to `migrations/`; databases on one adapter may share one. There's no `--adapter`, but on `init`.
- **`init`** writes `active-record.jsonc` (or the file `--config` names). When the file is there, it adds each database that the adapters the file names (or, with `--adapter`, that adapter, #305) find there and the file doesn't name, as `{ "adapter": … }` lines at the end of its `databases`, indented as the entries before them and with a trailing comma if the last had one, and leaves the rest of the text as written, comments included (`Added LOGS to active-record.jsonc (on d1)`, or `Added LOGS and CACHE to active-record.jsonc (LOGS on d1, CACHE on postgresql)` across adapters, with notes for the added ones only, or `… names every database init finds; it wrote nothing`); without `--adapter` it adds no database of an adapter the file doesn't name, so a D1 binding kept in Wrangler's config during a move to Postgres isn't added back; `--adapter` naming an adapter the file already uses adds what that plugin finds, with no guess (`init(dir, false)`), and one this Node can't run (`unsupported`) adds nothing, saying why; and a file the command can't read is left as it was. It never writes through a link at the file's own path, even one to nothing. Each adapter's plugin says what it finds in the Wrangler config beside the file (`init(dir, named)`): D1, each `d1_databases` binding, as an entry with only its adapter; PostgreSQL, each Hyperdrive binding, with its `localConnectionString` as `url` (or a guess, noted). Exactly one adapter with something found is used; both, or neither, need `--adapter d1|postgresql` (with both, it says to run `init` again with the other to add its databases too), and with `--adapter postgresql` and no Hyperdrive binding it writes `DATABASE_URL`, its `url` a guess named as Rails names a development database (`postgres://localhost:5432/shop_development`, from the folder's name), noted. An `--adapter` that isn't one says which there are. The file opens with `"$schema"`, a relative link to the `config-schema.json` the package ships, in the nearest `node_modules` that has the package (or the project's, once installed), for an editor to complete and check it; the schema describes each adapter's entry, with `adapter` required. It prints `Wrote active-record.jsonc (DB and LOGS, on d1)`, any notes, then `Next: npx active-record schema`.
- **The plugin:** an adapter's plugin exports `cli`, typed by the core's `/cli` (`CliAdapter`, unstable): its name (the registry's, which a database's `adapter` names), what `init` writes for it, why this Node can't run it (`unsupported`, checked as it loads, before any command starts), the config setting a migrations pattern comes from (`patternSetting`, if it reads one), the project's databases from the entries `active-record.jsonc` has for it (`ProjectDatabases`), with its own config, a database's tables read from its migrations (asynchronously, given its config entry, and with each key column's declared type when it reads one), a migration's SQL (the command names its file) with notes for what it guessed, the remote database a person confirms, the folder for the command's local files (`stateFolder`), opening a database for the console, and applying migrations. The database it's handed (`ChosenDatabase`) carries its binding, its config entry, its config file and its migrations folder. Each plugin ships with the command, which imports it when a project's file names its adapter. The core keeps everything else, and names no database: its help and messages say the database, its binding and its config, and what is one database's to say (Wrangler, `.wrangler`, `migrations_pattern`) comes from the plugin (#284). A unit test fails on any database named in `active-record/cli/` outside the registry of adapters.
- **The project's config file** is `active-record.jsonc`, beside `package.json`, or the file `--config` names (JSON with comments and trailing commas). The core reads it, and hands each plugin its databases' entries, so later settings can go in it too. (D1) A D1 database's settings stay in its Wrangler config: the one its entry's `wranglerConfig` names, relative to the file (`"DB": { "adapter": "d1", "wranglerConfig": "../worker/wrangler.jsonc" }`, for a Worker in another folder, #306), or else the one beside the file (`wrangler.jsonc`, `wrangler.json` or `wrangler.toml`), which is needed only when some D1 entry names none. Databases may name different Wrangler configs. A `wranglerConfig` that isn't a string, isn't there, or is a folder is refused, naming the setting and its path relative to the file. Each binding the file names must be in its config's `d1_databases`, or that's an error naming it and the config's path (`active-record.jsonc names DB, which isn't in ../worker/wrangler.jsonc's d1_databases`). Its migrations folder, `migrations_pattern` and local state (`.wrangler/state`) are relative to its Wrangler config's folder, as Wrangler reads them. Wrangler's other D1 databases, in each config the file's D1 databases read, are left out, each noted by `schema`, `g`, `migrate` and the console ("wrangler.jsonc has the D1 database LOGS, which active-record.jsonc doesn't name", saying to run `npx active-record init` to add it; `init` reads only the config beside the file, so for a config elsewhere the note shows the `"wranglerConfig": "../worker/wrangler.jsonc"` line that adds it). (Postgres) A Postgres database's settings are its entry: `{ "databases": { "HYPERDRIVE": { "adapter": "postgresql", "migrationsDir": "migrations", "url": "postgres://localhost/shop_development", "remoteUrl": "${PRODUCTION_DATABASE_URL}" } } }`. `migrationsDir`is`migrations`unless set;`url` is the local database (`migrate`and the console),`remoteUrl` the real one (`--remote`), and `schemaUrl`a server the schema may be read on when PGlite can't load an extension (never`url`, so a read reaches no server the app uses unless asked). Each `${NAME}` in them is read from the environment when it's used, and one that isn't set is an error naming it. A connection string is never printed: messages name its database and host. A setting that isn't a string is refused, naming it.
- **`migrate`** applies a database's pending migrations, to the local database by default. `--database` chooses one, as for the console. `--remote` names the real database and asks for its name to be typed first, as the console does, and `--yes` skips that (the only way without a terminal). (D1) It runs the project's `wrangler d1 migrations apply <binding> --local` or `--remote`, with its config, printing what Wrangler prints, and exits with Wrangler's code. (Postgres) The PostgreSQL adapter's runner applies them itself, to `url`, or with `--remote` to `remoteUrl`, which needs the real database's password in the environment and a network route to it. It prints the database (`Local database HYPERDRIVE (shop_development on localhost)`), then `Applied <file>` for each migration, or `No migrations to apply`. Migrations are the folder's `.sql` files, each with its version, the number its name starts with, applied in the order of their versions as numbers (`9_…` before `10_…`), the order Wrangler applies D1's in; a file without one, two with one version (`1_…` and `01_…` count as one), or a migration with its own transaction control (`BEGIN`, `COMMIT`, `ROLLBACK`, `END`, `ABORT`, `START TRANSACTION`, `PREPARE TRANSACTION`, outside strings, comments and `$$` bodies; savepoints are fine) is refused before any runs, by `schema` and the generators too. It holds an advisory lock for the database and schema while it runs, and a run that finds it held exits 1 at once ("Another migrate is running on this database"), as Rails refuses one; creates `schema_migrations (version TEXT PRIMARY KEY)` if it's missing; and applies each pending migration in a transaction with its version's row, so one that fails is rolled back whole (`<file> failed: <Postgres's message>`, exit 1) and none after it runs. A migration that can't run in a transaction (`CREATE INDEX CONCURRENTLY`) fails. There's no status or rollback, on either adapter.
- The generators' next step is `npx active-record migrate` (with `--database` when there are several).

## The generated schema

_Portable: the schema, its Models and `--check` are the core's, and each adapter reads its own database's columns._

_Guide:_ [schema](<../site/docs/(background)/schema.md>), [adopt-a-database](<../site/docs/(how-to)/adopt-a-database.mdx>), [command-line](<../site/docs/(basics)/command-line.mdx>). _Code:_ `active-record/cli/schema/`, `active-record/cli/project/`, `active-record/cli/adapters/d1/schema.ts`, `active-record/cli/adapters/d1/conventions.ts`, `active-record/cli/adapters/d1/wrangler.ts`, `active-record/cli/adapters/postgresql/schema.ts`, `active-record/cli/adapters/postgresql/catalog.ts`, `active-record/cli/adapters/postgresql/conventions.ts`, `active-record/cli/adapters/postgresql/extensions.ts`, `active-record/cli/adapters/postgresql/server-schema.ts`, `active-record/src/generated-model.ts`, `active-record/src/spec-keys.ts`.

`npx active-record schema` (Node 22.13+) writes `src/db/schema.ts` from the project's D1 migrations and its Models, the migrations found through its Wrangler config (`migrations_dir`, `migrations_pattern`, `migrations_table`; one file per binding when there are several). It applies them to an in-memory SQLite database and converts each table's columns to attributes by convention: the declared type first (`INTEGER`, `TEXT`, `REAL`, `BOOLEAN`, `DATETIME`/`TIMESTAMP`/`DATE`, `JSON`, a `TEXT` with `CHECK (json_valid(…))` as `json`), then, only for a column declared exactly `TEXT` or `INTEGER`, its name (`…_at` `TEXT` → `datetime`, `is_…`/`has_…` `INTEGER` → `boolean`, printed as a note). A column with no declared type, or one that matches none of these (`UUID`, `ANY`), is read as a `string` and gets a note that a number in it fails when the record loads (#159), whatever tool wrote the migration. `NOT NULL` → `null: false`; literal defaults are copied, and a `TEXT` primary key without a literal default gets `generateId: true`. `NUMERIC`/`DECIMAL`, `BLOB`, composite or missing primary keys, and names that would collide are errors that say what to do; a broken migration is reported by file name and the last good file is kept. A `DATETIME` or `TIMESTAMP` column whose default is a number or an epoch function (`DEFAULT 0`, `unixepoch()`, `strftime('%s', …)`) gets a note naming the `storage` override, whatever tool wrote the migration. Migrations written by Drizzle or Prisma (recognized by `drizzle.config.*`, `schema.prisma`, `prisma/schema.prisma` or `prisma.config.ts` in the database's config's folder (on D1, its Wrangler config's) or a folder above it up to the repository's root, or by the `--> statement-breakpoint` and `-- CreateTable` lines they write) add more notes, since those tools can store values differently. The first names the tool and links #73. Then each column worth checking gets one, whether it's named in snake_case or camelCase. An `INTEGER` named `…_at`/`…At` may hold a Unix timestamp, and its note shows the `storage` override that reads it as a `Date`, naming Drizzle's `timestamp` and `timestamp_ms` modes for Drizzle. A `TEXT` without a `json_valid` check named `…_json`/`…Json`, `metadata`, `settings`, `payload` or `properties` may hold JSON. A `DATETIME`/`TIMESTAMP` column whose default is `CURRENT_TIMESTAMP` or `datetime('now')` gets a note, under a recognized tool's migrations only: its default writes `2026-10-12 06:38:30` where Active Record writes ISO text, and the two sort apart as text (#143). A Prisma `datetime` otherwise gets no note, since Prisma writes ISO text to D1. These per-column notes come only with a recognized tool's migrations: they're hints, where the `is_…` note reports a guess the generator made for you. Notes come with a file that's written, so they don't repeat when it's up to date, while watching, or with `--check`. Migrations in folders (`migrations/0000_init/migration.sql`, as Drizzle writes them) with no `migrations_pattern` to find them get a note, every time, naming the pattern to set and the config file to set it in (the plugin's `patternSetting`; an adapter without one is told they aren't read). It never replaces a file it didn't write (one without its "Generated by" header, such as a Drizzle schema), and never writes a file next to a folder of the same name (`src/db/schema.ts` beside a Drizzle `src/db/schema/`), whose imports it would take over; either is an error suggesting `--out`, and the generators check it before writing anything. `--check` fails when the file is stale (it compares a fingerprint of the schema, its adapter and its Models, so formatting doesn't matter), and `--watch` regenerates as migrations or Model files change; when its adapter won't load (none installed, or a Node the plugin can't run on), it says why and exits 1 without watching. `--migrations <dir>` reads the migrations from another folder (one database only), and `--config <file>` names the project's config file in place of `active-record.jsonc`.

(Postgres) On Postgres, `npx active-record schema` reads each database in `active-record.jsonc` from its `migrationsDir`. It applies the migrations in order to an in-memory PGlite, so it needs no server, and reads each table's columns from the catalog, in the current schema (`public` on PGlite), leaving out views, other schemas, partitions and `schema_migrations`. A table is last changed by the migration that changed its columns or constraints (an index alone doesn't count). Types map by the catalog's base type (a domain's underlying one): `smallint`, `integer` and `bigint` → `integer`; `real` and `double precision` → `real`; `boolean`; `timestamptz`, `timestamp` and `date` → `datetime`; `json` and `jsonb` → `json`; `text`, `varchar`, `char`, `citext`, `uuid`, `name` and enums → `string`. `numeric`, `bytea` and arrays are errors that say what to do; any other type (`inet`, `interval`) is read as a `string`, with a note to override it in its Model if it holds another type. Names don't change a type, as Postgres's types are real. `NOT NULL` → `null: false`; literal defaults are copied with their casts taken off (`'it''s'::text`, `'{}'::jsonb`, `-1`, `true`), and a function's (`now()`, `gen_random_uuid()`) is left to Postgres. A string key without a literal default gets `generateId: true`, even with a database default, so autosaves can link it (ADR-0013). A migration that creates a contrib extension PGlite has its own build of (`citext`, `uuid-ossp`, `pg_trgm`, `pgcrypto`, `hstore`, `ltree`, …, matched by `CREATE EXTENSION`) gets it. A migration that needs any other extension (PostGIS, `dblink`) is read on the server the database's `schemaUrl` names instead: in a new database (`active_record_schema_<random>`, which needs `CREATEDB`), with every migration in one transaction that's rolled back (so a `CREATE ROLE` leaves nothing; a statement that can't run in a transaction fails, as under the runner), dropped afterwards (and on SIGINT, SIGTERM or SIGHUP while it's there, before the signal stops the command; a `SIGKILL` can leave one), with a note naming the extension and the host. A `schemaUrl` Node can't read as a URL (a socket's `postgres://app@/shop`) is refused before any database is made. Without a `schemaUrl`, that's an error saying to set one; `url` is never used for it. A broken migration is reported by file name, with Postgres's message, and migrations `migrate` would refuse (one without a version, or two sharing one) are refused before any is read. Keys, collisions and the rest are as on D1.

  static override schema = schema;

- The generated `schema.ts` is a document, like Rails' `schema.rb`: each table's attributes, then `schema`, holding its adapter (`adapter: d1({ binding: "DB" })`, #277: the factory named for the plugin, imported from the adapter's entry, #284, #301), every table, and `models` (each generated Model's class name, with its table). After it, a `declare module` block per Model file adds each class's table attributes, after its own `static attributes`, typed with the core's `TableAttributes`. Those are type-only, so at runtime the file imports only `d1` from `@forestfuture/active-record/d1`. A schema written before 0.7 imports `@forestfuture/d1-record`; its fingerprint covers the import, so `--check` reports it as out of date. When it's missing, `active-record schema` also writes the app's base class, `src/models/application-record.ts` (`abstract class ApplicationRecord extends Model`, holding `schema`), as Rails apps have `ApplicationRecord`; it never writes over it, so it's the app's to edit (`--check` writes nothing). With several databases, each binding gets its own schema file and base class, named as Rails names them (`LOGS` → `LogsRecord` in `src/models/logs-record.ts`, `MY_DB` → `MyDbRecord`); two bindings whose names would give the same base class (`DB` and `db`) are an error. `--models <dir>` puts it in another folder (`src/app/models`); the generators take the same flag, so Models and their base class stay together.
- **Finding the Models (#232).** `active-record schema` loads the `.ts` files in `--models` (`src/models`), or the one file it names, with jiti, as the console does, through the project's own copy of the library (ADR-0014). While they load, the schema as the migrations make it now stands in for the schema file (written there for the moment when there's none), with no `models` list, so nothing is checked against the old file. A generated Model is an exported class directly below a base class (one holding a schema, or marked `static abstract = true`) whose schema is the one being generated. A subclass of a Model, an abstract class, and a hand-declared Model aren't listed. A Model whose table the migrations don't make, a file that throws when it loads (named by its file), or a Model exported as its file's `default` (its declarations need a named export) is an error, and the last good file is kept. The generators load the Models too, adding the one they write. `--check` fails when a Model was added, renamed or removed, since the `models` list is part of the fingerprint. A list too long for a line is written one entry a line, as a formatter would.
- **A generated Model's attributes** are its table's, in the schema its nearest base class holds, after its overrides. They're settled when the Model is first used, once its class and statics are all defined: its table is bound and its accessors are defined then. Until then, each read of its `table`, `primaryKey` or attributes finds them again, so the statics of a class body may come in any order. A `validates` in a `static {}` block checks its attribute names when the Model is first used (an `UnknownAttribute`), not when it's declared. Its `primaryKey` is the table's; it can still be set, and must name an attribute. A subclass shares them; one that names another table throws `InvalidModel`.
- **Generation is required.** A Model whose class name isn't in its schema's `models`, or whose table there isn't its table now, throws `InvalidModel` naming `active-record schema` when it's first used. That's what stops a dev server, which doesn't type-check. Its query statics (`find`, `where`, …) are a compile error too, as an abstract class's are: they take only a class whose records have attributes. A schema with no `models` list (`DatabaseSchema`'s `models` is optional for this alone) checks nothing, which is how `active-record schema` loads the Models.
- **Overrides** go in the class: `static override attributes = {...} as const`. Without `as const` it's a compile error on the class (TS2417), since a widened `string` isn't an attribute type. An override is a type name (`"integer"`), or `{ type?, null?, default?, generateId?, storage? }` merged into the generated spec; a key left `undefined` changes nothing, the column can't change, and an attribute can't be added. A key that isn't one of the table's attributes, or anything else that isn't an override, is an `InvalidModel` naming the Model and attribute when its attributes are first read, so plain JavaScript and casts get the same rules, and `active-record schema` reports it. It isn't a compile error: a check that knows the table, from inside the class, would refer to itself. The record's TypeScript types follow the merged spec, read from the class's own `static attributes`, so an edit needs no regeneration; like a hand-declared Model's, a `default` isn't type-checked against the attribute's type yet (#74). An override that changes the `type` without giving a `default` drops the generated one, which was for the old type: the column's own default applies on insert (#81). A `default` that returns a value the type can't cast throws `TypeError` when a record is built. A `default` replaces a generated `generateId`, and `generateId` a generated `default`; changing the `type` drops `generateId` too; `generateId: false` turns it off, and `generateId: true` turns it on for a `string` attribute. An override that leaves `generateId` with a `default`, or on another type, is a compile error, and an `InvalidModel` when the Model's attributes are first read (#99).
- `false` ignores a column, as Rails' `ignored_columns`: it isn't an attribute, so it's never typed, assigned or written, and the Model's queries name its columns instead of `*` (`SELECT` and `RETURNING`), so it's never read. The primary key can't be ignored. Inserts leave an ignored column to its database default, so a `NOT NULL` column without one makes them fail.
- **`define`** declares a Model's attributes by hand, for views and tables outside the migrations (see Declaring a Model). It's a static, so it builds on the class it's called on: `ApplicationRecord.define({...})` shares the app's base class and its binding, and isn't checked against the schema's `models`.
- **Shared behavior**, as on Rails' `ApplicationRecord`: the app's base class is a real class extending `Model` (the library's base class), so `record instanceof ApplicationRecord` holds. The generated one holds the schema, with commented-out examples of a shared method, scope, and callback, and of `onQuery`, `filterAttributes`, `hiddenAttributes` and `generateId`. Instance methods and getters, static methods, callbacks declared in its `static {}` (they run for every Model, before the Model's own, in declaration order), and scopes (`static newest = this.scope(…)`) are inherited by every Model built on it, generated or hand-declared. A Model's own scopes add to the base's, as scopes inherit down any chain of classes. Once a Model is used, the classes it inherits declarations from (the base class too) are sealed as it is. Inside the base class, `this` is typed as it: it has every record method, but no attributes, since those differ by table (read them with `this.attributes()`), so shared scopes use `sql` fragments and `this.validates(…)`, which names an attribute, isn't available there; shared validation logic goes in a callback. It's abstract, as Rails' `abstract_class`: it has no table, so `db.model(ApplicationRecord)` throws `InvalidModel`. A class between it and some Models marked `static abstract = true` is abstract too: it shares its behavior, and each class directly below it has its own table. The statics that declare behavior (callbacks, `validates`, `errorMessages`, `humanAttributeNames`, `scope`) take an abstract class.

### Generators

_D1._

_Guide:_ [generators](<../site/docs/(how-to)/generators.mdx>), [change-a-table](<../site/docs/(how-to)/change-a-table.mdx>), [command-line](<../site/docs/(basics)/command-line.mdx>). _Code:_ `active-record/cli/generate/`, `active-record/cli/adapters/d1/migration.ts`, `active-record/cli/adapters/postgresql/migration.ts`.

`npx active-record g model <Name> [columns]` writes a `CREATE TABLE` migration and a Model; `npx active-record g migration <Name> [columns]` writes a migration whose name says what it does. Both then regenerate the schema and print the next step (`npx active-record migrate`, with `--database` when there are several); neither applies migrations.

- **Columns** are `name:type`: `string` (the default, so `title` and `slug:index` are strings), `integer`, `real`, `boolean`, `datetime`, `json` or `references`; then `!` for `NOT NULL`, `=value` for a literal default (`string`, `integer`, `real` and `boolean` only, and it may hold a `:`; Rails' generators have no such syntax), and `:unique` or `:index` for an index named as Rails names it (`index_products_on_sku`). Names are written in snake_case whichever way they're given. (D1) Types write `TEXT`, `INTEGER`, `REAL`, `BOOLEAN`, `DATETIME` and `TEXT CHECK (json_valid(…))`. (Postgres) Types write `TEXT`, `BIGINT` (an integer attribute holds any safe integer, which `INTEGER` can't), `DOUBLE PRECISION`, `BOOLEAN`, `TIMESTAMPTZ` and `JSONB`. `user:references` writes `user_id`, typed like the `users` key as its adapter declares it (`TEXT` on D1, `UUID` on Postgres, if `users` isn't in the migrations yet, with a note), `NOT NULL` with `REFERENCES users (id)`, and an index. Names the database reserves are quoted.
- **Names** are letters, digits and `_`, starting with a letter; anything else is refused, so a file can only land in the migrations or Models folder. A Model's name is made singular, as Rails makes it (`g model line_items` writes `LineItem`, with a note), and a migration's table plural (`CreateWidget` creates `widgets`).
- **`g model LineItem`** creates `line_items` with a key generated in code (D1: `id TEXT PRIMARY KEY NOT NULL`; Postgres: `id UUID PRIMARY KEY`, since `generateId` makes UUIDs) or, with `--id integer`, one the database generates (D1: `INTEGER PRIMARY KEY`; Postgres: `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`), the columns, and `created_at`/`updated_at NOT NULL` (`DATETIME` on D1, `TIMESTAMPTZ` on Postgres; `--no-timestamps` leaves them out). It writes `src/models/line-item.ts` with `export class LineItem extends ApplicationRecord {}` (the database's base class; its table, `line_items`, comes from its class name), a `belongsTo` field for each reference, and extensionless imports of the base class and of each target's file. `--models <dir>` writes it (and expects the base class) in another folder, as `active-record schema --models` does; `--out` names the schema file to regenerate, as for `active-record schema`. `--models src/models.ts` appends the class to one file instead, with the base class beside that file, adding the `belongsTo` and base-class imports if they're missing; a file that imports a base class of that name from somewhere else is refused.
- **`g migration`** reads its name as Rails does (`AddSkuToProducts` or `add_sku_to_products`): `Create<Table>` creates the table as `g model` does, `Add…To<Table>` adds the columns (a reference added this way can be `NULL`, as Rails' `add_reference`), `Remove…From<Table>` drops them (D1: after `DROP INDEX IF EXISTS` for the index a generator would have named; Postgres drops a column's indexes with it), and any other name is an empty migration. (D1) Adding a `NOT NULL` column without a default is refused, since SQLite can't. (Postgres) It's written, and Postgres refuses it when it runs on a table with rows.
- **Files** are named for the UTC second they're written in, on every adapter, as Rails names them (`20261108090503_add_sku_to_products.sql`), or one past the highest leading number in the migrations folder when that's later, so two written in one second keep their order (#285). Files numbered `0001_…` sort before them, and Wrangler orders D1's migrations by that number too. The command names the file, and the plugin writes the SQL. (D1) A file the config's `migrations_pattern` wouldn't match is refused, as `wrangler d1 migrations create` refuses it.
- **Nothing is written** unless the new migration applies after the existing ones (in memory, as `active-record schema` applies them) and the Model file is new (or, for `--models` with one file, doesn't have the class yet). Otherwise the command prints why, then "Wrote nothing". With several databases, `--database <binding>` chooses one, and the Model imports that database's schema file. `--config <file>` names the config file, as for `active-record schema`.

## Console

_Portable: the session, its commands and `-e` are the core's; each adapter opens its own database._

_Guide:_ [console](<../site/docs/(how-to)/console.mdx>), [command-line](<../site/docs/(basics)/command-line.mdx>). _Code:_ `active-record/cli/console/`, `active-record/cli/adapters/d1/binding.ts`, `active-record/cli/adapters/d1/installed-wrangler.ts`, `active-record/cli/adapters/d1/remote.ts`, `active-record/cli/adapters/postgresql/open.ts`, `active-record/cli/adapters/postgresql/targets.ts`. See ADR-0014.

- `active-record console` (also `c`; options `--database`, `--models`, `--config`, `--no-history`, `--history`, `--verbose`, `--remote`, `--yes`, `-e`/`--eval`) opens the project's database in a REPL (#104). (Postgres) It opens a `pg` Pool on the database's `url` (with `--remote`, its `remoteUrl`), from the `pg` the project's PostgreSQL adapter imports, passes it to the project's `connect`, and ends it when the console closes; it prints `Local database DB (shop_development on localhost)` after any notes, and `--remote` asks for the database's name, from the connection string. The rest of this section is D1's. (D1) **Local unless `--remote`**: `getPlatformProxy` is called with `remoteBindings: false`, so a binding marked `remote: true` still opens locally.
- **The database** is the only database `active-record.jsonc` names, or the one `--database` names; with several and no `--database`, or a name the config doesn't bind, it prints why and exits 1, as `g` does. Only that binding is started: `getPlatformProxy` is given a temporary Wrangler config holding the chosen `d1_databases` entry as the project's config has it (removed when the console ends), because it starts every binding a config declares (Durable Objects, services, secrets from `.dev.vars`), with their warnings and failures. State is read and written in `<config dir>/.wrangler/state/v3`, where `wrangler dev` keeps it (not relative to the working directory, as `getPlatformProxy`'s own default is).
- **The project's own code.** `wrangler` and `@forestfuture/active-record` (with its adapter's entry) are resolved from the project, never from the CLI's copy (`wrangler`, for `migrate` too, first from its Wrangler config's folder, where a monorepo's Worker has it, #306), so the Models and the console share one library instance (ADR-0014). One `jiti`, based in the project, loads the Models (TypeScript, extensionless imports, `tsconfig.json` `paths`, and the library itself). Without either package installed, the console says so.
- **The Models** are the exported classes extending `Model` (but not the classes Models are built on, such as `ApplicationRecord`) of every `.ts` file in `--models` (`src/models`), or of the one file `--models` names. Each is in scope by its class name, with `db` (the connected `Database`). No Models, a file that throws on load (named in the message), or no folder: it prints why and exits 1.
- **Each line** is evaluated inside `withDatabase(db, …)`, so Models' statics and records need no database argument. Top-level `await` works; `const` and `let` last for the session. A result prints as `#=> ` and its `util.inspect` (colored on a terminal, so a record prints as under Printing); an uncaught error prints as Node prints it, without `#=>`, and the session carries on.
- **Lines pasted or piped** run in order, each after the one before, and the session finishes them before it ends. The REPL closes as soon as its input ends, so piped input is held back until they are done.
- **History** is kept on a terminal only, in the plugin's `stateFolder` (`<config dir>/.wrangler` on D1, `<config dir>/node_modules/.cache/active-record` on Postgres), as `active-record-history`; `--no-history` keeps nothing (a line can hold a token or an email). A remote session keeps none unless `--history` is given, and then in `active-record-history-remote` beside it, so an up arrow never offers a line typed against the real database to a local session; `--history` with `--no-history` is a usage error.
- **The prompt** is `local> ` or `remote> `, the latter red on a terminal.
- **`--remote`** opens the chosen binding on the project's real D1 through Wrangler's remote proxy: the temporary config's entry is marked `remote: true` whatever the project's config says, `remoteBindings` is `true`, and nothing is persisted locally. The temporary config carries the project's `account_id`. The database is the one Wrangler uses, `preview_database_id` before `database_id`; the session says "Remote preview database" when it is the preview one. Before Wrangler is started (so before any sign-in; the project's own Models have been loaded, which needs no database) it names the database and its id and asks for its `database_name` (the binding's name when there is none) to be typed: anything else, a blank line, or the end of the input cancels (`Not opened.`, exit 1; a database with an empty `database_name` is named by its binding, so an empty answer is never the name). The one line is read and everything typed or pasted behind it is dropped, from the answer until the database is open (a terminal delivers a paste a line at a time, so those lines would otherwise reach the session and run on the real database). `--yes` skips the question (and is the only way to open it off a terminal, which otherwise exits 1 saying so; a terminal is stdin and stdout both being one, so a pipe on either end can't answer); `--yes` without `--remote` is a usage error. A binding with no `database_id` exits 1 before asking. When Cloudflare refuses, Wrangler's message is printed with how to sign in (`wrangler login`, or `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`). It starts by printing `Remote database DB (name, id …)`.
- **Console commands** are `.name` REPL commands (listed by `.help`), run in line order like any line, that print one message and show the next prompt. Two exist (#104):
  - **`.reload`**, and the bare line `reload!`, read the project's Models again: its own modules (everything the loader read under the project's folder, not `node_modules`) are forgotten and the Model files read afresh, so edits, added and removed files show. The library and `db` are not reloaded, so the Models stay Models of the same library. The session's names are updated (Models removed from the folder are no longer named; other variables are untouched) and it prints `Reloaded: A, B`. A file that fails prints `Couldn't load <file>: <message>`, or no Models says why, and the loaded Models stay as they were. Records and values already held keep their old class.
  - **`.verbose`** (and the bare line `verbose!`) toggles, `.verbose on` and `.verbose off` set: each statement prints before the line's result as `  Model  1.2ms  SQL  [ params ]` (or `failed` and the message), dim on a terminal, to the console's output stream. `--verbose` starts it on. It is the database's own `onQuery` (so params are the ones listeners get, filtered ones `[FILTERED]`), and the app's base-class `onQuery` still fires after it. Replies `SQL logging on` or `SQL logging off`.
- **`-e <code>`** (`--eval`) runs the code once instead of opening a session, and exits (#105). It is evaluated as a line is, so top-level `await`, `const`, the Models and `db` work, and each statement runs inside `withDatabase`. **stdout holds the code's `console.log` output, then the result**: a string as it is, anything else as `util.inspect` shows it (colored only when stdout is a terminal), no `#=> `, nothing for `undefined`; with several statements, the last value. The code's `console` is its own: `console.log` and `console.info` go to stdout, `console.error` and `console.warn` to stderr. **stderr holds everything else**: the database and Models banner, `--verbose` statement lines, refusals to start, and a failure's stack (`util.inspect` of what was thrown or rejected). The remote confirmation's question is asked on stdout, which is a terminal whenever it is asked. Success exits 0. A throw, a rejected `await`, an unfinished statement, a refusal, or a database that won't close exits 1, prints no result, and no later statement runs; the output is written after the database is closed, so a result is never printed for a run that fails to close. A console command line (`reload!`, `verbose!`) or REPL command (`.help`) runs and prints nothing. A promise the code doesn't await may not finish before the console exits, and a rejection that arrives after the code has finished is not reported; there is no time limit. It keeps no history and ignores what is piped to it. `-e` given twice, or with only whitespace, is a usage error. With `--remote` the same consent applies (a terminal to answer on, else `--yes`): `$(…)` makes stdout a pipe, so it needs `--yes`. Piped lines without `-e` are unchanged: the banner, prompts and results on stdout, and exit 0 even when a line fails. Code: `active-record/cli/console/script.ts`.
- **Leaving:** a line that is just `quit` or `exit` (also `.exit`, and Ctrl-D on a terminal) closes the session without evaluating anything, so nothing prints, and lines queued after it are not run. They are matched as whole lines, so `quit()` or `await quit` are not.
- **Ctrl-C** on a terminal stops a line that is still running (`breakEvalOnSigint`), such as an `await` that never ends; the session carries on.
- **When it can't start** it prints why and exits 1: a binding Wrangler can't open (with Wrangler's reason), or `wrangler` or the library that is found but throws on load (named as that, not as "not installed").
- **Needs** Node 22.13 or later on D1, as every command there does (23.4 on Node 23): its plugin needs `node:sqlite`. The core alone needs 22.5. It starts with any notes about the project's databases (`Note: wrangler.jsonc has the D1 database LOGS, …`), before `--remote` asks for a name, then prints the database (`Local database DB (.wrangler/state)`) and the Models (`Models: Post, User`).
- Not yet: `--sandbox` (#107, which records why it is a discardable copy and not a transaction).

## Scopes

_Portable._

_Guide:_ [querying](<../site/docs/(basics)/querying.mdx>), [models](<../site/docs/(basics)/models.mdx>). _Code:_ `active-record/src/scoped-relation.ts`.

- Declared one static each, as Rails' `scope :active, -> { … }`: `static active = this.scope((q, ...args) => q…)`. A scope receives the current Relation and its arguments and returns a changed Relation of the **same Model**; anything else throws `TypeError` naming the scope. The Relation it returns may start again from the Model's statics: it must be on the same database when the query runs, or it throws `IncompatibleRelation` naming the scope (#93), so a query never silently moves to another database.
- Callable as a static (`User.active()`, on the current database, #77), on `db.model(X)`, and on any Relation of that Model, and chainable with everything: `User.where(…).active().createdAfter(d).order(…)`. Scope calls are typed, including what a static scope returns when called on a subclass (`Admin.active()` is a Relation of `Admin`): a wrong argument type or an unknown scope name is a compile error.
- Calling a scope never queries. A scope's arguments, and anything it computes such as `new Date()`, are evaluated when it's called, not when the class is defined.
- Inside a scope body, `q` has every Relation method but not the Model's other scopes (their types would refer to themselves). To reuse logic, share a plain function between scopes.
- Scopes are statics, so they inherit as statics do, down any chain of classes, in types and at runtime: a subclass has its parent's scopes plus its own, and a same-named one (`static override admins = this.scope(…)`) replaces the parent's. The parent never gains the subclass's. Scopes on the app's base class (`ApplicationRecord`) are every Model's.
- A scope whose body names its own class needs its type written out, as any self-reference does: `static elsewhere: ScopeStatic<[]> = this.scope(…)` (`ScopeStatic<[...arguments]>`).
- A scope can't use any name a Relation already has: its methods (`where`, `count`, …), the standard object ones (`constructor`, `toString`, …), or `then`, which would make Relations awaitable; nor a Model static's (`validates`, `beforeSave`, `scope`, `all`, …). `db.model(X)` throws `InvalidModel` for such a name.
- Scopes are fixed once a Model is used: replacing one afterwards (`User.active = User.scope(…)`) makes `db.model(X)` throw `InvalidModel`.
- Default scopes and `unscoped` are deferred (#25).

## Inheritance, shared behavior and serialization

_Portable._

_Guide:_ [shared-behavior](<../site/docs/(how-to)/shared-behavior.mdx>), [models](<../site/docs/(basics)/models.mdx>). _Code:_ `active-record/src/ancestors.ts`, `active-record/src/declarations.ts`, `active-record/src/model.ts`, `active-record/src/model-statics.ts`, `active-record/src/verify-model.ts`.

- A subclass (`class Admin extends User`) inherits a copy of its parent's attributes, validations, callbacks, scopes and associations. Declaring more on the child never changes the parent. Single-table inheritance is out of scope.
- Share behavior between all Models on the app's base class, `ApplicationRecord` (see "Shared behavior" under The generated schema), as Rails does. Behavior only some Models share can go on a class between them and it, marked `static abstract = true`, or in a function called from their `static {}` (e.g. `audited(this)`). A `.with({...})` helper for adding attributes to a subclass of a shared base is deferred (#14).
- `attributes()` returns a plain object of loaded camelCase attributes with JavaScript values. `toJSON()` returns the same object, but with a `Date` as an ISO string, so `Response.json(user)` works. It leaves out the Model's **hidden attributes** (#101): `static hiddenAttributes: readonly string[]`, exact camelCase names, empty on `Model`, inherited, and replaced (not merged) by a Model's or the app's base class's own list (`[...ApplicationRecord.hiddenAttributes, "apiKey"]`). It's read when `toJSON()` runs, and doesn't touch `attributes()`, which stays whole. A name in a Model's own list that the Model has no attribute for is an `InvalidModel` when the Model is first used; names listed by a class without attributes (the app's base class, `Model`) are ignored where a Model lacks them, even when spread into the Model's own list. A name a partial record didn't load is harmless. The generated `application-record.ts` shows a commented-out example. Associations are never included automatically.
- **Printing (#104):** a record and a Relation print readably under `Symbol.for("nodejs.util.inspect.custom")`, so Node's `util.inspect`, `console.log`, the REPL and workerd's `node:util` use it, with the `depth`, `colors` and `stylize` they pass. A record prints `Name { attribute: value, … }` with its loaded attributes (a new record's unassigned ones as `null`; a partial record's only the columns it loaded), and its values printed by the runtime's own `inspect`. A filtered attribute's non-null value prints as `[FILTERED]`, unquoted and in the special color; `null` prints as `null`. On a persisted record, an attribute that differs from its Snapshot prints `after (was before)`, a filtered one prints `[FILTERED] (changed)` (also when it became `null`, so the old value never shows), and an attribute a partial record never loaded prints `after (changed)`, since its value before is unknown; a new record flags nothing. `hiddenAttributes` don't affect it, and associations aren't printed. Nested deeper than `depth` allows, a record prints as `[Name]`. A Relation prints `Relation<Name> { sql, params }`: the SELECT `toSql()` shows, never sent (printing is synchronous, so it can't load records), with a filtered attribute's param as `[FILTERED]`; past `depth`, `[Relation]`. A record's `errors` print `Errors [ { attribute, type, message, values? }, … ]` (`Errors []` when there are none; `[Errors]` past `depth`). Code: `active-record/src/record-inspect.ts`, `active-record/src/relation-inspect.ts`, `active-record/src/errors-collection.ts`.

## Change tracking

_Portable._

_Guide:_ [models](<../site/docs/(basics)/models.mdx>). _Code:_ `active-record/src/record-state.ts`, `active-record/src/attribute.ts`.

- Change detection compares each attribute's current serialized value with the value last loaded or saved, so in-place changes to `json` values and `Date`s are detected.
- After a successful save (an insert or an update), every loaded attribute holds what D1 stored, as a reload gives (#163): a `unixSeconds` `Date` has no milliseconds, and a `json` value's `NaN` or `Map` is `null` or `{}`, even when assigning it wasn't a change.
- `isChanged()`, `changed()` → `["email"]`, `changedAttributes()` → `{ email: old }`, `changes()` → `{ email: [old, new] }`.
- `savedChanges()` holds the changes from the last **successful** save (`{}` after a clean save). After `create`, that's everything the new row holds, including what D1 filled in (the generated key, column defaults), each changed from `null`. A failed save doesn't change it. `changes()` and `savedChanges()` return copies, so editing the record afterwards never alters them. Use it in `after*` callbacks, where the record is already clean.
- A new record's changes are its assigned attributes, each changed from `null`.
- Per attribute, as Rails' generated helpers (with the attribute's name, typed from the Model): `attributeWas("email")` is the value before the unsaved change (a new record's is its declared default, or `null`, as in Rails, so it agrees with `restoreAttributes`; `changes()` still reports a new record's changes from `null`, #41); `isAttributeChanged("email", { from?, to? })` and `willSaveChangeTo("email", { from?, to? })` check an unsaved change, for before-callbacks; `savedChangeTo("email")` (`[before, after]` or `undefined`), `hasSavedChangeTo("email", { from?, to? })` and `attributeBeforeLastSave("email")` read the last save, for after-callbacks. `from`/`to` compare as stored, so dates by time and `json` by content. Every one of them throws `MissingAttribute` for an attribute that wasn't loaded, as reading it does.
- `restoreAttributes(names?)` undoes unsaved changes, to the named attributes or all: a persisted record's go back to their stored values, and a new record's to their declared defaults or generated ids (or `null`), as in Rails.

## Associations

_Portable._

_Guide:_ [associations](<../site/docs/(basics)/associations.mdx>). _Code:_ `active-record/src/association-fields.ts`, `active-record/src/associations.ts`, `active-record/src/association-writers.ts`, `active-record/src/foreign-keys.ts`, `active-record/src/resolved-association.ts`, `active-record/src/owned-collection.ts`, `active-record/src/autosave.ts`, `active-record/src/dependents.ts`, `active-record/src/preload.ts`.

```ts
class User extends Model.define({ id: { type: "integer", null: false } }) {
  posts = hasMany(Post); // foreign key inferred: userId
  profile = hasOne(Profile);
}

class Post extends Model.define({ id: "integer", userId: "integer" }) {
  author = belongsTo(User, { foreignKey: "userId" }); // "author" would infer authorId
}
```

- `belongsTo`, `hasMany` and `hasOne` are declared as record fields (ADR-0008): `posts = hasMany(Post, {...})`, imported from the package. The field's name is the association's name, and TypeScript infers the accessor's type from it: no `declare` line. The target class is passed directly, in any declaration order, since a field's initializer only runs when a record is made.
- The library reads a Model's associations once, from a probe record made on first use, and removes the fields from the records it builds, so the accessors on the prototype answer. On a record constructed directly (`new User()`), calling an association, or its `set`/`build`/`create`/`createOrThrow`, throws `NoDatabase`. Plain (non-association) class fields stay on records as declared. Fields compiled as assignments (without `useDefineForClassFields`) work the same.
- `foreignKey` names an attribute, not a column, like everything outside `sql` fragments (so `foreignKey: "userId"` where Rails writes `foreign_key: :user_id`): the owner's for `belongsTo`, the target's for `hasMany`/`hasOne`. Left out, it's inferred by Rails' convention: a `belongsTo`'s name + `Id` (`author` → `authorId`), or for a `hasMany`/`hasOne` the owner's class name + `Id`, through the same `underscore` rule as columns (`User` → `userId`, `APIKey` → `apiKeyId`, `BlogPost` → `blogPostId`). An explicit `foreignKey` always wins. A `hasMany`/`hasOne`'s inferred key comes from the class whose table it is, the class the table name comes from, so a subclass's association infers its parent's key (Rails uses the declaring class).
- Inferring from the class name needs the class to keep its name when bundled. Wrangler keeps names by default, even with `--minify` (its `keep_names` setting); a bundler that renames classes turns `User` into something like `e`, and the inferred `eId` fails loudly at first use. The `InvalidModel` message names the attribute it looked for and where it came from ("inferred from the class name User") and suggests `foreignKey`. A Model's own `modelName` for this is #47.
- `primaryKey` is the attribute the foreign key points at. It defaults to the target's primary key for `belongsTo`, and the owner's for `hasMany`/`hasOne`. Keys aren't type-checked. They're checked when the Model is first used, as are an association named like an attribute or a record method/property, and a target that isn't a Model: all `InvalidModel`.
- `await post.author()` and `await user.profile()` resolve to a record or `null`. `user.posts()` returns a lazy Relation of the target, with its scopes and every Relation method. All three query through the owner's Database, or for an association to another database, the target's (below). Without a query: `belongsTo` resolves to `null` when its foreign key is `null`, and `hasOne`/`hasMany` resolve to `null`/an empty Relation when the owner has no key (it's unsaved, or its key attribute is `null`). A `belongsTo` on an unsaved record whose foreign key is set loads the target, as in Rails.
- Writing through a `belongsTo` or `hasOne`, as Rails' `post.author = user`, `build_author` and `build_profile` do: the accessor also has methods, so `await post.author()` is unchanged.
  - `post.author.set(user)` sets the post's foreign key to the user's key and makes the user the loaded `author` (no query to read it). `set(null)` clears both. A record of another Model throws `TypeError`. It's written when the post is saved.
  - `post.author.build(attrs)` makes a new author the post points at. `post.author.create(attrs)`/`createOrThrow` save the author at once, then point the post at it (the post itself isn't saved).
  - `user.profile.build(attrs)` makes a new profile pointing at the user, loaded as its `profile` and autosaved with it. An unsaved owner's built profile stays its loaded `profile` after the owner saves it. `create`/`createOrThrow` save it at once, and throw `RecordNotSaved` on an unsaved owner, as in Rails; a created profile that doesn't save is kept, so saving the owner tries it again. An existing profile is left as it is (Rails' replacement rules are #40), so a unique foreign key fails loudly rather than losing anything.
  - A new record set or built through a `belongsTo` is validated with its owner ("Author is invalid") and saved **before** it, then the owner's foreign key is filled in, as Rails' belongs_to autosave does. It's filled in even if the record was saved on its own in between. When its key is generated in code, the owner's foreign key holds it from `set`/`build` on, so the owner's `beforeSave` sees it. When D1 generates it, the owner's before-callbacks run before it exists (they see `null`): a save prepares everything, callbacks included, before writing anything. When its key is known in advance (generated in code), both writes are one atomic batch; when D1 generates it, the new record is written first, then the owner. In `db.batch`, that's only allowed when the key is known (`RecordNotSaved` otherwise).
- A loaded association is cached on the record, as in Rails: `await post.author()` and `await user.profile()` query once (a `null` result included), and `await user.posts().toArray()` loads the collection once, in target primary-key order. Preloading with `includes` fills the same cache. Each cached value remembers the key it was loaded for, so changing a foreign key (`post.userId = 2`) makes the next read query again, preloaded or not. `reload()` clears the cache and discards records built through the associations, as Rails' reload does; `save()` keeps the cache. `await record.reloadAssociation("author")` queries again, replaces what's cached (discarding that association's built records) and returns it (Rails' `reload_author`, and `user.posts.reload`). A `belongsTo` or `hasOne` read sent before `set`, `build`, `create` or `reload()`, and answered after it, resolves to what it loaded but isn't kept: what `set`, `build` or `create` made stays loaded, and after `reload()` nothing is.
- **A belongsTo requires its record (#339)**, as Rails 5+ does: validation adds `required` ("must exist") to the association's name when the record it points at isn't there. It runs after `beforeValidation` and before the declared validations, in association order, and only for a belongsTo whose foreign key is loaded, and `null` or changed (Rails 7.1's default), so saving a record whose key hasn't changed sends no read. The record is read through the accessor, so it uses and fills the association's cache: a record set or built through it passes without a query, and one found stays loaded. On another database (#228) it's looked for there. `belongsTo(X, { optional: true })` leaves the check out; `optional` on a `hasMany` or `hasOne` is a type error and an `InvalidModel`. There's no app-wide switch.
- **A record built through a `hasMany` or `hasOne` points back at its owner (#339)**, as Rails' automatic `inverse_of` does: the first of the target's `belongsTo` associations with the same foreign key, to the owner's Model and through the same key, has the owner loaded, for the foreign key the record holds then. So `await post.author()` on a post built through `user.posts()` is the user, with no query, and a required `belongsTo` passes before either is saved.
- Records built or created through `user.posts()` get the owner's key. On an unsaved owner, `create`/`createOrThrow` throw `RecordNotSaved`, as in Rails, and `build` gives a record whose key is filled in when the owner is saved (autosave, below).
- **Autosave**, as Rails' `has_many` does by default: a record built through a `hasMany` joins the association at once, and saving the owner saves the ones still new, with its key. An unsaved owner's `user.posts().toArray()` returns its built records without a query; a saved owner's loaded collection is its stored records followed by the built ones, however and whenever it's loaded. (As in Rails, `pluck` and `count` on a collection that isn't loaded query the database, so they leave built records out.)
  - They're validated with the owner: an invalid one makes the owner invalid, with "Posts is invalid" on the owner and its own errors on the record.
  - The order is the owner's validation (the records included), the owner's before-callbacks, the records' before-callbacks, the writes, then the owner's after-callbacks and the records'. An owner with no changes of its own still saves its built records.
  - Autosave reaches every level: a built record's own built records are saved too, validated one after another in the order they were built, as Rails does.
  - When the owner's key is known before its INSERT (a key generated in code, or an owner that's already saved), the owner and its records on its database are written in one atomic batch. When D1 generates the key, the owner is written first and its records follow in the next batch (and theirs in the one after, a level at a time): that isn't atomic between the batches, so a record that then fails (only a constraint error can, after validation) throws with the owner saved and the record still new. The after-callbacks of everything already written still run first. Generate keys in code where the whole graph must be atomic.
  - In `db.batch`, `b.save(owner)` autosaves only when the owner's key is known; otherwise it throws `RecordNotSaved`, since the batch couldn't be atomic.
  - Records created with `create` aren't autosaved (they're saved at once), and a built record saved on its own isn't saved again. In `db.batch`, each record is written once: listing a record twice, or listing a record its owner's autosave already saves, doesn't write it again. List the owner rather than its built records: a built record listed before its owner is saved on its own, without the owner's key. `autosave: true` (changed records, marking for destruction) is #37, and `validate: false` is #39.
- `includes("posts", "profile")` and nested `includes({ posts: "comments" })` or `includes({ posts: ["comments", "tags"] })` preload associations for every record loaded, by `toArray`, `first`, `last`, `take`, `find` and `findBy`. Names are typed from the association fields, and an unknown one throws `UnknownAssociation`. Each association is loaded with one `WHERE key IN (…)` query, whatever the number of parents, never one query per record, as in Rails. The whole tree on the records' database goes to D1 with their own query, in one batch (#217; a level on another database is preloaded from there, above): each association's query selects its owners' keys with a subquery of their query (`WHERE key IN (SELECT …)`), not with keys bound once they're loaded, so `includes({ posts: "comments", profile: "country" })` is five queries in one round trip, however deep the tree, where Rails sends each association's query on its own. A batch runs as one transaction, so every level reads the same data. Each subquery runs its owners' query's conditions again, and its order only with a `limit` or `offset`, so a query that scans its table reads it once more for each association below it (D1 bills rows read): index what it filters and sorts by. The batch is planned before anything is found, so every association in the tree is sent, even under owners that find nothing; one with a `none()` scope sends nothing, and nor does anything under it. With a `limit` or `offset`, a query with `includes` ends its order with the primary key (unless the order has it already), and the subqueries keep its order, limit and offset, so they select the records it loads. A key that isn't text, linked to a text key, is selected as text (`CAST(… AS TEXT)`), so the text column's index is searched. (Postgres) A text key linked to an integer key is selected as the number its digits are, as a condition casts it, and text that isn't digits matches nothing, since Postgres compares no text with a number. Records are attached by the key cast as a condition's (#94), so an integer key matches a text key's digits only. An association scope's own `includes` go in the same batch. An association the caller writes out again further down (`includes({ author: { posts: "author" } })`) goes in the batch like any other. A scope that includes an association it's already under, a tree of records, can't be planned to a depth: unless the caller wrote that level out, the batch stops there, and that association's records are preloaded by the loaded records' keys (one bound value), one round trip per further level, until a level finds nothing. A level binds the values of every query above it, so one that would bind more than D1's 100 values a statement is left until its owners are loaded, then preloaded by their keys (one bound value), in one more round trip. A level under it that an association scope's own values take past 100 again waits for the round trip after. The batch's statements are reported to `onQuery` one by one, as any batch's are; when it fails, D1 doesn't say which statement failed, so each, the records' query included, is reported with the error and the caller gets the translated error. A scope that can't be preloaded throws `IncompatibleRelation` before anything is sent. With a Session, the batch goes through it. Keys preloading needs are loaded even if `select` leaves them out, the query's or an association scope's: the key each association's records are matched to their owners by, and the keys its nested includes need. The records stay partial (#201). Adding the keys would undo a `distinct`, so `includes` with `select(...).distinct()` throws `IncompatibleRelation`. `includes` on `none()` sends nothing. Models reached only through `includes` are checked and prepared like any other.
- On a loaded `hasMany`, `toArray`, `first`, `last`, `take` and `pluck` answer from the loaded records without a query. `count` always queries, like Rails' `count`; `size()` uses the loaded records. Chaining further (`user.posts().published()`, …) queries as normal and doesn't change the cache. `create` through a loaded `hasMany`, narrowed or not (`user.posts().where(…).create(…)`), appends the new record when it saves, as Rails' association and association relation do. `insert`, `upsert`, `updateAll` and `deleteAll` built through it, narrowed or not, clear the cache, and clear it again once they're written, alone or in `db.batch`. They do the same when the `hasMany` is joined into another Relation: on either side of `or()` or `merge()` (both owners' loaded collections, if both sides are associations), or by a scope that starts a new query (#194). Only the association on the left of `or()` or `merge()` gets records built or created through the joined Relation; a record created through it clears any other's loaded collection. A read sent before such a write, or a `create`, and answered after it, resolves to what it loaded but isn't kept. `build` appends the new, unsaved record (see autosave). A record destroyed some other way stays in an owner's cached collection until it's reloaded, as in Rails. A loaded `hasMany`'s records are in its scope's order, then target primary-key order, and a `hasOne` (lazy, preloaded or as a dependent) picks the first record in that same order, so ties resolve alike everywhere. A `belongsTo` with a `null` key, or a `hasOne` whose owner has no key, reads as `null` without a query, and that `null` counts as loaded.
- `record.loaded("posts")` returns a loaded association synchronously (records for a `hasMany`, a record or `null` otherwise), typed from its field. A list is returned as a copy. It throws `AssociationNotLoaded` unless the association was preloaded or already read, for the key the record holds now. `record.isLoaded("posts")` is the predicate (Rails' `association(:posts).loaded?`).
- `or()` needs the same `includes`, and `merge()` combines both sides' includes.
- A subclass has its parent's associations, inherited as fields, plus its own. Redeclaring a field replaces the parent's association; removing one isn't possible, as in Rails.
- `user.posts().insert(attrs)`, `updateAll(...)` and `deleteAll()` write through the association, and so do a Batch's, given the association (`b.deleteAll(user.posts())`, see _Batches_). As in Rails' `has_many`, `deleteAll()` on the association itself deletes the records when its `dependent:` is `"destroy"` or `"deleteAll"`, and otherwise sets their foreign key to `NULL` (a NOT NULL foreign key raises `NotNullViolation`). Once narrowed (`user.posts().where(...)`, `.limit(…)`, a scope), `deleteAll()` deletes, as a Rails association relation does. For an owner without a key, `insert` rejects with `RecordNotSaved` (and so does a batch preparing it), and `updateAll`/`deleteAll` match nothing.
- An association can declare a scope, as Rails' `has_many :posts, -> { order(created_at: :desc) }`: `hasMany(Post, { scope: (q) => q.order({ createdAt: "desc" }) })`, on `hasMany`, `hasOne` and `belongsTo`. `q` is the target's Relation with its named scopes, typed from the target. One case is circular for TypeScript: a Model's association to itself whose scope calls the Model's own scopes, which needs its field's type written out (`children: HasMany<typeof Category> = hasMany(Category, { scope: (q) => q.top() })`). It's also checked when the scope first runs (`UnknownAttribute`, and `TypeError` if the scope doesn't return a Relation of the target).
- The scope applies to lazy reads and to preloads alike. A `hasMany`'s records come in the scope's order, then by primary key, and a `hasOne` takes the first by the scope's order. Records built or created through the association take the scope's equality values, so `scope: (q) => q.where({ published: true })` creates published posts. `deleteAll()` and `updateAll()` through it only touch the scope's records. A scope using `limit`, `offset` or `distinct` works for lazy reads, but preloading it throws `IncompatibleRelation`, at any level of the tree, before any preload query is sent, whether or not the levels above it find records (#92), because a grouped preload would apply them to every owner's records together (Rails gives silently wrong results here).
- **An association to another database (#228):** when the owner's and the target's schemas each name a database (`d1({ binding: "LOGS" })`), and not the same one, possibly on another adapter, the target's records are on the target's database. Reads (the accessor, a `hasMany`'s Relation with its finders, counts, scopes and bulk writes, and `reloadAssociation`) go to the target's current database, found as its statics find it: the request's for its binding, or else the binding's own. That holds whether the owner came from a Model's statics, `withDatabase`, or an explicit `db.model(X)`, which is only ever the owner's own database. Records built, created or loaded through the association are on the target's database, and save and destroy there. If either schema names no database, or both name the same one, the association is on the owner's database, as before. Nothing joins across databases. As in Rails, every write still works, as separate writes on each database, so not atomically together:
  - Autosave: a new record the owner points at through a `belongsTo` on another database is written there before the owner, and records built through a `hasMany` or `hasOne` on another database are written there after it, with its key, each association's records in one batch. Validation and every before-callback still run before any write, and every after-callback after the last. A write the other database refuses throws with what's written before it kept (the owner saved, the record still new), after their after-callbacks run.
  - `batch` and `db.batch`, which write one database atomically, refuse a save whose autosave reaches another database, and a destroy whose writing `dependent:` associations reach one (its own, or those of the records its `"destroy"` strategies destroy, at every level), with `IncompatibleRelation`, before any validation or callback runs. Records on another database that a callback brings in are refused the same way, once the callbacks have run, before anything is written.
  - Preloading: a level on another database can't go in its owners' batch, or select their keys with a subquery. It's preloaded once its owners are loaded, by their keys (one bound value), as its own round trip on the target's database, written in its SQL, with the levels under it there in the same round trip. So each other database a tree reaches takes one more round trip, at each depth where it's reached; levels on different databases at one depth are sent at once.
- `dependent:` sets what destroying the owner does to an association's records, as in Rails: `"destroy"`, `"deleteAll"`, `"nullify"`, `"restrictWithException"` or `"restrictWithError"` on a `hasMany`, and the same with `"delete"` in place of `"deleteAll"` on a `hasOne` (its first record, by the scope's order or the primary key). `belongsTo` has none; a strategy the kind doesn't have is a type error and an `InvalidModel`. `"destroyAsync"` waits for a job library (#35).
- Strategies run when a persisted owner is destroyed, after its `beforeDestroy` callbacks and before its DELETE, so an abort leaves the records alone. (Rails runs them where the association is declared among the callbacks, so an abort declared later comes too late.) Restrictions are checked first, so a restricted owner touches nothing:
  - `"restrictWithException"` throws `DeleteRestriction` ("Cannot delete record because of dependent posts") while there are records.
  - `"restrictWithError"` adds a `base` error instead ("Cannot delete record because dependent posts exist", or "…because a dependent profile exists"), so `destroy()` returns `false` and `destroyOrThrow()` throws `RecordNotDestroyed`.
  - `"deleteAll"`, `"delete"` and `"nullify"` are statements sent in one `batch()` with the owner's DELETE, so on one database all of it happens or none of it does. Callbacks on the records don't run, as in Rails.
  - `"destroy"` runs each record's destroy lifecycle, with its callbacks and its own dependents, and its DELETE goes in the same batch as the owner's, so on one database all of it happens or none of it does. Every record's `beforeDestroy` runs before anything is written, and the `afterDestroy` callbacks run afterwards, the records' before the owner's. If a record's destroy aborts, nothing is written and the owner's destroy throws `RecordNotDestroyed`. If a record's own `"restrictWithException"` refuses, its `DeleteRestriction` propagates as it is.
  - On an association to another database, a restriction looks for the records there, and every other strategy is written there as its own write, before the owner's DELETE, as in Rails: not atomically with it.
- Without a strategy, destroying an owner whose records point at it leaves the database to decide: D1 enforces foreign keys, so it throws `InvalidForeignKey`. Polymorphic associations (#60) and counter caches (#61) aren't built; inverse associations beyond records built through an owner are #62.

## Persistence results

_Portable._

_Guide:_ [persistence](<../site/docs/(basics)/persistence.mdx>). _Code:_ `active-record/src/lifecycle.ts`, `active-record/src/model.ts`, `active-record/src/model-statics.ts`.

| Method                                   | Resolves to                           | Domain errors                                         |
| ---------------------------------------- | ------------------------------------- | ----------------------------------------------------- |
| `save()` / `update(attrs)`               | `true` / `false`                      | constraint errors, `RecordDestroyed`                  |
| `saveOrThrow()` / `updateOrThrow(attrs)` | `true`                                | same as above, plus `RecordInvalid`, `RecordNotSaved` |
| `create(attrs)`                          | record, persisted or not              | constraint errors                                     |
| `createOrThrow(attrs)`                   | persisted record                      | same as above, plus `RecordInvalid`, `RecordNotSaved` |
| `destroy()`                              | destroyed record, or `false` on abort | constraint errors, `RecordDestroyed`                  |
| `destroyOrThrow()`                       | destroyed record                      | same as above, plus `RecordNotDestroyed`              |
| `find(id)`                               | record                                | `RecordNotFound`                                      |
| `findBy(conds)`                          | record or `null`                      | none                                                  |
| `findByOrThrow(conds)`                   | record                                | `RecordNotFound`                                      |

Any error thrown by a callback other than an `abort(...)` propagates unchanged. That includes an error from an `after*` callback after the persistence lifecycle has already succeeded. Operational D1 errors always propagate. `false` means only "validation failed" or "a callback aborted" (ADR-0005).

## Constraint errors

_Portable._

_Guide:_ [errors](<../site/docs/(basics)/errors.mdx>). _Code:_ `active-record/src/constraints.ts`, `active-record/src/adapters/d1/errors.ts`.

- `RecordNotUnique`, `InvalidForeignKey`, `NotNullViolation` and `CheckViolation`, all subclasses of `ConstraintViolation`, are recognized from D1 error messages on insert, update and delete, and (Postgres) from Postgres's SQLSTATE codes, whose errors name their table and columns even in a batch (an allowed difference). They carry the original error as `cause` (on Postgres, without its `detail`, `where` and `internalQuery`, where Postgres writes a row's values, so neither `cause` nor `onQuery`'s `error` puts them in a log; #269), and `.table`, `.columns` and `.attributes` where the message names them (SQLite's foreign-key and check messages don't name a column). The same errors come from statements and batches. `.table` is the table D1's message names, and `.attributes` are mapped when that table is one being written to (a trigger's write to another table leaves them empty). When the message names no table (foreign-key and check failures), it's the only table written to. A batch that writes to several then has `.table` `null`, and the message starts with `batch:`.
- (Postgres) A value Postgres refuses (SQLSTATE class 22: a string that isn't a uuid or one of an enum's values, an integer past the column's range) is thrown as Postgres's own error, its message naming the type but not the value: `invalid input syntax for type uuid: "[FILTERED]"`, in its stack too, so neither the error nor `onQuery`'s `error` puts it in a log (#269). This reads Postgres's messages in English; with another `lc_messages` the value may be quoted differently and kept. An error the app raises itself, from its own function or trigger (`RAISE EXCEPTION`, SQLSTATE class P0), keeps the message and hint the app wrote, values included.
- Both the throwing and non-throwing methods throw them. After a constraint error the caller's own changes are kept and `errors` is not changed, because nothing was persisted. Timestamps are only applied once D1 accepts a write, so a failed save doesn't leave `createdAt`/`updatedAt` behind.
- Uniqueness validation is a friendly early check, not race-safe. The database constraint has the final say.

## Validation

_Portable._

_Guide:_ [validations](<../site/docs/(basics)/validations.mdx>). _Code:_ `active-record/src/validations.ts`, `active-record/src/lifecycle.ts`.

`await record.isValid()` is the only public entry point. It clears `errors`, runs `beforeValidation`, runs the synchronous and asynchronous validators (uniqueness reads D1), runs `afterValidation`, and returns `true`/`false`. It catches `abort()` and returns `false`; every other error propagates. `save()` and `saveOrThrow()` call it internally. `isChanged()` is a pure synchronous state check, while `isValid()` does work and may query D1.

## Errors collection

_Portable._

_Guide:_ [validations](<../site/docs/(basics)/validations.mdx>). _Code:_ `active-record/src/errors-collection.ts`, `active-record/src/error-messages.ts`.

```ts
record.errors.add("email", "is invalid", { type: "invalid" }); // type defaults to "invalid"
record.errors.add("base", "Account is locked");
record.errors.add("endsAt", { type: "afterStart" }); // its message is looked up
record.errors.add("handle", { type: "tooShort", count: 3 }); // %{count} is 3
record.errors.get("email"); // ["is invalid"] (always an array)
record.errors.fullMessages(); // ["Email is invalid"]; createdAt displays as "Created at"
record.errors.toArray(); // [{ attribute, type, message, values? }]
record.errors.isEmpty();
record.errors.size;
```

Validators add entries with a `type` (`"blank"`, `"taken"`, `"tooShort"`, …) and the values their message shows (`count`). An entry keeps its type and values, and its message is looked up each time it's read (`get`, `fullMessages`, `toArray`, printing, `RecordInvalid`'s message), unless it was given as text (`validates`' `message`, `errors.add` with a string), which is used as it is. `toArray()` gives `values` only for an entry that has some, a copy, and never the attribute's value.

**Error messages (#88).** `this.errorMessages(messages: ErrorMessages)`, called in a class's `static {}` (the app's base class or a Model): messages by type (`blank: "is required"`), and under `attributes` by attribute, then type. It's a declaration, kept with validations and callbacks: a subclass starts from its parent's, a class's calls add up (a later call's message wins, type by type, for each attribute too), and calling it once the class is sealed (first use) is `InvalidModel`. On a Model, the keys of `attributes` are typed to its attributes, associations and `"base"`; on a class without attributes, any string. A message is a string, or `{ one?, other }`, chosen by `Intl.PluralRules("en")` from the entry's `count` (`other` without one). `restrictDependentDestroy` is `{ hasOne, hasMany }`. The lookup, first match wins, Rails' order for a Model and its ancestors: for the record's Model, then each class it extends (the app's base class included), its own calls' `attributes.<attribute>.<type>`, then their `<type>` (own keys only, read with `Object.hasOwn`); then the built-in English, Rails' en.yml. Unlike Rails' two shared scopes, where `activerecord.errors.messages.<type>` beats `errors.attributes.<attribute>.<type>`, the app's base class tries the attribute's message first, as every class does. Placeholders: `%{count}` and any value given to `errors.add`; `%{attribute}` (the human attribute name); `%{model}` (the class name in words: `BlogPost` → "Blog post", so a bundler that renames classes changes it; a Model's own name is #47); `%{value}` (the attribute's current value: empty for `base`, null, or an attribute not loaded, `[FILTERED]` for a filtered attribute, an ISO string for a Date, JSON for an object). An unknown placeholder is left as written. `errors.add` with a type no class or built-in message has throws `TypeError` naming where to add one, and adds nothing; without a type or a message, it throws `TypeError`.

**Attribute names.** `this.humanAttributeNames({ createdAt: "Signed up" })`, declared the same way and typed the same way, looked up nearest class first (a later call first), else the attribute in words (`createdAt` → "Created at"). `Model.humanAttributeName(attribute)` returns it; `fullMessages()` and `%{attribute}` use it. A name in `errorMessages`' `attributes` or `humanAttributeNames` declared by a class with attributes (the Model, or a Model it extends) that isn't its attribute, association or `"base"` is `InvalidModel` at first use; those of a class without attributes (the app's base class) apply where a Model has the attribute. Locales: #211.

## Validators

_Portable._

_Guide:_ [validations](<../site/docs/(basics)/validations.mdx>). _Code:_ `active-record/src/validations.ts`.

Declared in `static {}` with `this.validates(attribute, rules)`. The attribute name and the `if` callback's record are typed against the Model. Every declared validation runs, in declaration order, with no stopping at the first failure, so one attribute can collect several errors. Within one `validates` call the rules apply in a fixed order: presence, length, format, inclusion, numericality, uniqueness.

All validators accept `allowNull` (skip when the value is null), `message` (replaces every default message from that call) and `if: (record) => boolean`. Without `allowNull`, a null value fails `presence`, `format`, `inclusion` and `numericality`. `length` counts it as length 0 (so it fails a `minimum` or `is`, and passes a `maximum`), and `uniqueness` never treats it as taken.

Default messages (Rails' English, replaced through `errorMessages`): `blank` "can't be blank", `required` "must exist" (a required belongsTo), `tooShort` "is too short (minimum is N characters)", `tooLong` "is too long (maximum is N characters)", `wrongLength` "is the wrong length (should be N characters)", `invalid` "is invalid", `inclusion` "is not included in the list", `notANumber` "is not a number", `notAnInteger` "must be an integer", `greaterThan`/`greaterThanOrEqualTo`/`lessThan`/`lessThanOrEqualTo` "must be greater than (or equal to) N" / "must be less than (or equal to) N", `taken` "has already been taken".

- `presence`: not null, and not blank after trimming a string. For a boolean, use `inclusion: [true, false]`.
- `length`: `{ minimum, maximum, is }`.
- `format`: `{ with: /re/ }`, or `format: /re/` as shorthand.
- `inclusion`: `{ in: [...] }`, or an array as shorthand.
- `numericality`: `{ onlyInteger, greaterThan, greaterThanOrEqualTo, lessThan, lessThanOrEqualTo }`, or `true`. Only real numbers pass: a numeric string such as `"12"` is `notANumber`, so convert form input first.
- `uniqueness`: `{ scope: [...], caseSensitive }`. It leaves out the record itself when updating and runs `SELECT 1 … LIMIT 1` through the record's Database (so the same session). `null` is never taken, matching SQLite's UNIQUE, which allows any number of NULLs. `caseSensitive: false` compiles to `lower(col) = lower(?)`, and SQLite's `lower()` only lowercases ASCII letters.

## Callback lifecycle

_Portable._

_Guide:_ [callbacks](<../site/docs/(basics)/callbacks.mdx>). _Code:_ `active-record/src/lifecycle.ts`, `active-record/src/declarations.ts`.

Declared in `static {}`: `this.beforeValidation(fn)`, `afterValidation`, `beforeSave`, `beforeCreate`, `beforeUpdate`, `afterCreate`, `afterUpdate`, `afterSave`, `beforeDestroy`, `afterDestroy`. Each takes a function that receives the record, typed as the Model's record, and may be async; callbacks of one kind run in declaration order. A subclass runs its parent's callbacks and validations plus its own, and declaring on it never changes the parent. Declarations belong in the class's `static {}` block: once a Model has been used (`db.model(X)`), declaring on it throws `InvalidModel`, so request code can never add callbacks that leak into later requests.

```text
beforeValidation → validators → afterValidation
→ beforeSave → beforeCreate | beforeUpdate
→ D1 write (skipped when a persisted record is still clean)
→ record becomes persisted and clean
→ afterCreate | afterUpdate → afterSave
```

- `after*` callbacks run after a **successful persistence lifecycle**, which isn't necessarily a D1 write. Saving a clean persisted record runs every callback, issues no UPDATE and leaves `updatedAt` unchanged, as in Rails. If a `before*` callback changes an attribute, the record is dirty again and the UPDATE happens.
- An `after*` callback that changes the record makes it dirty again, and no second write happens automatically.
- Nothing rolls back after a successful write.

## Abort

_Portable._

_Guide:_ [callbacks](<../site/docs/(basics)/callbacks.mdx>), [persistence](<../site/docs/(basics)/persistence.mdx>). _Code:_ `active-record/src/lifecycle.ts`.

```ts
this.beforeSave((account) => {
  if (account.suspended) throw abort("Account is suspended");
});
```

- `abort(reason)` returns a `CallbackAbort` (an `ActiveRecordError`; the reason defaults to "Aborted by a callback"), and only that class is caught. Returning `false` never halts anything.
- It only takes effect in `beforeValidation`, `afterValidation`, `beforeSave`, `beforeCreate`, `beforeUpdate` and `beforeDestroy`.
- `save()` returns `false`, does no write, and keeps the dirty and new-record state. `saveOrThrow()` throws `RecordNotSaved` with the reason. `destroy()` returns `false`, and `destroyOrThrow()` throws `RecordNotDestroyed`.
- `record.abortReason` holds the reason. It's cleared at the start of each `isValid()`, `save()` and `destroy()`, and never copied into `errors`.
- An `abort()` in `afterSave`, `afterCreate`, `afterUpdate` or `afterDestroy` becomes `AbortAfterPersistence`, which records the callback name, the reason and the original `CallbackAbort` as `cause`. The persisted or destroyed state stays as it is.

## Destroyed records

_Portable._

_Guide:_ [persistence](<../site/docs/(basics)/persistence.mdx>). _Code:_ `active-record/src/record-state.ts`, `active-record/src/lifecycle.ts`.

- A record is marked destroyed only after the D1 `DELETE` succeeds, and before `afterDestroy` runs. Destroying a never-saved record sends nothing, since there's no row, and marks it destroyed. If `afterDestroy` throws, the row stays deleted and the record stays destroyed.
- `isDestroyed()` is `true` and `isPersisted()` is `false`. Attributes stay readable, but the record is read-only: setting a property or calling `assign` throws `RecordDestroyed`.
- `save`, `saveOrThrow`, `update`, `destroy` and `reload` throw `RecordDestroyed`.
- A keyless record from `select(...).distinct()` has no identity to write by, so the same methods throw `MissingAttribute`. A record constructed directly (`new User()`) has no Database, so they throw `NoDatabase`.

## Relations

_Portable._ A bullet or sentence marked (D1) is the D1 adapter's alone.

_Guide:_ [querying](<../site/docs/(basics)/querying.mdx>). _Code:_ `active-record/src/relation.ts`, `active-record/src/relation-checks.ts`, `active-record/src/load.ts`, `active-record/src/query.ts`, `active-record/src/compiler.ts`, `active-record/src/comparisons.ts`, `active-record/src/sql.ts`, `active-record/src/fragment-guard.ts`.

- Every modifier returns a new Relation. Building a Relation never queries D1.
- `static primaryKey` (default `"id"`) must name a declared attribute, or `db.model(X)` throws `InvalidModel`. `find(id)` takes one id, a `string | number`, and resolves to a record. `find(1, 2)` or `find([1, 2])` resolves to an array in the ids' order, or in the Relation's order if it has one, as in Rails. It's one query, repeated ids are found once, `find([])` resolves to `[]`, and a missing id throws `RecordNotFound` saying how many were found. Ids are cast to the key's type first, as in Rails, so `"01"` and `1` are the same id for an integer key. Unlike Rails, `find(1, 1)` still resolves to an array, so the return type follows the arguments. Any number of ids fits in the one query, as with `where`.
- An empty conditions object (`where({})`, `whereNot({})`, `findBy({})`) adds no condition. An `undefined` value throws `TypeError`: use `null` to match NULL, or leave the key out. `undefined` would otherwise bind NULL and silently match nothing.
- Condition values (`where`, `whereNot`, `findBy`, `exists`, lists and comparisons) are cast as assigned values are, except that a finite number matches a `string` attribute as its decimal string (`7` → `"7"`), as `find` does for a text key and as Rails does, so a foreign key of another type still finds its target. One that can't be cast matches nothing (`1 = 0`), as in Rails 6.1+, never NULL and never an error, so `where({ quantity: "abc" })` finds nothing and `find("abc")` on an integer key throws `RecordNotFound`. In a list, the values that can't be cast are left out. So `whereNot` with one matches every row, NULLs included (`NOT (1 = 0)`), as in Rails: excluding a record by a value that can't be cast excludes nothing.
- `where({ x: null })` → `"x" IS NULL`. `where({ x: [1, 2] })` binds the whole list as one value (converted like the attribute's own values), so a list of any length fits a statement's limits on bound values. (D1) On D1 that's `"x" IN (SELECT value FROM json_each(?))`, within its 100 bound parameters. (Postgres) On Postgres it's `"x" = ANY($1)`, the list bound as an array. `where({ x: [] })` → `1 = 0`. `whereNot({ x: [] })` → `1 = 1`. `where({ x: [1, null] })` → `(<the list> OR "x" IS NULL)`.
- Comparisons: `where({ age: gte(18) })`, `gt`, `lt`, `lte`, and `where({ createdAt: between(start, end) })`, which includes both ends like Rails' `start..end`. `between(start, end, { excludeEnd: true })` is `start <= x < end`, like `start...end`. `gte` and `lte` are also Rails' endless and beginless ranges. The value is converted like the attribute's own, so dates compare by time, and its type must be the attribute's. Only number, string and datetime attributes can be compared: a comparison on a boolean or `json` attribute is a type error, and throws `TypeError`. A comparison with `null` or `undefined` throws `TypeError`: use `where({ x: null })` to match NULL. Comparisons are values of their own class, so a `json` attribute's object value (`{ gt: 1 }`) still means equality. A record built from the Relation doesn't take a comparison's value.
- `whereNot` wraps the whole condition: `whereNot({ a, b })` → `NOT ("a" = ? AND "b" = ?)`. Following SQL semantics, `whereNot({ role: "admin" })` also excludes NULL roles. `whereNot({ role: null })` → `"role" IS NOT NULL`.
- Other hand-written conditions must be `sql` tagged templates (ADR-0006): ``where(sql`lower(${column("email")}) = ${email}`)``. Plain strings are rejected with a `TypeError` (and are compile errors). Values interpolated into a fragment have no declared type, so a `Date` is bound as ISO text and a boolean as 1/0, matching how attributes are stored by default. `column("publishedAt").value(date)` (#142) is a value of that attribute: cast as an assigned value (a value it can't hold throws `TypeError` naming the Model and attribute), then written as the attribute stores it (an integer for `storage: "unixSeconds"` or `"unixMilliseconds"`, 0/1 for a boolean, JSON text for `json`). It's still a bound parameter, hidden from `onQuery` when the attribute is filtered (#83), and an attribute the Model doesn't have is `UnknownAttribute` when the fragment is used. Fragments with equal typed values have the same shape for `or`, and equal `json` inputs are compared by their JSON text. It takes one value, not an array, so an `in (…)` list takes one `value` per element; a typed value is cast when `where`, `order` and the other methods are given the fragment, not when the query runs. (#149) A `Date` or a date text string (an ISO date or datetime, or SQLite's zone-less `2026-01-02 03:04:05`) interpolated bare binds ISO text, which never compares with an attribute stored as an integer, so use `value` there. A bare one placed beside the `column()` of an attribute with `storage` throws `TypeError` naming the Model and attribute, when `where`, `whereNot`, `findBy`, `exists`, `order`, `reorder` or `updateAll` is given the fragment (inside an `or` too). It reads only the text between the column and the value: a comparison operator (`=`, `==`, `<>`, `!=`, `<`, `<=`, `>`, `>=`) alone, or `BETWEEN … AND` (and `NOT BETWEEN`) with the value as a bound or as the value tested, in either order. Anything else isn't judged, so `abs(col - ${date})`, `datetime(col, 'unixepoch') >= ${date}`, `col + 1 = ${date}`, `IN` and `IS` pass, and so do a parenthesised column or a comment between the two. A value is never read, and there's no way to switch it off.
- `order({ createdAt: "desc", id: "asc" })` sorts by each key in turn, and repeated calls append. NULLs sort first in ascending order, as SQLite sorts them, unless placed: `order({ role: { direction: "asc", nulls: "last" } })` compiles to `NULLS LAST`. An expression is an `sql` fragment: ``order(sql`lower(${column("email")})`)``, with the direction inside it. Plain strings throw `TypeError`. `reorder(spec)` replaces the order so far, as in Rails, and `reorder()` removes it. `limit`/`offset` page, and `offset` works without a `limit`.
- `first()` and `last()` with no order sort by the primary key ascending or descending. With `limit`/`offset`, `first`, `last`, `take` and `exists` work within that page (so `limit(0)` has none). `last()` reverses every direction of an explicit order, and moves placed NULLs to the other end, as Rails' `reverse_order` does. It can't reverse an `sql` fragment, so it throws `IrreversibleOrder` (Rails' `IrreversibleOrderError`). That is stricter than Rails, which flips a plain string order such as `"name DESC"` and only raises for ones it can't parse (function calls, NULLS placement). A fragment is a template with bound values, and reversing it would mean parsing SQL. `take()` adds no ordering.
- `find()`, `findBy()` and `findByOrThrow()` keep the Relation's where conditions, scopes and includes, ignore its limit, offset and `select()`, and always load full rows. They ignore its order too, except that `find` with several ids returns them in the Relation's order when it has one (see above).
- `or()`: same Model on the same database (checked when the query runs, #93), and the same select, order (fragments compare by text and values), limit, offset and distinct. Only where conditions may differ, and each side is wrapped in parentheses. Otherwise it throws `IncompatibleRelation`.
- `merge()`: same Model on the same database only (checked when the query runs, #93). Where conditions combine with AND. For order, limit, offset, select and distinct, a clause the argument sets explicitly replaces the receiver's, and a clause it doesn't set leaves the receiver's alone. Orders are replaced, not concatenated, which is a deliberate difference from Rails. An argument built with `reorder()` replaces the order even when its own is empty, as in Rails. Merging across Models throws `IncompatibleRelation`.
- `toSql()` (#46), as Rails' `to_sql`, returns `{ sql, params }` for the SELECT `toArray()` sends, with the database's own placeholders (`?` on D1, `$1`, `$2`, … on Postgres), without sending it, so it needs no database when its Model's schema names its adapter. A Model with no schema compiles for the request's database, and with none it throws `NoDatabase`, since nothing says which database's SQL to write (#277). It shows the columns really loaded (a `select` plus the primary key and the keys `includes` needs), `limit` and `offset` as bound values, and a `none()` Relation as its conditions with `1 = 0`. It isn't the query `count()`, `pluck()` or `exists()` send, as in Rails. Values are never inlined (ADR-0006), so Rails' inlined values are `params` here. The params are the values D1 would bind, filtered attributes included: `onQuery` hides them, `toSql()` doesn't, as Rails' `to_sql` doesn't filter. A Model has it as a static (`User.toSql()`).

## Terminal operations

_Portable._

_Guide:_ [querying](<../site/docs/(basics)/querying.mdx>). _Code:_ `active-record/src/relation.ts`, `active-record/src/load.ts`, `active-record/src/pagination.ts`.

- `toArray`, `first`, `last`, `take`, `find`, `findBy`, `findByOrThrow`.
- `pluck("email")` resolves to converted values. `pluck("id", "email")` resolves to tuples.
- `count()` counts over the whole query as a subquery, so it always equals the number of rows `toArray()` would return, including `limit`, `offset`, `select` and `distinct` (with `select("role").distinct()`, NULL counts as one distinct value). `count("role")` counts non-null values, and after `distinct()` without a `limit` or `offset` it compiles to `COUNT(DISTINCT "role")`, the distinct non-null values. After `distinct()` with a `limit` or `offset`, the limit and offset pick from the distinct values, as in Rails. The subquery selects `DISTINCT "role"` with the Relation's order, limit and offset, and the count is of its non-null values. So `count("role")` is how many non-null values `pluck("role")` returns (#250). A NULL takes its place among the values the limit and offset pick, but isn't counted. The counted attribute replaces the Relation's `select`. Without a `limit` or `offset`, the subquery leaves out the Relation's order (#215). The order can't change how many rows it finds. Leaving it out saves SQLite sorting every match only to count it. With a `limit` or `offset`, the order stays, because it picks the rows. `paginate()` refuses a Relation with its own `limit` or `offset`, so its count never sends the order.
- `exists(conds?)` issues `SELECT 1 … LIMIT 1`, with the Relation's `offset` if it has one. It leaves out the Relation's order (#215). Whether a row exists doesn't depend on the order, even past an offset. So D1 reads one row, or up to the offset, instead of sorting every match. After `distinct()` with an offset, it selects the Relation's own columns instead of `1`, and D1 reads until it has found one distinct row past the offset (#222). With `DISTINCT 1`, every match would be the same row, and the offset would skip it. `isEmpty()` and `hasAny()` go through `exists()`.
- `paginate({ page, perPage })` (#100) resolves to a **Page**, a plain object ready for `Response.json()`: `{ records, page, perPage, total, totalPages, hasNext, hasPrevious }`. Its `COUNT` (as `count()`'s, so `select` and `distinct` count what the pages hold) and the page's `SELECT` go to D1 as one batch: one round trip. (Postgres) On Postgres they're sent one after another on one client, so the count can briefly disagree with the rows (an allowed difference). Its `includes()` preloads go in the same batch. It's a terminal, not chainable (`page(2).per(25)`), since only a terminal can promise one round trip. Pages end their order with the primary key (alone, with no order, as `first()` does), unless the order already has it, so tied records keep their pages between requests; after `distinct()`, where the key isn't loaded, they end it with the selected attributes instead. `totalPages` is `ceil(total / perPage)`, so `0` with no records, as in Kaminari; `hasNext` is `page < totalPages`, and `hasPrevious` is `page > 1`. Past the last page, `records` is `[]` with the real `total`, not an error.
  - `{ count: false }` skips the `COUNT`, which reads every matching row (D1 bills rows read): one `SELECT` fetches `perPage + 1` records, returns `perPage` of them, and reports `hasNext`. Its type has no `total` or `totalPages`, rather than `undefined` ones. Keyset (cursor) pagination is a separate, deferred issue.
  - `page` and `perPage` are untrusted input, cast as an `integer` attribute's assigned value is (#81): `"2"` is 2, and `"abc"`, `1.5` or anything below 1 rejects with `TypeError`, before any query, as does a page so far that its offset isn't a safe integer. `undefined`, `null` and `""` mean the default, so `paginate({ page: url.searchParams.get("page") })` is page 1 without one. The default `perPage` is `static perPage` (25), and a larger `perPage`, given or declared, is capped at `static maxPerPage` (100) without an error. Both are inherited, usually set on the app's base class, and each must be a whole number from 1, or the Model is an `InvalidModel` when it's first used. D1 caps neither rows returned nor response size; the cap exists because D1 bills every row read, a Worker has 128 MB of memory, and a query has 30 seconds.
  - A Relation with its own `limit` or `offset` rejects with `IncompatibleRelation`, rather than having them replaced. On `none()`, it's an empty page (`total: 0`) with no query. On a `hasMany`, it queries D1 even when the owner has the records loaded, as `count()` does.
- `size()`, `isEmpty()` and `hasAny()`, as Rails' `size`, `empty?` and `any?`. A loaded association answers from its records, built ones included, without a query. Otherwise `size()` is a `COUNT(*)` plus an association's unsaved built records, and `isEmpty()` is `!exists()` (it's `false` without a query while an association has unsaved built records). `hasAny()` is the opposite of `isEmpty()`. Rails' `one?`, `many?` and `none?` aren't offered: `hasOne`/`hasMany` would read like the association declarations, and `isEmpty()` already says "none".
- Naming: `is…` asks about a state of the thing itself (`isNewRecord()`, `isEmpty()`, `isLoaded()`, `isAttributeChanged()`), and `has…` about something it holds: a collection's records (`hasAny()`) or a record's last saved change (`hasSavedChangeTo()`). Methods that raise end in `OrThrow` (ADR-0005).
- `none()` never touches D1, so it needs no database (no `withDatabase` or binding): `toArray` gives `[]`, `count` gives `0`, `exists` gives `false`, `first`/`last`/`take`/`findBy` give `null`, `pluck` gives `[]`, and `find` throws `RecordNotFound`. Chaining keeps it `none()`. `none().or(r)` and `r.or(none())` both return `r`.

## Partial records

_Portable._

_Guide:_ [querying](<../site/docs/(basics)/querying.mdx>). _Code:_ `active-record/src/relation.ts`, `active-record/src/record-state.ts`.

- `select()` on a Model Relation accepts only declared attributes. The primary key is always loaded too, so a partial record keeps its identity, except after `distinct()`, where adding the key would make every row distinct. Such records carry only the selected attributes.
- Reading an unloaded attribute throws `MissingAttribute`, including when a validator or callback reads it. Setting one is allowed and makes it loaded and dirty.
- `save()` writes only changed attributes (plus `updatedAt`), and never fills in unloaded ones. `reload()` loads the full row.

## Batches

_Portable._ A bullet or sentence marked (D1) is the D1 adapter's alone.

_Guide:_ [batches](<../site/docs/(basics)/batches.mdx>). _Code:_ `active-record/src/batch-builder.ts`, `active-record/src/prepared-writes.ts`, `active-record/src/statement.ts`, `active-record/src/record-statement.ts`, `active-record/src/unit-of-work.ts`, `active-record/src/batch.ts`, `active-record/src/database.ts`, `active-record/src/relation.ts`, `active-record/src/load.ts`.

```ts
const userId = crypto.randomUUID(); // ids generated in code link rows inside one batch
await db.batch((b) => [
  b.insert(User, { id: userId, email: "a@example.com" }),
  b.insert(Post, { userId, title: "Hello" }),
  b.deleteAll(db.model(Post).where({ published: false })),
]);
const published = await db.model(Post).where({ id: postId }).updateAll({ published: true }); // 1
await db.model(Post).updateAll(sql`${column("views")} = ${column("views")} + ${1}`);
```

- Bulk writes run when called, skipping validations, callbacks and hydration, as Rails' `insert_all`/`update_all`/`delete_all` do: `insert(attrs)`, `insertAll(rows)`, `upsert(attrs)` and `upsertAll(rows)` resolve to a `WriteResult`, `{ rowsAffected, rows }` (#266); `updateAll(changes)` and `deleteAll()` resolve to the number of rows, as in Rails. Unknown attributes, `undefined` values and plain strings reject the call.
- Writes are batched in a callback (#332, ADR-0020): `db.batch((b) => [...])` and `batch((b) => [...])` hand it a `Batch`, whose methods prepare each write: `b.insert`, `b.insertAll`, `b.upsert`, `b.upsertAll`, `b.updateAll` and `b.deleteAll`, each taking what it writes to first (a Model, or a Relation such as `Post.where(…)` or `user.posts()`), then the same arguments as the write run alone; and `b.save(record)` and `b.destroy(record)`. A Model is written on the batch's database: `db` for `db.batch`, the current database for `batch`. A Relation built from a Model's statics (`Post.where(…)`) is on the current database even inside `db.batch`, so a `db` that isn't it refuses it with `IncompatibleRelation`. The callback returns the prepared writes as an array, and they're sent once it has returned.
  - The callback can't await: its type is refused, and anything but an array (such as a Promise) rejects with a `TypeError`, with nothing sent. A `Batch` used after its callback has returned throws a `TypeError`.
  - A bulk write prepared this way is a **Statement**. It's compiled when prepared, so unknown attributes and the like throw then, rejecting the batch before anything is sent. It runs on the Database it was built on, and only with its batch. It has no `toSql()`: `onQuery` reports its SQL once it's sent. A save or destroy is a **record statement**, compiled only when the batch runs.
- `db.batch` runs statements atomically with D1's `batch()`: all of them are written, or none. (Postgres) On Postgres it's a transaction, on a client of its own, so a write sent beside it on the request's client never joins it, nor is lost when it rolls back (ADR-0017). It resolves to each entry's result, in order: a statement's `WriteResult` (its `rows` empty for `updateAll` and `deleteAll`), or a record statement's record. A callback returning `[]` resolves to `[]` without a query. A statement or record from another Database rejects with `IncompatibleRelation`, before any callback runs.
- Records join a batch through **record statements**: `db.batch((b) => [b.save(user), b.destroy(post), b.insert(Log, {…})])`. Unlike statements, their validations and callbacks run, when the batch runs:
  1. Each record, in order, runs its validation and before-callbacks, exactly as `save()` or `destroy()` would (a destroy brings in its `dependent:` strategies). The first that's invalid or aborts throws `RecordInvalid` (with `.record`), `RecordNotSaved` or `RecordNotDestroyed`, as saving with `save!` inside a Rails transaction does, and nothing is sent.
  2. Every write goes out as one atomic batch. If D1 refuses it (a constraint error, thrown as usual), nothing is written and every record keeps its unsaved state.
  3. Each record takes its saved state (loading what `RETURNING` gave back, or becoming destroyed), then its after-callbacks run, in order.
     This differs from a Rails transaction, where one record's `after_save` runs before the next record's `before_save`: here every before-callback runs before any write, much like Rails' `after_commit`.
- Records in one batch can't point at each other's database-generated keys, which don't exist until the batch is written. Keys generated in code (`generateId`, or a `default`) exist from `build()`, so records can be linked by them, or through autosave (#29).
- (D1) There's no interactive `transaction(async tx => …)`. D1 can't hold a transaction open across awaits, so a callback that reads and then decides what to write can't be made atomic; a batch of statements and record statements, prepared in its callback without awaiting, can.
- `insert(attrs)` writes one row. Declared attribute defaults fill attributes that aren't given (unlike Rails' `insert_all`, because in D1 app-side defaults are where keys are generated), and `createdAt`/`updatedAt` are set unless given, as Rails does. A Relation's equality conditions are inserted too, as with `build()`. A constraint failure throws, as everywhere (ADR-0005).
- `insertAll(rows)` inserts several rows in one statement (Rails' `insert_all!`), and throws on a duplicate, writing nothing. Every row must be given the same attributes, in any order, compared as given, before defaults and timestamps are filled in (`TypeError` otherwise, and for `[]`), and defaults, timestamps and a Relation's equality values apply to each row. The rows are bound as one value, so any number of rows fits in one statement. (D1) On D1 that's `INSERT … SELECT … FROM json_each(?)`, within its 100 bound parameters and its 2 MB limit on one value. Rows with no attributes at all can't be inserted together or with an `onDuplicate` or upsert (`TypeError`, as Rails raises); a lone `insert({})` writes the table's `DEFAULT VALUES`.
- `insert(attrs, { onDuplicate: "skip" })` and `insertAll(rows, { onDuplicate: "skip" })` skip rows that clash with a unique index (`ON CONFLICT DO NOTHING`). Skipping is opt-in: Rails' `insert` and `insert_all` skip by default, which ADR-0005 rules out.
- `upsert(attrs)` and `upsertAll(rows)` update a row that clashes with the unique index on `uniqueBy`, which is the primary key by default or names another unique index's attributes. As in Rails, only the attributes given are updated, never ones filled in by defaults (such as a generated key), and not the `uniqueBy` ones or `createdAt`; `updatedAt` is set. Rails' `update_only` option is deferred (#36).
- An insert or upsert's `rows` holds the `returning` attributes of each row it wrote, as Rails' `insert_all` returns its `:returning` columns (#266): the primary key by default, or the attributes `returning: [...]` names, each read as its type and typed in `rows` (a `Partial` of the attributes when `returning` isn't given, since the key's name isn't in the type). `returning: false` sends no `RETURNING` and gives `rows: []`, and so does `returning: []`. A `returning` that's neither a list nor `false` throws `TypeError`. A row that `ON CONFLICT DO NOTHING` skips isn't returned, and neither D1 nor Postgres promises the rows' order. A name that isn't an attribute throws `UnknownAttribute` when the write is built. `rowsAffected` is D1's `changes`: an upsert counts the rows it inserted and the ones it updated.
- `updateAll(changes)` takes an object of declared attributes (converted like any write) or an `sql` fragment, and leaves `updatedAt` alone, as in Rails. `{}` is a `TypeError`: `updateAll` rejects with it, and so does a batch preparing it.
- Which rows `updateAll`/`deleteAll` write follows Rails. With a `limit` or `offset`, it's `WHERE <primary key> IN (SELECT <primary key> … ORDER BY … LIMIT … OFFSET …)`, so the Relation's order picks the rows. Otherwise it's the Relation's conditions, and `order`, `select` and `includes` don't matter. `distinct()` is `IncompatibleRelation`: `updateAll`/`deleteAll` reject with it, and so does a batch preparing them.
- On a `none()` Relation, `updateAll`/`deleteAll` send nothing and resolve to `0`, as in Rails. Prepared in a batch, they're still sent, as `WHERE 1 = 0`, and report `rowsAffected: 0`.
- Neither Relations nor statements are awaitable directly (they have no `then`), so an `async` function that returns one never runs it by accident. A write runs only when its method is called, or when the batch it was prepared in runs.

## Instrumentation

_Portable._

_Guide:_ [logging](<../site/docs/(how-to)/logging.mdx>). _Code:_ `active-record/src/executor.ts`, `active-record/src/adapters/d1/driver.ts`, `active-record/src/filtering.ts`.

- `connect(env.DB, { onQuery(event) })` is called once per statement, batches included, with `{ model, sql, params, durationMs, meta, error? }` (`model` is the statement's Model's class name). `meta` is the database's own detail about the statement: on D1, its `meta` (`changes`, `rows_read`, `duration`, …); on Postgres, `{ command, rowCount }` (`PgMeta`). `sql` is the SQL as sent, with the database's own placeholders. The core's `QueryEvent<Meta>` takes its type as a parameter; the package exports `QueryEvent` and `QueryListener` with `D1Meta` filled in (#266). A `QueryListener` is declared as a method's type, so one typed for D1's `meta` can be a Model's `static onQuery`. The integration tests' query-count checks use this same hook. No logger is built in.
- **App-wide (#78):** `static onQuery` on a Model class, usually the app's base class (`static override onQuery: QueryListener = (event) => …`), is called with the same event for every statement of that Model and those extending it, at every level (the binding, `withDatabase`, an explicit `db`), after the database's own `onQuery`. It's inherited, and a Model's own replaces it. It holds no request state, so it's safe on a class, and can't tell requests apart: a request's ID comes from a database opened for it with `withDatabase`.
- **Filtered attributes (#83):** `static filterAttributes: readonly (string | RegExp)[]`, as Rails' `filter_attributes`, starts on `Model` as Rails' default `filter_parameters` (`passw`, `email`, `secret`, `token`, `_key`, `crypt`, `salt`, `certificate`, `otp`, `ssn`, `cvv`, `cvc`). An attribute is filtered when its snake_case name holds a string entry, in any case (`passwordDigest` → `password_digest` holds `passw`; `apiKey` → `api_key` holds `_key`), or a RegExp entry matches the attribute or its snake_case name. It's inherited, and a Model or the app's base class replaces it (`static override filterAttributes = [...Model.filterAttributes, "iban"]`; `[]` filters nothing). A filtered attribute's bound values are `"[FILTERED]"` in `event.params`: inserts, updates, `updateAll`, conditions, lists (the whole list, bound as one value), comparisons, and a record's stored primary key in its `UPDATE` and `DELETE`; in a multi-row insert's single JSON value, its column is `"[FILTERED]"` in every row. D1 still gets the real values. A value in an `sql` fragment has no attribute, so it's shown as given, unless it's written as `column(attribute).value(v)` (#142), which is filtered like the attribute's other values. A cast error (#81) shows a filtered attribute's value as `[FILTERED]`, and `RecordNotFound` (from `find`, `find([...])` and `reload`) shows a filtered primary key's values as `[FILTERED]`. `toJSON()` and `attributes()` are unchanged, as in Rails.
- **A listener never changes a query's outcome:** each is called on its own, and one that throws is logged with `console.error` ("onQuery threw; the query's result is unaffected:"), so the query's result, or D1's (translated) error, reaches the caller as it would have, and the other listener and the other statements of a batch are still reported. `event.model` is the Model's class name: `""` for an anonymous class, and renamed by a bundler that renames classes (Wrangler keeps names by default).
- In a batch, each statement's `durationMs` is the database's own timing for it when it reports one (D1's `meta.duration`), or else the batch's elapsed time. When a batch fails, D1 doesn't say which statement failed, so every statement is reported with the error and the batch's elapsed time. `event.error` is D1's own error; the caller gets the translated `ConstraintViolation`, with D1's error as its `cause`.

## Errors

_Portable._

_Guide:_ [errors](<../site/docs/(basics)/errors.mdx>). _Code:_ `active-record/src/errors.ts`.

Everything extends `ActiveRecordError`:

- **Lifecycle:** `RecordNotFound`, `RecordInvalid` (`.record`), `RecordNotSaved`, `RecordNotDestroyed`, `RecordDestroyed`, `CallbackAbort` (from `abort()`), `AbortAfterPersistence` (`.callback`, `.reason`)
- **Usage:** `UnknownAssociation`, `InvalidModel` (a problem in a Model's declaration, detected the first time it's used), `UnknownAttribute`, `MissingAttribute`, `IncompatibleRelation`, `IrreversibleOrder`, `DeleteRestriction`, `AssociationNotLoaded`, `NoDatabase`, `NoSession`
- **Names are a Model's own (#84).** Attributes and associations are looked up in Maps, so a name every object inherits (`constructor`, `__proto__`, `toString`, `hasOwnProperty`), from a URL's `?include=` or a JSON key say, is an `UnknownAttribute` or `UnknownAssociation` like any other unknown name, from every method that takes one. Reading an unknown attribute is `UnknownAttribute`; `MissingAttribute` is only for a declared attribute that `select` didn't load.
- **Constraints:** `ConstraintViolation`, with subclasses `RecordNotUnique`, `InvalidForeignKey`, `NotNullViolation` and `CheckViolation`
