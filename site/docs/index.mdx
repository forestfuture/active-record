## What’s inside

<CardGroup cols={2}>
  <Card title="Models, declared once" href="/models" icon="database">
    Typed attributes come from your tables, camelCase in your code and snake_case in SQL, with
    defaults, timestamps, dates, and JSON converted both ways.
  </Card>
  <Card title="Lazy, composable queries" href="/querying" icon="list-filter">
    Conditions, ordering, pagination, scopes, and preloading with one query per association, never
    N+1. Hand-written SQL goes through a tagged template, so values are always bound.
  </Card>
  <Card title="A predictable lifecycle" href="/persistence" icon="refresh-cw">
    `save`, `create`, `update`, and `destroy` run validations and callbacks in a predictable order,
    with dirty tracking and dependent strategies. Methods that throw end in `OrThrow`.
  </Card>
  <Card title="Atomic batches" href="/batches" icon="layers">
    `batch` writes a set of statements and records all at once, or not at all, on D1 and on
    Postgres. Keys generated in code let a whole graph save in one batch.
  </Card>
  <Card title="One API, two databases" href="/move-to-postgres" icon="arrow-right-left">
    Start on D1 and move to Postgres with your Models and code unchanged. Each adapter lists what
    works differently on its database.
  </Card>
</CardGroup>
