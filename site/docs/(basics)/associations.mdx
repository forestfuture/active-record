Associations connect Models: `belongsTo`, `hasMany`, and `hasOne`.

## Defining associations

Declare each association as a field, passing the target Model’s class. The field’s name is the association’s name:

<include>/_excerpts/guide/associations/declare.ts</include>

Models can refer to each other in any order. A subclass inherits its parent’s associations, and can redeclare one to change it.

## belongsTo

Use `belongsTo` on the Model whose table holds the foreign key. A post belongs to its author:

<include>/_excerpts/guide/associations/belongs-to.ts</include>

- **`await record.author()`** reads the associated record, or `null`.
- **`record.author.set(user)`** points the record at another record, and `set(null)` clears it. It’s written when the record is saved.
- **`record.author.build(attrs)`** builds a record to point at. It’s validated with the record, and saved before it, so the foreign key can be filled in.
- **`record.author.create(attrs)`** and **`createOrThrow(attrs)`** save a new record at once, and point at it. The record itself isn’t saved.

| Option       | Does                                                                                                      |
| ------------ | --------------------------------------------------------------------------------------------------------- |
| `foreignKey` | The attribute on this record that holds the link. Defaults to the association’s name + `Id`               |
| `primaryKey` | The attribute on the target it points at. Defaults to the target’s primary key                            |
| `scope`      | Narrows the target, `(q) => q.where(…)`. See [Scoping associations](#scoping-associations)                |
| `optional`   | Lets the record point at nothing. See [Requiring the record](#requiring-the-record)                       |
| `autosave`   | `true` saves the record’s changes with this record. See [Saving changed records](#saving-changed-records) |

### Requiring the record

Saving a record checks that each `belongsTo` points at a record that exists. If the foreign key is `null`, or no row has that key, the save fails with “must exist” on the association, such as `author`. The record it finds stays loaded. A saved record whose foreign key hasn’t changed isn’t checked again.

If a record may point at nothing, pass `optional: true`. A top-level category has no parent:

<include>/_excerpts/guide/generators/self-reference.ts</include>

A record built through a `hasMany` or `hasOne` already points at its owner, so it passes the check before either is saved. See [Autosaving](#autosaving).

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

Rails requires a `belongs_to` record by default too, and `optional: true` works the same. As in Rails 7.1, an unchanged foreign key isn’t checked. There’s no setting to turn the check off for every association, like Rails’ `belongs_to_required_by_default`.

</Callout>

## hasMany

Use `hasMany` on the Model the other table’s foreign key points at. A user has many posts:

<include>/_excerpts/guide/associations/has-many.ts</include>

- **`record.posts()`** is a Relation of the associated records, with every Relation method and the target’s scopes.
- **`record.posts().build(attrs)`** builds a record with the owner’s key, saved with the owner. See [Autosaving](#autosaving).
- **`record.posts().create(attrs)`** and **`createOrThrow(attrs)`** save a new record at once. The owner must already be saved.
- **`record.posts().push(...records)`** adds records. It sets their foreign key and saves them in one write, or resolves to `false` and saves none if one can’t be saved. On an unsaved owner, they’re saved with it.
- **`record.posts().delete(...records)`** removes records by the `dependent` strategy. It destroys them for `"destroy"`, deletes them for `"deleteAll"`, and otherwise sets their foreign key to `NULL`.
- **`record.posts().destroy(...records)`** destroys records with their callbacks, whatever the strategy.
- **`record.posts().clear()`** removes every record, as `deleteAll()` does.
- **`record.posts().destroyAll()`** destroys every record with its callbacks, whatever the strategy, and leaves the association empty.
- **`insert`, `upsert`, `updateAll`, and `deleteAll`** write to the owner’s records. See [Writing many rows](#writing-many-rows).

| Option       | Does                                                                                                             |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| `foreignKey` | The attribute on the target’s records that holds the link. Defaults to this Model’s class name + `Id`            |
| `primaryKey` | The attribute on this record the foreign key points at. Defaults to the primary key                              |
| `scope`      | Narrows or orders the records, `(q) => q.order(…)`. See [Scoping associations](#scoping-associations)            |
| `dependent`  | What destroying the owner does to the records. See [Destroying dependent records](#destroying-dependent-records) |
| `autosave`   | `true` saves the records’ changes with the owner. See [Saving changed records](#saving-changed-records)          |

## hasOne

Use `hasOne` like `hasMany`, when there’s at most one record. A user has one profile:

<include>/_excerpts/guide/associations/has-one.ts</include>

- **`await record.profile()`** reads the associated record, or `null`. If several records point at the owner, it’s the first by the scope’s order, then the primary key.
- **`await record.profile.set(profile)`** gives the owner another record, and `set(null)` removes it. On a saved owner, the record is saved at once, so await it. On an unsaved owner, it’s saved with the owner.
- **`record.profile.build(attrs)`** builds a record with the owner’s key, saved with the owner.
- **`record.profile.create(attrs)`** and **`createOrThrow(attrs)`** save a new record at once. The owner must already be saved.

`hasOne` takes the same options as `hasMany`.

### Replacing the record

Giving a saved owner a new record removes its old one, by the association’s `dependent` strategy:

<include>/_excerpts/guide/associations/has-one-replace.ts</include>

| `dependent`                               | What happens to the old record                   |
| ----------------------------------------- | ------------------------------------------------ |
| `"destroy"`                               | It’s destroyed, with its own callbacks           |
| `"delete"`                                | It’s deleted, without callbacks                  |
| `"nullify"`, a restrict strategy, or none | Its foreign key is set to `NULL`, and it’s saved |

The old record is removed in the same atomic batch that writes the new one. That’s at once for `set` and `create`, and when the owner is saved for `build`.

If the old record can’t be saved with a `NULL` foreign key, the write throws `RecordNotSaved`, and nothing is written. If the new record doesn’t save, the old one stays. `set` throws `RecordNotSaved` and leaves the association as it was. `create` returns the unsaved record, and saving the owner tries again.

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

`await user.profile.set(profile)` is Rails’ `user.profile = profile`. Rails removes the old record as soon as you build a new one, so a build that’s never saved still loses it. Here, `build` waits for the owner’s save.

</Callout>

## Polymorphic associations

A polymorphic `belongsTo` points at a record of any of several Models, listed in an array. A like can belong to a photo or a video:

<include>/_excerpts/guide/associations/polymorphic-declare.ts</include>

The record holds the link in two attributes: a type, which names the Model, and a foreign key. They’re the association’s name with `Type` and `Id`, so `likeable` uses `likeableType` and `likeableId`. On each listed Model, a `hasMany` or `hasOne` names the `belongsTo` with `as`, and reads the records whose type is that Model.

- **`await like.likeable()`** reads the record of the Model the type names, or `null`.
- **`like.likeable.set(video)`** sets both the type and the foreign key, and `set(null)` clears both. It’s written when the record is saved.
- **`video.likes()`** works like any `hasMany`. Records built, created, or pushed through it get the video’s type and key. Removing records through it, or by a `"nullify"` strategy, clears both.

Here’s each of them at work:

<include>/_excerpts/guide/associations/polymorphic-read.ts</include>

| Option        | Does                                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `foreignType` | The attribute that holds the type. Defaults to the association’s name + `Type`, or on a `hasMany` or `hasOne`, the `as` name + `Type` |
| `as`          | On a `hasMany` or `hasOne`: the name of the target’s polymorphic `belongsTo`. Its foreign key defaults to that name + `Id`            |

The polymorphic `belongsTo` also takes `foreignKey`, `primaryKey`, `optional`, and `autosave`, as any `belongsTo` does.

:::note
The polymorphic side has no `build` or `create`, since it can’t tell which Model to make, and no `scope`. Neither D1 nor Postgres can enforce a foreign key that points at a different table in each row.
:::

### Storing the type

The type holds the listed Model’s `modelName`, such as `"Photo"`. A subclass of a listed Model is stored as the Model whose table it shares. If a stored type names none of the listed Models, reading the association throws `UnknownModelName`.

:::warning[Set modelName if your bundler renames classes]
The type is saved in your rows. A Model’s name is its class name unless it sets `static modelName`, so a bundler that renames `Photo` to `e` saves `"e"`, and a later build can’t read those rows. Wrangler keeps class names by default. With any other bundler, set `static modelName` on each listed Model. See [Naming Models](/models#naming-models).
:::

### Preloading polymorphic records

`includes` preloads a polymorphic association with one query for each listed Model:

<include>/_excerpts/guide/associations/polymorphic-preload.ts</include>

Each query runs the likes’ query again to find their keys, even for a Model no like points at. Index what that query filters and sorts by. A nested include can name an association that only some listed Models have: `includes({ likeable: "album" })` loads the photos’ albums and skips the videos.

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

Rails declares `belongs_to :likeable, polymorphic: true` without a list, and finds the class from the stored name. Here you list the Models, so `await like.likeable()` is typed `Photo | Video | null`. Rails preloads a polymorphic association after the likes load, with one query per type it finds. Here every listed Model’s query goes with the likes’ own, in one round trip. The cost is that each of them reads the likes’ query again, even for a Model no like points at. Records built through `video.likes()` point back at the video without a query, which Rails doesn’t do for a polymorphic association.

</Callout>

## Naming foreign keys

A foreign key names an attribute, such as `authorId`, rather than a column. By default, it’s inferred:

- **`belongsTo`** uses the association’s name + `Id`. `author = belongsTo(Author)` uses the record’s own `authorId`.
- **`hasMany` and `hasOne`** use the Model’s name + `Id`, on the target. `Author`’s associations use `authorId`, `BlogPost`’s use `blogPostId`, and `APIKey`’s use `apiKeyId`.

If the name doesn’t follow the convention, pass `foreignKey`:

```ts
import { belongsTo } from "@forestfuture/active-record";

export class Post extends ApplicationRecord {
  author = belongsTo(User, { foreignKey: "userId" });
}
```

Keys are checked the first time a Model is used, and a missing attribute throws `InvalidModel`.

<Expandable title="Bundlers and class names">

A Model’s name is its class name, unless it sets `static modelName`. Wrangler keeps class names by default, even when minifying. If a bundler renames `Author` to `e`, the inferred `eId` doesn’t exist, and the first use of the Model throws `InvalidModel`, saying where the key came from. Set `static modelName = "Author"` (see [Naming Models](/models#naming-models)), pass `foreignKey`, or keep class names in your bundler’s settings.

</Expandable>

## Caching loaded records

A loaded association is cached on the record. Reading `author()` again doesn’t query, and neither does `articles().toArray()` once the collection is loaded:

<include>/_excerpts/guide/associations/read.ts</include>

- Changing a foreign key makes the next read query again.
- `reload()` clears the cache, and `await record.reloadAssociation("articles")` reloads one association.
- A write through a `hasMany` clears its loaded collection: `insert`, `upsert`, `updateAll` and `deleteAll`, alone or in `db.batch`, even after `where` or `order`, or with the association joined by `or()`, `merge()` or a scope. `create`, `push`, `delete`, `destroy`, and `clear` on the association itself update it instead, so the next read still doesn’t query.
- A write made another way, such as `Article.where({ authorId: author.id }).deleteAll()`, doesn’t touch a loaded collection: reload the association to see it.

<Callout type="info" title="Beyond Rails" icon="/ruby.svg">

After `author.articles().where({ title: "Untitled" }).deleteAll()`, you’d expect `author.articles()` not to hold the untitled articles any more, and here it doesn’t. In Rails it still does, until you reload: only a write on the association itself (`author.articles.delete_all`) resets what it has loaded, while a write after `where`, `or`, `merge` or a scope runs on a separate relation. In Active Record any write built from `author.articles()` clears it, at the cost of one query on the next read.

</Callout>

:::note
A `belongsTo` whose foreign key is `null`, or an association on an unsaved owner, reads without a query.
:::

## Preloading associations

Load an association for every record at once with `includes`, with one query per association however many records there are:

<include>/_excerpts/guide/associations/preload.ts</include>

Nest with an object: `includes({ articles: "comments" })` or `includes({ articles: ["comments", "tags"] })`.

The example above sends four queries, however many authors there are. On D1, the whole tree goes [in one round trip](./d1#sending-queries-in-one-round-trip) with the authors’ own query. An association to [another database](./several-databases#associating-models-on-different-databases) takes one more.

:::note
With a `limit` or `offset`, `includes` ends the order with the primary key, so the preloads find the same records the query loads.
:::

<Callout type="info" title="Beyond Rails" icon="/ruby.svg">

Rails sends each association’s preload query on its own, so every association adds a round trip. On D1, the whole tree on one database takes one.

</Callout>

:::note
`hasMany` and `hasOne` find their records by the foreign key, both with `includes` and when you read one record’s association, such as `author.articles()`. Add an index to the foreign key column. Otherwise D1 reads every row of the table for each lookup, and bills you for each row it reads. A `references` column from the [generators](./generators) is indexed already, and you can add an index to any other foreign key yourself:

```sql
CREATE INDEX index_articles_on_author_id ON articles (author_id);
```

`includes` also runs the query’s own conditions again for each association it preloads. With a `limit` or `offset`, it runs the query’s order again as well. Index the columns the query filters and sorts by, too. Otherwise D1 reads those rows again for every association, and bills you each time.

:::

`record.loaded("profile")` reads a preloaded association synchronously, and throws `AssociationNotLoaded` if it wasn’t loaded, so a template never sends a query. `record.isLoaded("profile")` checks first.

## Creating related records

Records built or created through a `hasMany` get the owner’s key:

<include>/_excerpts/guide/associations/create-through.ts</include>

### Autosaving

A record built through an association is saved with its owner. Build a whole graph, then save the owner:

<include>/_excerpts/guide/associations/autosave.ts</include>

The built records are validated with the owner. An invalid article makes the author invalid (“Articles is invalid”), with its own errors on the article. To validate the records an association loaded too, use [`validatesAssociated`](./validations#validating-associated-records). Each built article’s `author` is the owner, without a query, even before either is saved.

When the owner’s key is generated in code, as here, everything is written in one atomic batch. Records on [another database](./several-databases#associating-models-on-different-databases) are written there separately.

#### Saving changed records

By default, only new records are saved with their owner. Declare an association with `autosave: true` to save the changes to its loaded records too, as `Author`’s `articles` does above:

<include>/_excerpts/guide/associations/save-changed.ts</include>

Saving the author saves each article that changed, in the same atomic batch. Unchanged articles aren’t validated or written. Only the records the association holds count: those it loaded, and those built through it. A record you found with a query of its own isn’t saved.

The changed records are validated with the owner. An invalid one’s errors are copied to the owner under the association’s name: an article with a blank title gives the author an `articles.title` error, “Articles title can’t be blank”.

`autosave: true` works on a `hasOne` and a `belongsTo` too. A `belongsTo`’s record is saved before its owner.

#### Removing records on save

Mark a record with `markForDestruction()` to destroy it when its owner is saved:

<include>/_excerpts/guide/associations/mark-for-destruction.ts</include>

Marking writes nothing, and the marked articles stay in `author.articles()` until the author is saved. Then each is destroyed with its callbacks and `dependent` strategies, in the same batch as the author, and leaves the association. Changed articles are saved after the destroys.

`isMarkedForDestruction()` reads the mark, and `reload()` clears it. A marked record that was never saved is dropped from the association, and nothing is written for it. Through a `belongsTo`, the owner’s foreign key is set to `null`, and the owner is written before its record is destroyed.

If a marked record refuses to be destroyed, because its `beforeDestroy` aborts or a `restrictWithError` strategy stops it, nothing is written. `save()` returns `false`, and `saveOrThrow()` throws `RecordNotDestroyed`. The marked record holds the reason, in `abortReason` or `errors`.

:::note
A mark only counts through an association declared `autosave: true`.
:::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

`autosave: true`, `markForDestruction`, and the copied errors work as in Rails. Rails destroys a marked `belongs_to` record before it saves the owner. Here the owner is written first, so a foreign key constraint doesn’t refuse the delete. When a marked record refuses to be destroyed, Rails raises from `save` for a `has_many`, and saves the owner anyway for a `has_one` or `belongs_to`. Here the save is refused the same way for every association.

</Callout>

:::warning[Keys D1 generates]
When D1 generates the key, with an `INTEGER PRIMARY KEY`, the key doesn’t exist until the owner is written. So the owner is written first, and its records follow in the next batch, a level at a time. The batches aren’t atomic together: if a record fails at the second level, the save throws with the owner already saved. Generate keys in code wherever a graph must save all at once.
:::

## Reaching records through another association

Reach records through another association with `through`. A tag has many articles through its taggings:

<include>/_excerpts/guide/associations/through.ts</include>

`through` names one of the Model’s own associations, here `taggings`. The join Model’s association with the same name, singular or plural, leads on to the records: `articles` follows each tagging’s `article`.

| Option    | Does                                                                                            |
| --------- | ----------------------------------------------------------------------------------------------- |
| `through` | The association to go through                                                                   |
| `source`  | The join Model’s association to follow. Defaults to this association’s name, singular or plural |
| `scope`   | Narrows or orders the records. See [Scoping associations](#scoping-associations)                |

### Naming the source

If the join Model’s association has another name, pass it as `source`:

<include>/_excerpts/guide/associations/through-source.ts</include>

### Reading and preloading

Read it as you would any `hasMany`:

<include>/_excerpts/guide/associations/through-read.ts</include>

- **`tag.articles()`** is a Relation, with every Relation method, read in one query. Its writes go to the taggings, as [below](#writing-through-it).
- **Each record comes back once**, however many join records point at it.
- **`includes("articles")`** loads the join records and the articles with the tags’ own query, in one round trip on D1. The join records aren’t kept as `taggings` unless you include them too.

The scopes of both associations it goes through apply, and so does its own `scope`.

### Going through a belongsTo or a hasOne

`through` can name a `belongsTo`, a `hasMany`, or a `hasOne`, and the association it follows can be any of the three. A `hasOne` goes through a `belongsTo` or a `hasOne`:

<include>/_excerpts/guide/associations/through-has-one.ts</include>

An association can also go through one that goes through another, as `writers` does above through `articles`.

### Writing through it

Add records through the association with `push`, `build`, and `create`. Each makes the join record that links the owner to the record:

<include>/_excerpts/guide/associations/through-write.ts</include>

- **`push(article)`** saves a tagging for each article, in one write. A new article is saved first.
- **`build(attributes)`** builds the article and its tagging. Saving the tag saves both. Saving the article on its own saves no tagging.
- **`create(attributes)`** saves the article, then its tagging. An invalid article comes back unsaved, and nothing is written.

On a tag that isn’t saved yet, `push` and `build` wait for the tag’s save. `create` throws `RecordNotSaved` there, as it does through a `hasMany`.

Records built or created through it take the equality values of its `scope`, and their join records take those of the association it goes through.

#### Removing records

Removing records through the association removes their join records. The records themselves stay:

| Method             | Does                                                                                                |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| `delete(article)`  | Deletes the tag’s taggings to the article, without callbacks                                        |
| `destroy(article)` | Destroys those taggings, running their callbacks, in one write                                      |
| `clear()`          | Deletes every tagging to the tag’s articles, without callbacks. The tag then has no articles loaded |
| `deleteAll()`      | Deletes the same taggings, and resolves to how many it deleted                                      |
| `destroyAll()`     | Destroys the same taggings, running their callbacks, and resolves to the articles                   |

An article the tag doesn’t reach removes nothing. To remove an article itself, destroy it: `await article.destroy()`.

In a batch, pass the association to the write: `b.deleteAll(tag.articles())` deletes the tag’s taggings.

:::warning[A narrowed deleteAll or destroyAll removes the records themselves]
`updateAll`, and a narrowed `deleteAll` or `destroyAll`, act on the records, as any Relation’s do. `tag.articles().where({ title: "Draft" }).deleteAll()` deletes those articles for every tag, not the tag’s taggings.
:::

#### Removing join records with dependent

A `hasMany` through a join Model takes `dependent: "destroy"` or `dependent: "deleteAll"`, which acts on its join records. With `"destroy"`, destroying the tag destroys its taggings, running their callbacks, and `delete` destroys them too. With `"deleteAll"`, destroying the tag deletes them without callbacks. `clear` and `deleteAll` always delete them without callbacks.

#### Setting a hasOne through another

A `hasOne` that goes through another `hasOne` has `set`. `await member.club.set(club)` points the member’s membership at the club, or creates a membership if there isn’t one, with the equality values of the membership association’s `scope`. `set(null)` destroys the membership. It has no `build` or `create`.

#### Spotting read-only associations

Writes need a join Model: the association has to go through a `hasMany` (a `hasOne`, for a `hasOne`), and follow a `belongsTo` from there, with neither going through another. Any other write throws `ReadonlyAssociation`, naming the association that stops it. `writers` above is read-only, since it goes through `articles`, which goes through `taggings`.

`insert`, `insertAll`, `upsert`, and `upsertAll` throw `ReadonlyAssociation` on any association through another, since they write no join records.

:::note
Every association it goes through must be on one database. One that reaches [another database](./several-databases#associating-models-on-different-databases) is an `InvalidModel` for now ([#435](https://github.com/forestfuture/active-record/issues/435)).
:::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

`through` and `source` work as Rails’ `has_many :through` and `has_one :through` options do. Rails reads through a SQL join, so a record two join records point at comes back twice unless the association is `distinct`. Here it comes back once.

Writing through it works as in Rails: `destroy` destroys the join records rather than the records, `clear` deletes them whatever `dependent` is, and `insert_all` through it raises. Rails also writes through a `belongsTo` or `hasOne` hop by building or updating that hop’s record, which can change a record that other records share. Here that throws `ReadonlyAssociation`. Rails’ `disable_joins` has no counterpart yet.

</Callout>

## Destroying dependent records

Set what destroying the owner does to its records with `dependent`:

| Strategy                   | What happens                                                                            |
| -------------------------- | --------------------------------------------------------------------------------------- |
| `"destroy"`                | Each record is destroyed with its own callbacks and dependents                          |
| `"deleteAll"` / `"delete"` | The records are deleted in one statement, without callbacks (`"delete"` for a `hasOne`) |
| `"nullify"`                | Their foreign keys are set to `NULL`                                                    |
| `"restrictWithException"`  | The destroy throws `DeleteRestriction` while there are records                          |
| `"restrictWithError"`      | The destroy returns `false`, with an error on the owner’s `base`                        |

Everything a destroy does on the owner’s database, its DELETE included, is written in one atomic batch. Records on [another database](./several-databases#associating-models-on-different-databases) are written there separately. Strategies run after the owner’s `beforeDestroy` callbacks, so an `abort()` leaves the records alone.

:::note
Without a strategy, it’s up to the database. If the table declares the foreign key with `REFERENCES`, destroying an owner whose records still point at it throws `InvalidForeignKey`.
:::

## Counting records with a counter cache

To keep a count of an article’s comments on the article itself, declare `counterCache` on the comment’s `belongsTo`:

<include>/_excerpts/guide/counter-caches/declare.ts</include>

The article needs an attribute for the count, named for the counted Model: `commentsCount` for comments. To keep it in another attribute, name it: `counterCache: "replyCount"`.

Creating a comment adds one to its article’s count, and destroying it takes one away:

<include>/_excerpts/guide/counter-caches/counting.ts</include>

Each change is written in the same atomic batch as the comment, so the count can’t drift from the rows. Changing a comment’s `articleId` moves the count to the other article. An article you’ve loaded takes the new count too, without a save.

Removing comments through the article’s association counts them out: `delete`, `clear`, and `deleteAll()` on `article.comments()`. Bulk writes leave the count alone: `insert`, `insertAll`, `upsert`, `updateAll`, and `deleteAll()` on any other Relation.

:::note
A polymorphic `belongsTo` counts a record on whichever listed Model its type names, so each of them declares the attribute. A counter cache on a Model on [another database](./several-databases) throws `InvalidModel`, since its count couldn’t be written in the same batch.
:::

### Reading the count

A new counter starts at zero, even for an article that already has comments. To fill it in before anything reads it, declare it with `active: false`:

Writes keep the count up to date, while `size()` and the others count the rows. Run `resetCounters` for each article, then remove `active: false`.

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

Rails takes one from the article the comment’s key pointed at when it was loaded. Here the count is taken from the article the comment’s row points at as it’s deleted, so a comment that’s already gone, or that another request moved, doesn’t throw the count off.

Rails’ `belongs_to … touch: true` also touches the article when its count changes. That option isn’t built yet ([#353](https://github.com/forestfuture/active-record/issues/353)).

</Callout>

## Writing many rows

`insert`, `updateAll`, and `deleteAll` work through a `hasMany`, scoped to the owner’s records:

<include>/_excerpts/guide/associations/statements.ts</include>

In a batch, pass the association to the write: `b.deleteAll(article.comments())`.

`upsert` and `upsertAll` through a `hasMany` only update the owner’s records. When a row clashes with another owner’s record, that record stays as it is. The row isn’t written, counted, or returned. To find out whether a row was skipped, compare `rowsAffected` with the number of rows you gave.

<Callout type="info" title="Beyond Rails" icon="/ruby.svg">

In Rails, `upsert_all` through an association writes the owner’s key into a clashing row. So `current_user.posts.upsert_all(rows)`, given an id from a request, moves another user’s post to the current user. Here that row is skipped, as `onDuplicate: "skip"` skips a duplicate.

</Callout>

`deleteAll()` on the association follows its `dependent` strategy: it deletes the records for `"destroy"` or `"deleteAll"`, and otherwise sets their foreign keys to `NULL`. See [Bulk writes and batches](./batches).

## Not built yet

These features aren’t in Active Record yet. The code shows the shape they’re likely to take.

- **Autosaving through an association through another** ([#450](https://github.com/forestfuture/active-record/issues/450)): `articles = hasMany(Article, { through: "taggings", autosave: true })`, which saves the tag’s changed articles with it.
- **Associations through another across databases** ([#435](https://github.com/forestfuture/active-record/issues/435)): an association whose hops are on different databases, read with a query per database.
- **Never autosaving** ([#378](https://github.com/forestfuture/active-record/issues/378)): `articles = hasMany(Article, { autosave: false })`, which never saves the association’s records with the owner, not even new ones.
- **Numbered autosave errors** ([#379](https://github.com/forestfuture/active-record/issues/379)): `hasMany(Article, { autosave: true, indexErrors: true })`, which names a copied error by the record’s position, `articles[1].title`.
- **Inverse associations** ([#62](https://github.com/forestfuture/active-record/issues/62)): after `await post.comments().toArray()`, each `comment.post()` returns that same post, without a query.
