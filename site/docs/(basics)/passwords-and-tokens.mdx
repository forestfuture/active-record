:::warning[The default hash is limited by Workers]
Passwords are hashed with PBKDF2-SHA256 at 100,000 iterations. That’s the most Cloudflare Workers allow, and about a sixth of the 600,000 that OWASP recommends. Each sign-up, sign-in, or password change also takes about 10–40 ms of CPU time. The Workers Free plan allows 10 ms per request, so an app that signs people in may need Workers Paid. Each digest records its iteration count, so a later default can raise it without breaking the passwords you’ve stored. For a stronger hash, [plug in your own](#choosing-the-hash).
:::

## At a glance

| To                                     | Write                                                                   |
| -------------------------------------- | ----------------------------------------------------------------------- |
| keep a password as its digest          | `password: { securePassword: true }`, with a `password_digest` column   |
| check a record’s password              | `await user.authenticate(password)`: the record, or `false`             |
| find a record and check its password   | `await User.authenticateBy({ email, password })`: the record, or `null` |
| confirm a new password                 | `User.create({ password, passwordConfirmation })`                       |
| ask for the current password to change | `user.update({ password, passwordChallenge })`                          |
| hash with your own algorithm           | `password: { securePassword: { algorithm: bcryptPassword } }`           |
| give each new record a random token    | `authToken: { secureToken: true }`                                      |
| save a new token                       | `await user.regenerateAuthToken()`                                      |
| make a token yourself                  | `generateSecureToken(32)`                                               |

## Storing passwords

Declare `password: { securePassword: true }` in `static attributes`, as `User` does, and give the table a `password_digest` column. A sign-up form can then send the password and its confirmation:

<include>/_excerpts/pages/passwords-and-tokens/examples/sign-up.mdx</include>

- **It adds three virtual attributes:** `password`, `passwordConfirmation`, and `passwordChallenge`. None of them is saved.
- **The password is hashed when the record is saved.** Until then, `passwordDigest` keeps its old value:

<include>/_excerpts/pages/passwords-and-tokens/examples/digest.mdx</include>

- **Assigning `null` clears the digest.** Assigning `""` is ignored, so a blank field in a form leaves the password as it was.
- **Responses never send them.** `toJSON()` leaves out the password, its confirmation, its challenge, and its digest, as it does a secure token, without listing them in [`hiddenAttributes`](./serialization#hiding-attributes). `attributes()` still has them.
- **Logs never show them.** `onQuery` listeners, error messages, and printed records show the password, its confirmation, its challenge, and its digest as `[FILTERED]`, whatever [`filterAttributes`](./serialization#filtering-attributes) says. A secure token is filtered the same way.
- **Another name works the same way.** `recoveryPassword: { securePassword: true }` keeps its digest in `recovery_password_digest`, and checks it with `authenticateRecoveryPassword`.

:::note
Without a string digest column, the Model throws `InvalidModel`, and `active-record schema` reports it. Declaring `passwordConfirmation` or `passwordChallenge` yourself throws `InvalidModel` too.
:::

## Checking a password

Call `authenticate` with a password to check it against the record’s digest:

<include>/_excerpts/pages/passwords-and-tokens/examples/authenticate.mdx</include>

- It resolves to the record, or `false` when the password isn’t the one, or the record has no digest.
- It checks the digest as it’s saved, so a password you’ve assigned since is checked once you save it.
- Each secure password gets its own method, named for it: `authenticatePassword`, `authenticateRecoveryPassword`. Only `password` gets `authenticate`.

## Signing in

Call `authenticateBy` with an email (or any other attributes) and a password to find a record and check its password in one step:

<include>/_excerpts/pages/passwords-and-tokens/examples/sign-in.mdx</include>

- **It resolves to the record, or `null`.** It’s `null` when no record matches, when the password is wrong, or when the password is blank.
- **It takes as long when no record matches.** It hashes the password anyway, as it does for a record with no digest. So how long a sign-in takes doesn’t tell anyone which emails have accounts.
- **Its other attributes find the record as `findBy` does.** Normalizations and default scopes apply.
- **It needs both.** Without a password, or without an attribute to find the record by, it throws `TypeError`.

## Confirming and challenging

A secure password adds these validations, unless it’s declared with `validations: false`:

| Fails when                                        | Error on               | Message                |
| ------------------------------------------------- | ---------------------- | ---------------------- |
| there’s no digest, and no new password to hash    | `password`             | can’t be blank         |
| `passwordChallenge` isn’t the current password    | `passwordChallenge`    | is invalid             |
| the password is longer than the algorithm allows  | `password`             | is too long            |
| `passwordConfirmation` is given and doesn’t match | `passwordConfirmation` | doesn’t match Password |

The default algorithm allows 72 bytes, counted in UTF-8. Set `passwordChallenge` to ask for the current password before a change:

<include>/_excerpts/pages/passwords-and-tokens/examples/challenge.mdx</include>

- The challenge is checked against the digest as it was last saved. A record with no saved digest fails any challenge.
- A `null` challenge or confirmation is skipped, so leave them out when you don’t ask for them.

## Choosing the hash

Give `securePassword` an `algorithm` to hash passwords your own way. An algorithm has `hash`, `verify`, and an optional `maxBytes`. This one uses bcrypt, from the `bcryptjs` package:

<include meta='title="src/bcrypt.ts"'>/_excerpts/pages/passwords-and-tokens/src/bcrypt.ts</include>

`Admin` declares it as its password’s algorithm, and its digests are bcrypt’s:

<include>/_excerpts/pages/passwords-and-tokens/examples/bcrypt.mdx</include>

- **`hash`** resolves to a salted digest of the password, and **`verify`** to whether a password is the one a digest was made from.
- **`maxBytes`** sets the `is too long` validation. Without it, a password can be any length.
- **Each digest belongs to its algorithm.** The default throws `TypeError` for a digest it didn’t make, so give an algorithm that reads the digests you already have. bcrypt reads those made by another app’s bcrypt.

:::warning[A stronger hash costs more CPU time]
bcrypt in JavaScript at a cost of 10 takes about 100 ms of CPU time for each hash, well past the Free plan’s 10 ms. On Workers Paid, a request gets 30 seconds of CPU time by default. `bcryptjs` imports Node’s `crypto`, so turn on the `nodejs_compat` compatibility flag in `wrangler.jsonc`.
:::

## Generating tokens

Declare `secureToken: true` on a string column, as `User` does with `authToken`, to give each new record a random token:

<include>/_excerpts/pages/passwords-and-tokens/examples/token.mdx</include>

- **It’s made as the record is built,** unless a value is given that isn’t `null` or `""`. With `on: "create"`, it’s made as the record is created instead. A bulk insert, such as `insertAll`, makes the first kind but not the second.
- **It’s 24 characters of base58:** letters and digits, without `0`, `O`, `I`, and `l`, which look alike. `length` makes it longer, and `prefix` puts text before it.
- **A record loaded from the database keeps the token it has,** even when it has none.
- **Nothing checks that a token is unique.** Two tokens matching is very unlikely, but give the column a UNIQUE index, as `users.auth_token` has.

`generateSecureToken(length)` makes a token the same way, for anything that isn’t an attribute.

:::note
A `length` under 24, a type other than `string`, or a `default` alongside it throws `InvalidModel`.
:::

## Regenerating tokens

Call `regenerateAuthToken()` to save a new token, so the old one stops working:

<include>/_excerpts/pages/passwords-and-tokens/examples/regenerate.mdx</include>

- It saves the new token as `update` does, validations and callbacks included, and resolves to `false` when the record is invalid.
- `regenerateAuthTokenOrThrow()` throws `RecordInvalid` instead.
- Each token gets its own pair, named for it: `inviteCode` gets `regenerateInviteCode()`.

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

Rails declares these with `has_secure_password` and `has_secure_token`. Here they go with the attributes, so their methods are typed from the same place. Rails hashes a password with bcrypt as it’s assigned; here PBKDF2 hashes it when the record is saved, since Workers have no bcrypt of their own and hashing is asynchronous. `authenticate_by`, `password_challenge`, `regenerate_<attribute>` and base58 tokens work as in Rails. Rails’ `regenerate_token` raises on an invalid record; here `regenerateAuthToken()` resolves to `false`, and its `OrThrow` throws. Rails filters a password only when `filter_parameters` names it, and sends `password_digest` and a token in `as_json`; here a secure password, its digest, and a secure token are always filtered, and `toJSON()` leaves them out. Rails’ password reset tokens aren’t here yet ([#517](https://github.com/forestfuture/active-record/issues/517)).

</Callout>
