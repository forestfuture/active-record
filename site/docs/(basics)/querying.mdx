## Building a Relation

A query is a **Relation**. Each method that narrows, orders, or pages it returns a new Relation, and nothing runs until you ask for results:

<include>/_excerpts/guide/querying/relation.ts</include>

:::note
Relations have no `then`, so an `async` function that returns one never runs it by accident. Ask for results with a method such as `toArray()`, `first()`, or `count()`.
:::

## Starting a query

Every Relation method is also a static of every Model: `User.where(…)`, `User.find(id)`, `User.count()`, `User.create(…)`. `User.all()` is the Relation itself, and scopes are statics too: `User.active()`.

A query runs on the current database: the request’s, if it was opened with `withDatabase`, or the Model’s binding. To use another, start from `db.model(User)`. See [Connections](./connecting).

## Adding conditions

Narrow a query with `where`, `whereNot`, `or`, comparisons such as `gte` and `between`, and `sql` fragments. Replace them with `rewhere`, drop parts with `unscope`, and leave records out with `excluding`. See [Conditions](./conditions).

## Using raw statements

Bind what `serialize` gives when you send SQL to D1 yourself. `typeForAttribute` returns an attribute’s conversions:

<include>/_excerpts/guide/raw-statements/bind.ts</include>

`serialize` writes the `Date` as `paidAt` stores it: an integer here, ISO text for a plain `datetime`.

Turn a cell from a raw query into the attribute’s value with `deserialize`:

<include>/_excerpts/guide/raw-statements/read.ts</include>

For a cache key, or the value a test expects of a raw row, `serialize` gives the stored form too.

`cast` gives the JavaScript value for an input, without converting it to the stored form: `cast("2026-01-02")` is a `Date`. It keeps a `Date`’s milliseconds, where `serialize` floors them for `unixSeconds`.

- **`serialize` and `cast`** take what assigning would: a `Date` or an ISO string for a `datetime`, `"42"` for an `integer`. Anything else throws `TypeError` naming the Model and attribute, and so does `undefined`. Use `null` for NULL.
- **`deserialize`** reads a cell as loading a record does, and NULL and `undefined` are `null`. It throws the same `TypeError` for a cell that isn’t the attribute’s type. See [Fixing cells of the wrong type](./adopt-a-database#fixing-cells-of-the-wrong-type).
- **A filtered attribute’s value** is hidden in those errors, as it is anywhere else.

:::note
`typeForAttribute` needs no connection to D1, and the attribute’s name is checked when you compile.
:::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

`typeForAttribute` is `type_for_attribute`, with the same `cast`, `serialize`, and `deserialize`. Active Record’s are strict: a value the attribute can’t hold throws, where Rails casts it leniently.

</Callout>

## Getting results

Run a query with one of these methods:

<include>/_excerpts/guide/querying/terminal.ts</include>

- `find` throws `RecordNotFound` if the id is missing. Given several ids, it returns them in order, from one query, and throws if any are missing.
- `findBy` resolves to `null` when nothing matches, and `findByOrThrow` throws `RecordNotFound`.
- `findOrCreateBy` creates the record when nothing matches. See [Finding or creating a record](./persistence#finding-or-creating-a-record).
- `first` and `last` sort by the primary key unless the Relation has an order, and `last` reverses that order. An `sql` fragment can’t be reversed, so `last` throws `IrreversibleOrder` there.
- `firstOrThrow`, `lastOrThrow`, and `takeOrThrow` throw `RecordNotFound` instead of resolving to `null`.
- `sole` resolves to the only matching record. It throws `RecordNotFound` when nothing matches, and `SoleRecordExceeded` when more than one does. `findSoleBy(conditions)` is short for `where(conditions).sole()`.
- `pick` reads one attribute from the first record. Given several attributes, it reads a tuple. It resolves to `null` when nothing matches.
- `ids` plucks every primary key. On a loaded association, it leaves out records you’ve built that don’t have a key yet.
- `count()` always agrees with what `toArray()` returns, even with `limit`, `offset`, or `distinct`.
- `size()`, `isEmpty()`, and `hasAny()` count records, or check for any. On a loaded association, they answer without a query.
- `hasMoreThanOne()` and `hasExactlyOne()` count no further than two records. On a loaded association, they answer without a query too.

:::tip
`exists()`, `isEmpty()`, and `hasAny()` ignore the Relation’s order, so D1 stops at the first matching row. `count()` ignores it too, unless a `limit` or `offset` needs it. D1 bills each row it reads, so checks and counts stay cheap on an ordered Relation, such as an ordered association.
:::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

`size()`, `isEmpty()`, and `hasAny()` are Rails’ `size`, `empty?`, and `any?`, and `hasMoreThanOne()` and `hasExactlyOne()` are `many?` and `one?`. `firstOrThrow()` is `first!`, and `findSoleBy` is `find_sole_by`. There’s no `second` or `third`. Use `offset(1).first()` instead. Rails’ `ids` gives `nil` for a built record with no key, where `ids()` leaves it out.

</Callout>

## Selecting attributes

Load only some attributes with `select`. The primary key is always loaded too, so the records can still be saved:

<include>/_excerpts/guide/querying/select.ts</include>

- Reading an attribute that wasn’t loaded throws `MissingAttribute`, including from a validator or callback. `record.hasAttribute("email")` says whether it was loaded.
- Saving a partial record writes only what changed. `reload()` loads the whole row.
- After `distinct()`, the primary key isn’t added, since it would make every row distinct, so those records can’t be saved.

## Defining scopes

A scope is a named, reusable part of a query. Declare one as a static that receives the Relation, plus any arguments, and returns a narrower one:

<include>/_excerpts/guide/models/declare.ts</include>

Call it as a static, or on any Relation of the Model:

<include>/_excerpts/guide/models/scopes.ts</include>

- A scope’s arguments, and anything it computes such as `new Date()`, are evaluated when you call it.
- Scopes are inherited, including those on your app’s base class ([Shared behavior](./shared-behavior)). A subclass can replace one with `static override active = this.scope(…)`.
- A scope can’t reuse a Relation method’s name (`where`, `count`) or a Model static’s (`validates`, `scope`, `all`).
- Inside a scope, `q` has every Relation method but not the Model’s other scopes. Share logic between scopes with a plain function.

:::note
A scope whose body names its own class needs its type written out: `static roots: ScopeStatic<[]> = this.scope(…)`.
:::

An [enum](./models#declaring-enums) gives its Model a scope for each name, and a `not…` scope: `Ticket.open()` and `Ticket.notOpen()`. Conditions take its names, one or a list: `Ticket.where({ status: ["open", "in_progress"] })`.

## Defining a default scope

A default scope narrows every query on a Model. Declare one in the class’s `static {}` block:

<include>/_excerpts/guide/default-scopes/declare.ts</include>

Queries start from it, and new records take its conditions’ values:

<include>/_excerpts/guide/default-scopes/queries.ts</include>

- It applies to everything that queries the Model: `find`, `count`, `updateAll`, `deleteAll`, its scopes, and associations that read it, preloads included.
- `reload`, uniqueness validation, and a record’s own `save` and `destroy` ignore it, since they work by primary key.
- `insert`, `insertAll`, `upsert`, and `upsertAll` write its conditions’ values over the values you give. `build` and `create` use the values you give.
- Several default scopes all apply. A subclass adds its own to its parent’s.
- An order in a default scope is the Relation’s order. `reorder` replaces it.
- `rewhere` replaces its condition on an attribute, and [`unscope`](./conditions#replacing-conditions) drops its parts.

To leave the default scope out, start from `unscoped()`:

<include>/_excerpts/guide/default-scopes/unscoped.ts</include>

`unscoped()` is a Model static only. With a database you hold, call it inside [`withDatabase`](./connecting#using-the-requests-database).

:::warning[Default scopes hide records from associations too]
A default scope that hides soft-deleted records also hides them from every association. A comment on a deleted post then fails to save with “Post must exist”. And `dependent: "destroy"` leaves a deleted post’s comments behind. An upsert that updates a deleted post writes `deletedAt: null`, which brings the post back. It does this even when you pass a `deletedAt`. For soft deletes, use a named scope instead:

```ts
class Post extends ApplicationRecord {
  static kept = this.scope((q) => q.where({ deletedAt: null }));
}
```

Then call `Post.kept()` where deleted posts should stay hidden.
:::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

`this.defaultScope` is Rails’ `default_scope`, applied the same way. `unscoped()` is only a static: Rails also has it on a Relation, where `Post.where(…).unscoped` drops every condition, the Relation’s own included. Rails’ block form, `Post.unscoped { … }`, and `all_queries: true` aren’t here.

</Callout>

## Merging Relations

Combine two Relations of the same Model with `merge`. Their conditions are joined with AND, and anything the argument sets, such as an order, limit, or select, replaces the receiver’s:

```ts
const recent = User.order({ createdAt: "desc" }).limit(10);
const admins = await User.where({ role: "admin" }).merge(recent).toArray();
```

To merge a Relation of another Model, join that Model first. See [Joining associations](#joining-associations).

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

Rails adds the argument’s order to the receiver’s. Active Record replaces it.

</Callout>

## Joining associations

`joins` finds the records that have a linked record, through the associations you’ve declared. Name an association, or nest them in an object:

<include>/_excerpts/guide/joins/joins.ts</include>

A record comes back once for each linked record, so an author with three commented articles appears three times. Add `distinct()` to get each record once.

A joined query loads only its own Model’s columns, and every Relation method works on it. `count()` counts the rows `toArray()` returns, and `updateAll` and `deleteAll` write the records the join finds.

The association’s `scope` and the joined Model’s default scope are part of the join. So joining an association scoped to published articles finds only authors with a published article.

`leftJoins` joins the same way, but keeps the records that have no linked record:

### Filtering by a joined Model

Merge a Relation of the joined Model to filter or sort by its attributes:

<include>/_excerpts/guide/joins/merge.ts</include>

Its conditions, its scopes, and its order apply to the joined table. As with any `merge`, the joined Model’s order replaces the receiver’s.

:::note
The merged Relation can only add conditions and an order. A `limit`, `offset`, `select`, `distinct()`, `includes`, or `joins` of its own throws `IncompatibleRelation`. Merging a Model the query doesn’t join, or joins more than once, throws it too. So does `distinct()` on a query ordered by a joined Model.
:::

:::note
A join reads one database. Joining an association to a Model on another database throws `IncompatibleRelation` when you write the query.
:::

:::note
A polymorphic `belongsTo` can’t be joined, because its records may be in several tables. Joining one throws `IncompatibleRelation`. Join the `as:` association of each Model instead, such as `Photo.joins("likes")`.
:::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

- Rails builds the SQL for a merged Model the query doesn’t join, and the database rejects it when the query runs. Active Record throws `IncompatibleRelation` when you write it.
- Rails applies a merged Relation’s `limit` to the whole query. Active Record refuses it.
- Rails leaves `distinct` with an order on a joined table to the database, which Postgres refuses and SQLite runs. Active Record throws `IncompatibleRelation` on both.
- With a `hasMany` join, Rails’ `find(1, 2)` counts the duplicate rows and raises `RecordNotFound`. Active Record returns each record once.
- With a `hasMany` join, Rails’ `destroy_all` destroys a record once for each of its rows, running its callbacks each time. Active Record destroys each record once.
- Rails’ `where(author: { name: "Mary" })`, `where.missing`, `eager_load`, and joins through another association aren’t here yet. Joining a `through` association throws `IncompatibleRelation`. Merge a Relation of the joined Model instead, and preload with `includes`.

</Callout>
