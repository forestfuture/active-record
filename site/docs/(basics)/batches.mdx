Bulk writes change many rows in one SQL statement. A batch sends several writes to D1 at once, and they’re all written, or none of them.

## Writing many rows

Call a bulk write on a Relation. It runs straight away, without validations or callbacks:

<include>/_excerpts/guide/batches/statements.ts</include>

- **`updateAll(changes)`** takes attributes or an `sql` fragment, and resolves to the number of rows updated. It leaves `updatedAt` alone. With a `limit` or `offset`, the Relation’s order picks which rows are written.
- **`deleteAll()`** resolves to the number of rows deleted. On `none()`, both send nothing and resolve to `0`.
- **`insert(attrs)`** writes one row. It resolves to `{ rowsAffected, rows }`, and `rows` holds the new row’s primary key. Declared defaults, timestamps, and a Relation’s equality conditions fill what isn’t given.

### Inserting many rows

Insert many rows in one statement with `insertAll`:

<include>/_excerpts/guide/batches/insert-all.ts</include>

- **`insertAll(rows)`** inserts every row, however many, up to D1’s 2 MB per bound value. Every row must have the same attributes. A duplicate throws and writes nothing.
- **`{ onDuplicate: "skip" }`** skips rows that clash with a unique index.
- **`upsert(attrs)`** and **`upsertAll(rows)`** update a row that clashes with the primary key, or with the unique index named by `uniqueBy`. Only the attributes you give are updated, and `updatedAt` is set.

### Returning attributes

Inserts and upserts return the primary key of each row they write. Name other attributes with `returning`:

<include>/_excerpts/guide/batches/returning.ts</include>

- **`rows`** has one entry for each row written, typed from the attributes you name. A row skipped as a duplicate isn’t in it.
- **`returning: false`** returns no rows.
- **Order:** the rows come back in no set order.

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

These are Rails’ `insert_all`, `upsert_all`, `update_all`, and `delete_all`, with two differences. Declared defaults fill what an insert isn’t given, since on D1 defaults are where keys are generated. And skipping duplicates is something you opt in to, so a duplicate is never silently lost. The `returning` option works as Rails’ does.

</Callout>

## Batching writes

Prepare several writes in `batch`’s callback to write them atomically:

<include>/_excerpts/guide/batches/batch.ts</include>

The callback gets `b`, with a method for each bulk write: `insert`, `insertAll`, `upsert`, `upsertAll`, `updateAll`, and `deleteAll`. Each takes what it writes to, then the same arguments as the write itself. Pass a Model to write to its table, or a Relation to write to its rows, such as `Article.where(…)` or `author.articles()`.

`batch` resolves to each write’s result, in order. A bulk write gives the same `{ rowsAffected, rows }` it resolves to when it runs alone, and `rows` is empty for `updateAll` and `deleteAll`.

- **Keys:** rows in one batch can only point at each other through keys that exist before it’s sent, so generate keys in code, with [`generateId`](./models#generating-ids).
- **Errors:** a write that can’t be prepared, such as one with an unknown attribute, rejects the batch before anything is sent.
- **Databases:** `batch` writes a Model’s rows on the current database, and `db.batch` on `db`. A Relation or a record writes on the database it came from. Writes on two databases throw `IncompatibleRelation`.
- **Relations in `db.batch`:** `Article.where(…)` uses the current database. Build it with `db.model(Article).where(…)` to write on `db`.

:::note
The callback returns its writes without awaiting anything, since the batch is sent to D1 as one. Load what the writes need before you call `batch`. D1 can’t keep a transaction open across `await`s, so a batch is how you make writes atomic.
:::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

A batch reads like a `transaction do … end` block, but its callback only prepares writes. They’re sent together when it returns, so it can’t read in between.

</Callout>

## Batching records

Add a record’s save or destroy to a batch with `b.save(record)` and `b.destroy(record)`. Its validations and callbacks still run:

<include>/_excerpts/guide/batches/records.ts</include>

When the batch runs:

1. Each record, in order, is validated and runs its before-callbacks. The first that’s invalid or aborts throws `RecordInvalid`, `RecordNotSaved`, or `RecordNotDestroyed`, and nothing is sent.
2. Every write goes to D1 as one atomic batch. If D1 refuses it with a constraint error, nothing is written, every record keeps its unsaved state, and each record’s `afterRollback` runs.
3. Each record takes its saved state, then its after-callbacks run.
4. Every record’s [commit callbacks](./callbacks#running-code-after-the-commit) run, in the same order.

A record’s autosaved associations and `dependent` strategies join the same batch. A record listed twice, or already saved by its owner’s autosave, is written once.

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

In a Rails transaction, one record’s `after_save` runs before the next record’s `before_save`. In a batch, every before-callback runs first.

</Callout>
