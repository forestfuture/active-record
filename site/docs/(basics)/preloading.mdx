## At a glance

| To                                          | Write                                                                                |
| ------------------------------------------- | ------------------------------------------------------------------------------------ |
| preload an association                      | `Author.includes("profile")`                                                         |
| preload several                             | `Author.includes("profile", "articles")`                                             |
| preload nested associations                 | `includes({ articles: "comments" })`, `includes({ articles: ["comments", "tags"] })` |
| preload a polymorphic association           | `Like.includes("likeable")`                                                          |
| read a preloaded association, with no query | `author.loaded("profile")`                                                           |
| check whether it’s loaded                   | `author.isLoaded("profile")`                                                         |

## Preloading associations

Load an association for every record at once with `includes`, one query per association however many records there are:

<include>/_excerpts/pages/preloading/examples/preload.mdx</include>

- The example sends four queries, however many authors there are. On D1, the whole tree goes [in one round trip](./d1#sending-queries-in-one-round-trip) with the authors’ own query. On Postgres, the queries run one after another. An association to [another database](./several-databases#associating-models-on-different-databases) takes one more.
- `author.loaded("profile")` reads a preloaded association synchronously, and throws `AssociationNotLoaded` if it wasn’t loaded, so a template never sends a query. `author.isLoaded("profile")` checks first.
- With a `limit` or `offset`, `includes` ends the order with the primary key, so the preloads find the same records the query loads.

## Preloading polymorphic records

`includes` preloads a polymorphic association with one query for each listed Model:

<include>/_excerpts/pages/preloading/examples/polymorphic.mdx</include>

- Each query runs the likes’ query again to find their keys, even for a Model no like points at. Index what that query filters and sorts by.
- A nested include can name an association that only some listed Models have: `includes({ likeable: "album" })` loads the photos’ albums and skips the videos.

## Indexing what preloads read

Index each foreign key, as the migrations index `author_id` and `article_id`:

- `hasMany` and `hasOne` find their records by the foreign key, both with `includes` and when you read one record’s association, such as `author.articles()`. Without an index, D1 reads every row of the table for each lookup, and bills you for each row it reads.
- A `references` column from the [generators](./generators) is indexed already.
- `includes` also runs the query’s own conditions again for each association it preloads, and with a `limit` or `offset`, its order. Index the columns the query filters and sorts by, too.

<Callout type="info" title="Beyond Rails" icon="/ruby.svg">

Rails sends each association’s preload query on its own, so every association adds a round trip. On D1, the whole tree on one database takes one. Rails preloads a polymorphic association after the likes load, with one query per type it finds. Here every listed Model’s query goes with the likes’ own, in one round trip, at the cost of reading the likes’ query again for each.

</Callout>
