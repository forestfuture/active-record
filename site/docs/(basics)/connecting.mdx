A query finds its D1 database in one of three ways. Most apps only use the first.

|                            | How                                                      | Use it for                                                                      |
| -------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------- |
| **The binding**            | `User.find(id)`, with nothing to set up                  | Everyday queries                                                                |
| **The request’s database** | `withDatabase(connect(env.DB, …), fn)`, once per request | Read replicas with a Session, per-request `onQuery` logging, tests, and scripts |
| **An explicit database**   | `connect(env.DB).model(User).find(id)`                   | Code that passes its database around, or uses two at once                       |

[Database resolution](./query-databases) explains why there are three, and [which one you need](./query-databases#which-do-i-need).

## Using the binding

Each Model names the D1 binding it queries, so a Model queries by itself during any request:

<include>/_excerpts/guide/connecting/binding.ts</include>

`active-record schema` writes the binding into the generated schema your app’s base class holds, from your Wrangler config’s `d1_databases`.

Records remember their database, so `user.save()` and `user.posts()` use the same one later. Build records with `User.build(…)`: a record made with `new User()` has no database, and throws `NoDatabase` when it needs one.

:::note
The binding is only there during a request, inside a Worker. Tests and scripts that run in Node get their database from `withDatabase`. See [Testing](./testing).
:::

## Using the request’s database

Some things belong to one request, such as a D1 Session that reads its own writes, or logging tagged with the request’s ID. Open a database for the request, and run its code inside `withDatabase`:

```ts
import { withDatabase } from "@forestfuture/active-record";
import { connect } from "@forestfuture/d1-record";

export default {
  fetch(request, env) {
    const db = connect(env.DB, { onQuery: log });
    return withDatabase(db, () => app.fetch(request, env));
  },
};
```

Every query started from a Model inside it, and everything it awaits, uses that database instead of the binding.

:::warning[Node.js compatibility]
`withDatabase` uses Workers’ `AsyncLocalStorage`. It’s on by default for compatibility dates from 2026-08-04. For an earlier date, add `"compatibility_flags": ["nodejs_compat"]` to your Wrangler config, or `withDatabase` throws `NoDatabase`. The rest of d1-record doesn’t need it.
:::

These pages use a request’s database:

- **[Read replicas](./read-your-own-writes):** a D1 Session per request.
- **[Logging](./logging):** one request’s queries, tagged with its ID.
- **[Testing](./testing):** a database for Models outside a Worker.
- **[Multiple databases](./several-databases):** `withDatabase([...])`, matched to each Model’s binding.

## Connecting to Postgres

:::note
`@forestfuture/pg-record` isn’t on npm yet. It’s released once the `active-record` command can generate its schema and apply its migrations.
:::

On Postgres, `connect` takes a Hyperdrive binding, a connection string, or a `pg` Pool. Open the request’s database from your Hyperdrive binding:

```ts
import { withDatabase } from "@forestfuture/active-record";
import { connect } from "@forestfuture/pg-record";

export default {
  fetch(request, env) {
    const db = connect(env.HYPERDRIVE);
    return withDatabase(db, () => app.fetch(request, env));
  },
};
```

The first query inside `withDatabase` opens a client, and the rest of the request shares it. It closes when `withDatabase` finishes. Each `withDatabase` call gets its own client, so a Database your Worker opens once can serve every request. Without `withDatabase`, each query opens a client of its own and closes it when it’s done. So does work that outlives the request, such as a save in `ctx.waitUntil`.

Your schema names the binding with `adapter: pg({ binding: "HYPERDRIVE" })`. So `User.find(id)` works in a Worker with nothing to set up.

`connect(env.DATABASE_URL)` takes a connection string the same way.

:::tip
On Workers, use Hyperdrive. It pools connections, so a new client doesn’t mean a new connection to Postgres.
:::

On Node, pass your own Pool, which your app ends when it shuts down:

```ts
import pg from "pg";
import { connect } from "@forestfuture/pg-record";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
const db = connect(pool);
```

Outside a Worker there’s no binding, so wrap each request in `withDatabase(db, …)` for your Models’ statics.

Opening a client from a binding or a connection string waits up to 10 seconds for Postgres to answer. After that, the query fails with `Error: timeout expired`. Each query waiting for that client tries again, and can wait as long. To change the limit, set `connect_timeout` to a number of seconds:

```ts
import { connect } from "@forestfuture/pg-record";

const db = connect("postgres://app@db.example.com/app?connect_timeout=5");
```

If you want no limit, set `connect_timeout=0`.

:::note
A Hyperdrive binding’s connection string isn’t yours to change, so it always waits up to 10 seconds. A Pool uses its own `connectionTimeoutMillis`.
:::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

Rails sets no limit, so opening a connection waits as long as it takes unless you set `connect_timeout`. Here the limit is 10 seconds unless you set one.

</Callout>

[Postgres’s differences](./postgres) lists what works differently from D1.
