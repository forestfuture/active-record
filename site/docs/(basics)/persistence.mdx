## At a glance

| To                                         | Write                                                     |
| ------------------------------------------ | --------------------------------------------------------- |
| save a record, true or false               | `user.save()`, `User.create({ … })`, `user.update({ … })` |
| throw when it can’t be saved               | `saveOrThrow()`, `createOrThrow()`, `updateOrThrow()`     |
| change one attribute in memory             | `increment("viewCount")`, `toggle("isPinned")`            |
| write straight to the row                  | `incrementColumn(…)`, `updateColumns({ … })`              |
| set `updatedAt` without saving             | `touch()`                                                 |
| add to a number without loading the record | `Article.updateCounters(id, { viewCount: 1 })`            |
| find a record, or create one               | `findOrCreateBy({ … })`, `createOrFindBy({ … })`          |
| destroy a record, or many                  | `destroy()`, `destroyAll()`, `destroyBy({ … })`           |
| load a record’s row again                  | `reload()`                                                |

## Saving records

Save a record with `save`. It validates the record, runs its callbacks, and resolves to `true` or `false`:

<include>/_excerpts/pages/persistence/examples/save.mdx</include>

A new record is inserted, and a persisted one updates only the attributes that changed. `save` resolves to `false` for one of two reasons:

- **Validation failed.** The reasons are in `record.errors`.
- **A callback aborted** with [`abort()`](./callbacks#stopping-a-save). The reason is in `record.abortReason`.

`create(attrs)` builds and saves a record, and resolves to it whether it saved or not. Check `isPersisted()` or `errors`. `update(attrs)` assigns, then saves.

## Throwing on failure

When a failure is exceptional, use the `OrThrow` version of each method:

<include>/_excerpts/pages/persistence/examples/or-throw.mdx</include>

Instead of returning `false`, they throw:

- `RecordInvalid` when validation failed, with the record on `error.record`.
- `RecordNotSaved` when a callback aborted a save, with the abort’s reason as its message.
- `RecordNotDestroyed` from `destroyOrThrow()`, when a callback aborted the destroy or a `restrictWithError` association refused it.

### What each method returns

| Method                                   | Resolves to                           | Throws                                                            |
| ---------------------------------------- | ------------------------------------- | ----------------------------------------------------------------- |
| `save()` / `update(attrs)`               | `true` / `false`                      | constraint errors, `RecordDestroyed`                              |
| `saveOrThrow()` / `updateOrThrow(attrs)` | `true`                                | same as above, plus `RecordInvalid`, `RecordNotSaved`             |
| `create(attrs)`                          | record, persisted or not              | constraint errors                                                 |
| `createOrThrow(attrs)`                   | persisted record                      | same as above, plus `RecordInvalid`, `RecordNotSaved`             |
| `destroy()`                              | destroyed record, or `false` on abort | constraint errors, `RecordDestroyed`                              |
| `destroyOrThrow()`                       | destroyed record                      | same as above, plus `RecordNotDestroyed`                          |
| `find(id)`                               | record                                | `RecordNotFound`                                                  |
| `findBy(conds)`                          | record or `null`                      | none                                                              |
| `findByOrThrow(conds)`                   | record                                | `RecordNotFound`                                                  |
| `findOrCreateBy(attrs)`                  | record, persisted or not              | constraint errors                                                 |
| `createOrFindBy(attrs)`                  | record, persisted or not              | constraint errors but its own `RecordNotUnique`, `RecordNotFound` |

`false` only ever means validation failed or a callback aborted. Every method throws for anything else:

- **Constraint errors**, such as `RecordNotUnique`, since the database refused the write. See [Errors](./errors#constraint-errors).
- **An error thrown by a callback**, other than `abort()`, even from an after-callback once the record is saved.
- **The database’s own errors.**

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

A TypeScript method name can’t contain `!`, so the `OrThrow` suffix takes its place. `saveOrThrow`, `createOrThrow`, `updateOrThrow`, and `destroyOrThrow` are Rails’ `save!`, `create!`, `update!`, and `destroy!`.

</Callout>

## Changing one attribute

To bump a number or flip a flag, use `increment`, `decrement`, or `toggle`. They change the record without saving it, so save it afterwards:

<include>/_excerpts/pages/persistence/examples/in-memory.mdx</include>

`increment` and `decrement` take an amount as their second argument, and count `null` as zero. `toggle` turns `null` into `true`.

### Writing straight to the row

To write a value without validations, callbacks, or a new `updatedAt`, use a method ending in `Column`. Each one writes to the row at once:

<include>/_excerpts/pages/persistence/examples/columns.mdx</include>

- **`incrementColumn` and `decrementColumn`** add to the value in the row, not the one the record loaded. When two requests increment the same row, both count. The record then holds the row’s new value. To set `updatedAt` in the same write, pass `{ touch: true }` after the amount.
- **`toggleColumn`** writes the flipped value.
- **`updateColumns(attrs)`** writes the attributes you give. `updateColumn(name, value)` writes one.

Each resolves to `true`, or `false` when the row is gone. The record’s other unsaved changes stay unsaved. A record that was never saved has no row, so these methods throw `RecordNotSaved`.

### Touching a record

To mark a record as changed without saving it, call `touch`. It sets `updatedAt` to the current time in the row:

<include>/_excerpts/pages/persistence/examples/touching.mdx</include>

- **Name datetime attributes** to set them as well as `updatedAt`.
- **Pass `{ time }` last** to set a time other than now.
- **A Relation’s `touchAll`** sets them in every row it matches, in one statement. Like `updateAll`, it keeps the default scope and runs no callbacks.

`touch` skips validations and the save callbacks, and the record’s other unsaved changes stay unsaved. It runs `afterTouch`, then the commit callbacks for an update. See [Running code after a touch](./callbacks#running-code-after-a-touch).

`touch` resolves to `true`, or `false` when the row is gone. A record that was never saved throws `RecordNotSaved`. On a Model with no `updatedAt`, name at least one attribute. Inside a [`noTouching` block](./touching#turning-touches-off) for its Model, `touch` writes nothing and resolves to `false`.

To touch the record a record belongs to whenever it changes, declare `touch` on its `belongsTo`. See [Touching the record it belongs to](./touching#touching-the-record-it-belongs-to).

### Updating counters

To add to a number without loading the record, pass its primary key to `updateCounters`:

<include>/_excerpts/pages/persistence/examples/counters.mdx</include>

- **`Article.updateCounters(ids, counters)`** adds to the rows with those keys, even ones a default scope leaves out.
- **A Relation’s `updateCounters(counters)`** adds to every row it matches.
- **`incrementCounter` and `decrementCounter`** change one attribute by one, or by the amount in `{ by: 5 }`.

Each one sends a single statement and resolves to the number of rows it changed. Like `updateAll`, it skips validations and callbacks. To set `updatedAt` too, pass `{ touch: true }`. To set other datetime attributes as well, name them, as in `{ touch: "viewedAt" }`.

To keep a count of an association’s records, see [counter caches](./counter-caches).

:::warning[Counting by key skips the default scope]
`Article.updateCounters`, `incrementCounter`, and `decrementCounter` find rows by primary key alone. If a default scope keeps tenants apart or hides deleted rows, a key from a request can reach a row it hides. Start from a Relation instead, which keeps the default scope:

<include>/_excerpts/pages/persistence/examples/scoped-counter.mdx</include>

:::

:::note
`increment` and the counters take `integer` and `real` attributes. A `decimal` is stored as text, so they refuse it.
:::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

`incrementColumn`, `decrementColumn`, and `toggleColumn` are Rails’ `increment!`, `decrement!`, and `toggle!`. A method name can’t contain `!`, and the `OrThrow` suffix means something else, so the `Column` ending names what they do: write to the row now, as `updateColumns` does.

Rails’ `toggle!` runs the save callbacks and saves the record’s other changes. `toggleColumn` runs no callbacks and writes only the one attribute. For callbacks, call `toggle`, then `save`.

Rails’ `increment!` keeps the value it worked out. `incrementColumn` reads the row’s new value back, so it includes other requests’ increments.

`touch` and `touchAll` are Rails’ `touch` and `touch_all`. Rails writes the time to any column you name, and touching a Model with no `updated_at` does nothing. Here, an attribute that isn’t a datetime, or nothing to touch, throws a `TypeError`.

</Callout>

## Finding or creating a record

Find a record by its attributes, or create one with them when there isn’t one, with `findOrCreateBy`:

<include>/_excerpts/pages/persistence/examples/find-or-create.mdx</include>

`findOrCreateBy` creates the record as `create` does, so check `isPersisted()` or `errors` if it might not save. `findOrCreateByOrThrow` throws `RecordInvalid` instead. `findOrInitializeBy` builds the record without saving it.

They work on any Relation. A scope’s or an association’s conditions become the new record’s attributes too, so `user.posts().findOrCreateBy({ title })` finds or creates one of the user’s posts.

The attributes you pass become the new record’s values, so each must be one value. A list, a comparison such as `gte(18)`, or a `sql` fragment throws a `TypeError` before anything is sent. An array that an attribute holds as its value, such as a `json` attribute’s, is one value. These methods find the record that holds it.

### Giving new records more attributes

To give a new record attributes that aren’t part of the search, use `createWith`:

<include>/_excerpts/pages/persistence/examples/create-with.mdx</include>

The Relation’s `build`, `create`, and `insert` use them too. Attributes you pass to `build` and `create` win over them. `insert`, `insertAll`, `upsert`, and `upsertAll` write them over the attributes you pass. `createWith(null)` removes them.

To set attributes in code, pass a function as the last argument. It gets the new record once its attributes are assigned, before it’s saved:

<include>/_excerpts/pages/persistence/examples/init.mdx</include>

The function runs only when a record is made. `build`, `create`, and `createOrThrow` take one too. Each method awaits it, except `build`, which returns the record at once. An async function given to `build` throws a `TypeError`.

### Creating records from concurrent requests

Two requests can both find nothing, and both create a record. When a UNIQUE index covers the attributes, use `createOrFindBy` instead. It inserts first, and finds the existing row when the index refuses the duplicate:

<include>/_excerpts/pages/persistence/examples/create-or-find.mdx</include>

`createOrFindByOrThrow` throws `RecordInvalid` when the record is invalid.

:::warning[Let the index decide]
`createOrFindBy` only finds the existing row when the database refuses the insert:

- **Leave out a `uniqueness` validation on those attributes.** It refuses the duplicate before the insert, so `createOrFindBy` resolves to the invalid record, not the existing one. The UNIQUE index alone keeps the column unique.
- **Save the record alone.** When `init` builds or sets records through its associations, a refusal may be theirs, so `createOrFindBy` throws the `RecordNotUnique` instead of finding.
- **It throws `RecordNotFound` when there’s nothing to find:** when the index refused a value in an attribute you didn’t pass, when the existing row isn’t linked to the owner of an [association through another](./through-associations), or when a [D1 Session](./read-your-own-writes) reads from a replica that the other request’s row hasn’t reached yet.

:::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

`findOrCreateBy`, `findOrInitializeBy`, `createOrFindBy`, and `createWith` are Rails’ `find_or_create_by`, `find_or_initialize_by`, `create_or_find_by`, and `create_with`, and the `OrThrow` versions are the `!` ones. The function passed last takes the place of Rails’ block.

Rails reads a list in their attributes as `IN`, as `find_by` does. These methods refuse one instead, as [Untrusted input](./untrusted-input#querying-with-request-values) explains.

</Callout>

## Destroying records

Destroy a record with `destroy`:

<include>/_excerpts/pages/persistence/examples/destroy.mdx</include>

It runs the destroy callbacks and the associations’ [`dependent` options](./associations#destroying-dependent-records), then deletes the row. A destroyed record’s attributes stay readable, but setting one, or calling `save`, `update`, `destroy`, or `reload`, throws `RecordDestroyed`.

:::note
If another request already deleted the row, `save` and `destroy` still succeed.
:::

### Destroying many records

Destroy every record a query matches with `destroyAll`:

<include>/_excerpts/pages/persistence/examples/destroy-many.mdx</include>

- **`destroyAll()`** loads the records, runs each one’s destroy callbacks and `dependent` options, and deletes them all in one write. It resolves to the destroyed records.
- **`destroyBy(conditions)`** is `where(conditions).destroyAll()`.
- **`Post.destroy(id)`** finds the record by its primary key and destroys it. Given an array of keys, it destroys those records in one write. It throws `RecordNotFound` if a key has no record, before destroying any.

When one record can’t be destroyed, nothing is. A callback that aborts and a `restrictWithError` association both stop the whole write with `RecordNotDestroyed`.

To delete rows without loading them or running callbacks, use `deleteAll`, `deleteBy`, or `Post.delete(ids)`. See [Bulk writes and batches](./batches).

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

Rails’ `destroy_all` on a Relation destroys each record in a transaction of its own, skips a record whose callback aborts, and returns every record. Here the records are destroyed in one write, and one refusal stops them all, as Rails’ `destroy_all` on an association does.

</Callout>

### Destroying a large set

`destroyAll` holds every record it matches in memory, and writes them together. To destroy a large set in smaller writes, destroy it [a batch at a time](./batch-iteration#writing-a-batch-at-a-time):

<include>/_excerpts/pages/persistence/examples/destroy-in-batches.mdx</include>

Each batch is its own write, so a batch that fails leaves the earlier batches destroyed.

:::note
A batch bounds memory, not queries. Each record reads its `"destroy"` and restricted associations with a query of its own, so a large set sends as many reads, a batch at a time or not. On D1, that counts toward [the queries one Worker invocation can send](./batch-iteration#staying-within-d1s-query-limit).
:::

## Checking a record’s state

| State                                            | `isNewRecord()` | `isPersisted()` | `isDestroyed()` |
| ------------------------------------------------ | --------------- | --------------- | --------------- |
| New (from `build()`, or after a failed `create`) | `true`          | `false`         | `false`         |
| Persisted (loaded, or after a successful save)   | `false`         | `true`          | `false`         |
| Destroyed (after a successful `destroy()`)       | `false`         | `false`         | `true`          |

`isPreviouslyNewRecord()` says whether the last save created the record. `Article` uses it in an after-callback that runs only for new records:

<include>/_excerpts/pages/persistence/examples/previously-new.mdx</include>

It’s `false` again once the record is saved again or destroyed.

## Reloading records

Load a record’s row again with `reload`, which discards unsaved changes and loaded associations:

<include>/_excerpts/pages/persistence/examples/reload.mdx</include>

## Writing many rows

To insert, update, or delete many rows at once, without validations and callbacks, use `insertAll`, `upsertAll`, `updateAll`, `deleteAll`, and `deleteBy`. See [Bulk writes and batches](./batches).
