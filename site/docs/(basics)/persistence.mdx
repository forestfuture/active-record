Records are saved, updated, and destroyed with `save`, `create`, `update`, and `destroy`.

## Saving records

Save a record with `save`. It validates the record, runs its callbacks, and resolves to `true` or `false`:

<include>/_excerpts/guide/persistence/save.ts</include>

A new record is inserted, and a persisted one updates only the attributes that changed. `save` resolves to `false` for one of two reasons:

- **Validation failed.** The reasons are in `record.errors`.
- **A callback aborted** with [`abort()`](./callbacks#stopping-a-save). The reason is in `record.abortReason`.

`create(attrs)` builds and saves a record, and resolves to it whether it saved or not. Check `isPersisted()` or `errors`. `update(attrs)` assigns, then saves.

## Throwing on failure

When a failure is exceptional, use the `OrThrow` version of each method:

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

A TypeScript method name can’t contain `!`, so the `OrThrow` suffix takes its place. `saveOrThrow`, `createOrThrow`, `updateOrThrow`, and `destroyOrThrow` are Rails’ `save!`, `create!`, `update!`, and `destroy!`.

</Callout>

<include>/_excerpts/guide/persistence/or-throw.ts</include>

Instead of returning `false`, they throw:

- `RecordInvalid` when validation failed, with the record on `error.record`.
- `RecordNotSaved` when a callback aborted a save, with the abort’s reason as its message.
- `RecordNotDestroyed` from `destroyOrThrow()`, when a callback aborted the destroy or a `restrictWithError` association refused it.

### What each method returns

| Method                                   | Resolves to                           | Throws                                                            |
| ---------------------------------------- | ------------------------------------- | ----------------------------------------------------------------- |
| `save()` / `update(attrs)`               | `true` / `false`                      | constraint errors, `RecordDestroyed`                              |
| `saveOrThrow()` / `updateOrThrow(attrs)` | `true`                                | same as above, plus `RecordInvalid`, `RecordNotSaved`             |
| `create(attrs)`                          | record, persisted or not              | constraint errors                                                 |
| `createOrThrow(attrs)`                   | persisted record                      | same as above, plus `RecordInvalid`, `RecordNotSaved`             |
| `destroy()`                              | destroyed record, or `false` on abort | constraint errors, `RecordDestroyed`                              |
| `destroyOrThrow()`                       | destroyed record                      | same as above, plus `RecordNotDestroyed`                          |
| `find(id)`                               | record                                | `RecordNotFound`                                                  |
| `findBy(conds)`                          | record or `null`                      | none                                                              |
| `findByOrThrow(conds)`                   | record                                | `RecordNotFound`                                                  |
| `findOrCreateBy(attrs)`                  | record, persisted or not              | constraint errors                                                 |
| `createOrFindBy(attrs)`                  | record, persisted or not              | constraint errors but its own `RecordNotUnique`, `RecordNotFound` |

`false` only ever means validation failed or a callback aborted. Every method throws for anything else:

- **Constraint errors**, such as `RecordNotUnique`, since the database refused the write. See [Errors](./errors#constraint-errors).
- **An error thrown by a callback**, other than `abort()`, even from an after-callback once the record is saved.
- **D1’s own errors.**

## Finding or creating a record

Find a record by its attributes, or create one with them when there isn’t one, with `findOrCreateBy`:

<include>/_excerpts/guide/find-or-create/find-or-create.ts</include>

`findOrCreateBy` creates the record as `create` does, so check `isPersisted()` or `errors` if it might not save. `findOrCreateByOrThrow` throws `RecordInvalid` instead. `findOrInitializeBy` builds the record without saving it.

They work on any Relation. A scope’s or an association’s conditions become the new record’s attributes too, so `user.posts().findOrCreateBy({ title })` finds or creates one of the user’s posts.

### Giving new records more attributes

To give a new record attributes that aren’t part of the search, use `createWith`:

<include>/_excerpts/guide/find-or-create/create-with.ts</include>

The Relation’s `build`, `create`, and `insert` use them too. Attributes you pass to those methods win over them, and `createWith(null)` removes them.

To set attributes in code, pass a function as the last argument. It gets the new record once its attributes are assigned, before it’s saved:

<include>/_excerpts/guide/find-or-create/init.ts</include>

The function runs only when a record is made. `build`, `create`, and `createOrThrow` take one too. Each method awaits it, except `build`, which saves nothing and takes only a function that isn’t async.

### Creating records from concurrent requests

Two requests can both find nothing, and both create a record. When a UNIQUE index covers the attributes, use `createOrFindBy` instead. It inserts first, and finds the existing row when the index refuses the duplicate:

<include>/_excerpts/guide/find-or-create/create-or-find.ts</include>

`createOrFindByOrThrow` throws `RecordInvalid` when the record is invalid.

:::warning[Let the index decide]
`createOrFindBy` only finds the existing row when the database refuses the insert:

- **Leave out a `uniqueness` validation on those attributes.** It refuses the duplicate before the insert, so `createOrFindBy` resolves to the invalid record, not the existing one. The UNIQUE index alone keeps the column unique.
- **It throws `RecordNotFound` when there’s nothing to find:** when the index refused a value in an attribute you didn’t pass, or when a [D1 Session](./read-your-own-writes) reads from a replica that the other request’s row hasn’t reached yet.
  :::

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

`findOrCreateBy`, `findOrInitializeBy`, `createOrFindBy`, and `createWith` are Rails’ `find_or_create_by`, `find_or_initialize_by`, `create_or_find_by`, and `create_with`, and the `OrThrow` versions are the `!` ones. The function passed last takes the place of Rails’ block.

</Callout>

## Destroying records

Destroy a record with `destroy`:

<include>/_excerpts/guide/persistence/destroy.ts</include>

It runs the destroy callbacks and the associations’ [`dependent` options](./associations#destroying-dependent-records), then deletes the row. A destroyed record’s attributes stay readable, but setting one, or calling `save`, `update`, `destroy`, or `reload`, throws `RecordDestroyed`.

:::note
If another request already deleted the row, `save` and `destroy` still succeed.
:::

### Destroying many records

Destroy every record a query matches with `destroyAll`:

<include>/_excerpts/guide/persistence/destroy-many.ts</include>

- **`destroyAll()`** loads the records, runs each one’s destroy callbacks and `dependent` options, and deletes them all in one write. It resolves to the destroyed records.
- **`destroyBy(conditions)`** is `where(conditions).destroyAll()`.
- **`Post.destroy(id)`** finds the record by its primary key and destroys it. Given an array of keys, it destroys those records in one write. It throws `RecordNotFound` if a key has no record, before destroying any.

When one record can’t be destroyed, nothing is. A callback that aborts and a `restrictWithError` association both stop the whole write with `RecordNotDestroyed`.

To delete rows without loading them or running callbacks, use `deleteAll`, `deleteBy`, or `Post.delete(ids)`. See [Bulk writes and batches](./batches).

<Callout type="info" title="Compared with Rails" icon="/ruby.svg">

Rails’ `destroy_all` on a Relation destroys each record in a transaction of its own, skips a record whose callback aborts, and returns every record. Here the records are destroyed in one write, and one refusal stops them all, as Rails’ `destroy_all` on an association does.

</Callout>

### Destroying a large set

`destroyAll` holds every record it matches in memory, and writes them together. To destroy a large set in smaller writes, destroy a page at a time:

<include>/_excerpts/guide/persistence/destroy-in-pages.ts</include>

Each page is its own write, so a page that fails leaves the earlier pages destroyed.

:::note
A page bounds memory, not queries. Each record reads its `"destroy"` and restricted associations with a query of its own, so a large set sends as many reads, a page at a time or not.
:::

## Checking a record’s state

| State                                            | `isNewRecord()` | `isPersisted()` | `isDestroyed()` |
| ------------------------------------------------ | --------------- | --------------- | --------------- |
| New (from `build()`, or after a failed `create`) | `true`          | `false`         | `false`         |
| Persisted (loaded, or after a successful save)   | `false`         | `true`          | `false`         |
| Destroyed (after a successful `destroy()`)       | `false`         | `false`         | `true`          |

## Writing many rows

To insert, update, or delete many rows at once, without validations and callbacks, use `insertAll`, `upsertAll`, `updateAll`, `deleteAll`, and `deleteBy`. See [Bulk writes and batches](./batches).
