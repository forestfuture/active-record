title: Multiple databases
description: "Use two or more databases from one Worker, on D1 or on D1 and Postgres: a schema and base class for each binding, queries and writes on each, associations between them, a Session for each, tests with both, the console on one, and databases on different adapters."
---

A Worker can bind several D1 databases, or a D1 database and a Postgres one. Each gets its own schema file and base class, and each Model queries the database its base class names.

## Binding the databases

Add each database to your Wrangler config, with its own `migrations_dir`:

```jsonc wrangler.jsonc
{
  "d1_databases": [
    { "binding": "DB", "database_name": "my-app-db", "database_id": "…" },
    {
      "binding": "LOGS",
      "database_name": "my-app-logs",
      "database_id": "…",
      "migrations_dir": "logs-migrations",
    },
  ],
}
```

Wrangler applies a folder’s migrations to one database, so each needs its own folder.

## Generating a schema for each

Generate the schemas as usual:

```sh
npx active-record schema
```

With several databases, it writes one of each per binding:

| Binding | Schema           | Base class                                   |
| ------- | ---------------- | -------------------------------------------- |
| `DB`    | `src/db/DB.ts`   | `DbRecord`, in `src/models/db-record.ts`     |
| `LOGS`  | `src/db/LOGS.ts` | `LogsRecord`, in `src/models/logs-record.ts` |

Each base class holds its database’s schema, which names its binding, so its Models query that database:

```ts
import { LogsRecord } from "./logs-record";

export class Entry extends LogsRecord {}

await Entry.where({ level: "error" }).count(); // on LOGS
```

## Generating Models for one database

Name the binding with `--database`:

```sh
npx active-record g model Entry 'level:string!' message --database LOGS
npx active-record migrate --database LOGS
```

## Writing to both

Each write goes to one database. Write to the database that matters most first:

<include>/_excerpts/guide/several-databases/sign-up.ts</include>

If `createOrThrow` throws, nothing reaches `LOGS`.

:::warning[Two databases aren’t one write]
The second write can still fail after the first one succeeds. A batch can’t join them either. It writes to one database, so entries from two throw `IncompatibleRelation`.
:::

An association can link Models on different databases. Declare it as usual:

Each read goes to the database its Model is on:

<include>/_excerpts/guide/several-databases/reading-associations.ts</include>

`includes` loads the users from `DB` once the entries are loaded, in one more round trip. Each other database a [preload](./associations#preloading-associations) reaches adds one.

Records you create through an association are written to their own database:

<include>/_excerpts/guide/several-databases/creating-through.ts</include>

Saving a record also saves the records built through it, each on its own database. Here the user is written to `DB` first, then the entry to `LOGS` with the user’s new key:

<include>/_excerpts/guide/several-databases/autosaving.ts</include>

[`dependent` strategies](./associations#destroying-dependent-records) work the same way. With `dependent: "destroy"` on a user’s entries, destroying the user destroys its entries on `LOGS`, then deletes the user from `DB`.

:::warning[Each database is written on its own]
A save or a destroy that reaches two databases writes to each one separately. If the second write fails, the first stays written. A batch writes to one database, so `batch` throws `IncompatibleRelation` for a record whose writes reach another one.
:::

## Testing with several databases

Outside a Worker, a Model can’t look up its binding. Give your tests the bindings by mocking `cloudflare:workers`. First, let Vitest’s mocks reach Active Record:

```ts vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: { server: { deps: { inline: ["@forestfuture/active-record"] } } },
});
```

Then mock the module with your test databases as its `env`, using the `testDatabase` helper from [Testing](./testing):

```ts test/worker.test.ts
import { afterAll, beforeAll, expect, test, vi } from "vitest";
import worker from "../src/index";
import { testDatabase } from "./d1";

const env = vi.hoisted(() => ({}) as Env);
vi.mock("cloudflare:workers", () => ({ env }));

let databases: Awaited<ReturnType<typeof testDatabase>>[];
beforeAll(async () => {
  databases = await Promise.all([testDatabase(), testDatabase("logs-migrations")]);
  Object.assign(env, { DB: databases[0].binding, LOGS: databases[1].binding });
});
afterAll(() => Promise.all(databases.map((database) => database.dispose())));

test("signing in logs an entry", async () => {
  const request = new Request("https://example.com/?email=ada@example.com");
  const response = await worker.fetch(request, env);
  expect(response.status).toBe(200);
});
```

Each Model now finds its own database, as it does in a Worker. Call your Worker’s `fetch` without `withDatabase`.

:::note
Assign the bindings onto the mocked `env` object, as above. Active Record reads `env` the first time a Model needs its binding, so it never sees an object assigned later.
:::

## Opening one in the console

Name the binding with `--database`:

```sh
npx active-record console --database LOGS
```

## Using databases on different adapters

One project can keep some of its tables on D1 and others on Postgres. First install `pg` and PGlite, as [PostgreSQL](./postgresql) describes.

Name each database’s adapter in `active-record.jsonc`, and give the Postgres one its own migrations folder:

```jsonc active-record.jsonc
{
  "databases": {
    "DB": { "adapter": "d1" },
    "HYPERDRIVE": {
      "adapter": "postgresql",
      "migrationsDir": "pg-migrations",
      "url": "postgres://localhost/shop_development",
    },
  },
}
```

D1 and Postgres write their SQL differently, so each database needs a folder of its own. Both adapters read `migrations/` by default, and the command refuses two databases on different adapters that share one.

To add your Hyperdrive bindings to a file that names only D1 databases, run `init` with the adapter:

```sh
npx active-record init --adapter postgresql
```

`npx active-record schema` reads each database with its own adapter. `src/db/DB.ts` imports `d1`, and `src/db/HYPERDRIVE.ts` imports `postgresql`. Build each Model on its database’s base class:

```ts
import { HyperdriveRecord } from "./hyperdrive-record";

export class Order extends HyperdriveRecord {}
```

Name the database with `--database` for the generators, `migrate`, and the console:

```sh
npx active-record g model Order total:integer --database HYPERDRIVE
npx active-record migrate --database HYPERDRIVE
```
