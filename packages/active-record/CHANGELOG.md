# @forestfuture/active-record

## 0.8.1

### Patch Changes

- [#492](https://github.com/forestfuture/active-record/pull/492) [`980f06a`](https://github.com/forestfuture/active-record/commit/980f06a977b412d138614f1dfaaf5db1dadae683) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Inverse associations ([#62](https://github.com/forestfuture/active-record/issues/62)). A record loaded through its owner's `hasMany` or `hasOne`, by the association, its finders, a Relation narrowed from it, or `includes`, has the owner loaded as its `belongsTo`, the same object, so `await post.author()` sends no query. Through an `autosave: true` belongsTo, saving such a record now also saves the owner's unsaved changes, since the owner is loaded. A `belongsTo`'s record, read or preloaded, has the owner as its inverse `hasOne`. A record built through a new owner keeps pointing back after saving fills in its foreign key. The inverse is inferred by foreign key, so it's found with a `foreignKey:` option too; name it with `inverseOf: "author"` (on an association with a `scope:`, for one), or turn it off with `inverseOf: false`. A wrong `inverseOf` is `InvalidModel` when the Model is first used.

- [#495](https://github.com/forestfuture/active-record/pull/495) [`e2d8ed1`](https://github.com/forestfuture/active-record/commit/e2d8ed1350f7b3e61ebece08194f5c60b92d6abf) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Touching records ([#50](https://github.com/forestfuture/active-record/issues/50)). `record.touch()` sets `updatedAt`, and any datetime attributes named, to now (or `{ time }`) without a save, then runs `afterTouch` and the update commit callbacks. A Relation's `touchAll()` touches every row it matches in one statement, and `incrementColumn` and `decrementColumn` take `{ touch }`.

### Minor Changes

- [#333](https://github.com/forestfuture/active-record/pull/333) [`bfa9bb6`](https://github.com/forestfuture/active-record/commit/bfa9bb65ce28f96989b5027e7bc556da72c367f2) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A batch's writes are prepared in its callback ([#332](https://github.com/forestfuture/active-record/issues/332)): `batch((b) => [b.save(user), b.destroy(post), b.insert(Log, { … }), b.updateAll(Post.where({ … }), { … }), b.deleteAll(user.posts())])`, and `db.batch` the same. `b` has a method for each write, named as the write is when it runs alone, taking a Model or a Relation first. A Model is written on the batch's database, so `db.model(…)` isn't needed inside `db.batch`. The callback can't await: one that doesn't return an array, and a `b` used after it has returned, throw a `TypeError` with nothing sent.

  Breaking: the array form of `batch` and `db.batch` is removed, along with the `to…` methods (`toInsert`, `toInsertAll`, `toUpsert`, `toUpsertAll`, `toUpdateAll` and `toDeleteAll`, on Relations and as Model statics) and records' `toSave()` and `toDestroy()`. A prepared write no longer has `toSql()`; `onQuery` shows what a batch sent. Replace `batch([user.toSave(), Post.where(…).toDeleteAll()])` with `batch((b) => [b.save(user), b.deleteAll(Post.where(…))])`.

- [#394](https://github.com/forestfuture/active-record/pull/394) [`e688585`](https://github.com/forestfuture/active-record/commit/e688585da94d41dfea7138eac6e61a7f5dcd5187) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `binary` attributes and custom types ([#20](https://github.com/forestfuture/active-record/issues/20)).

  A `binary` attribute holds bytes as a `Uint8Array`, in a `BLOB` column on D1 or a `bytea` one on Postgres. It's assigned a `Uint8Array` or an `ArrayBuffer`, and always reads back as a plain `Uint8Array`. A change is found by comparing bytes, so a byte changed in place is saved. `where`, `gt` and `order` compare bytes in order. A printed record shows `<3 bytes of binary data>`. `active-record schema` reads `BLOB` and `bytea` columns as `binary`, where they were errors, and `g` writes `name:binary` as `BLOB` or `BYTEA`. `permit` still refuses a file: assign `new Uint8Array(await file.arrayBuffer())`.

  `defineType({ storedAs, cast, serialize, deserialize })` makes a custom type, which a spec takes as it takes a type's name: `price: money`, or `{ type: money, null: false }`, and a generated Model's override too. Its values are kept as `storedAs` keeps its own, so they're read strictly, compared and ordered as that type's are. What its `cast` or `deserialize` throws is a `TypeError` naming the Model and attribute, with the type's error as its `cause`; `defineType` throws `TypeError` for an unknown `storedAs` or a missing function.

  `isAttributeChanged` and the other change methods cast their `from` and `to` as a condition's value is cast, so `from: "2026-01-01"` matches a `datetime`, and a value that can't be cast matches nothing, where it could throw.

  Breaking: `typeForAttribute(name).serialize` is typed `string | number | Uint8Array | null`, since a `binary` attribute's stored form is bytes.

- [#405](https://github.com/forestfuture/active-record/pull/405) [`a451f78`](https://github.com/forestfuture/active-record/commit/a451f78d9d1fcbd0329fe62625dae24e97a6c421) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `decimal`, `date` and `time` attributes ([#391](https://github.com/forestfuture/active-record/issues/391)).

  A `decimal` holds an exact number as text in one form: `"12.50"` reads as `"12.5"`. It's assigned decimal text or a `bigint` exactly, or a number at 16 significant digits (`0.1 + 0.2` is `"0.3"`). A decimal past a JavaScript `number`'s range (`"1e400"`, `"1e-400"`) is refused. Conditions, comparisons and `order` compare decimals as numbers, and so do `numericality` and `comparison`. D1 keeps about 15 significant digits; Postgres's `numeric` keeps every one.

  A `date` holds a day, `"2026-01-02"`, and a `time` a time of day, `"09:30:00"` (up to `"24:00:00"`, the end of the day), both as text with no zone. A `Date` is refused for either, since its day and time depend on the time zone.

  `active-record schema` reads `NUMERIC` and `DECIMAL` columns as `decimal`, where they were errors, and `TIME` as `time`. `g` writes `price:decimal`, `starts_on:date` and `opens_at:time`, with `=value` defaults.

  Breaking: `active-record schema` reads a `DATE` column as a `date`, where it was a `datetime`. Override it with `"datetime"` to keep a `Date`. On D1, a `DATE` column a `datetime` wrote holds `2026-01-02T00:00:00.000Z`, which a `date` can't read; the upgrading guide shows the SQL that keeps each day. A `TIME` column, read as a `string` before, reads as `"09:30:00"`.

- [#387](https://github.com/forestfuture/active-record/pull/387) [`450bb89`](https://github.com/forestfuture/active-record/commit/450bb890cfc622709a35ca080f704d9b8a2abd4a) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Enum attributes ([#340](https://github.com/forestfuture/active-record/issues/340)). Declare one with `enum`, in an override (`status: { enum: ["draft", "published"] }`) or in `define`, with names stored as text or mapped to integers (`{ low: 0, high: 10 }`). Its property is typed as the union of its names, an unknown value throws `TypeError` when it's assigned, and a stored value the enum doesn't list reads as `null`. Each name gives records `isPublished()` and `saveAsPublished()` / `saveAsPublishedOrThrow()`, and the Model `published()` and `notPublished()` scopes; `Post.enumValues("status")` gives the names with their stored values. `prefix`, `suffix`, `scopes: false`, `instanceMethods: false` and `validate: true` work as Rails' options do.

  The generated `schema.ts` is now a `defineSchema({ … })` call, which makes a generated Model's enum scopes statics from the start. Run `npx active-record schema` to regenerate yours; `--check` reports a schema an older version wrote.

- [#390](https://github.com/forestfuture/active-record/pull/390) [`e5fb4d5`](https://github.com/forestfuture/active-record/commit/e5fb4d5d8ed184c167de2f3423fa5618e3beae3f) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `active-record schema` reads enums from the database ([#64](https://github.com/forestfuture/active-record/issues/64)). A column whose values a Postgres enum type, or a `CHECK (column IN ('open', 'done'))` on D1 or Postgres, restricts to a list of strings becomes a generated enum: its spec lists the names, with `scopes: false` and `instanceMethods: false`, so its type is the union of the names and assigning any other value throws `TypeError`. Its Model turns the predicates, setters, and scopes on with an override's `enum: true`, or drops the enum with `enum: false`.

  Regenerating an existing schema narrows such columns to their names, so code that assigned other text to one now throws `TypeError`; override the column with `enum: false` to keep it a plain string.
