# @forestfuture/active-record

## 0.8.0

### Minor Changes

- [#333](https://github.com/forestfuture/active-record/pull/333) [`bfa9bb6`](https://github.com/forestfuture/active-record/commit/bfa9bb65ce28f96989b5027e7bc556da72c367f2) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A batch's writes are prepared in its callback ([#332](https://github.com/forestfuture/active-record/issues/332)): `batch((b) => [b.save(user), b.destroy(post), b.insert(Log, { … }), b.updateAll(Post.where({ … }), { … }), b.deleteAll(user.posts())])`, and `db.batch` the same. `b` has a method for each write, named as the write is when it runs alone, taking a Model or a Relation first. A Model is written on the batch's database, so `db.model(…)` isn't needed inside `db.batch`. The callback can't await: one that doesn't return an array, and a `b` used after it has returned, throw a `TypeError` with nothing sent.

  Breaking: the array form of `batch` and `db.batch` is removed, along with the `to…` methods (`toInsert`, `toInsertAll`, `toUpsert`, `toUpsertAll`, `toUpdateAll` and `toDeleteAll`, on Relations and as Model statics) and records' `toSave()` and `toDestroy()`. A prepared write no longer has `toSql()`; `onQuery` shows what a batch sent. Replace `batch([user.toSave(), Post.where(…).toDeleteAll()])` with `batch((b) => [b.save(user), b.deleteAll(Post.where(…))])`.

- [#373](https://github.com/forestfuture/active-record/pull/373) [`c169409`](https://github.com/forestfuture/active-record/commit/c1694097df43efc761b1434904d555b8ab9f4d68) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A `hasOne` replaces its record as Rails does ([#40](https://github.com/forestfuture/active-record/issues/40)). `await user.profile.set(profile)` gives the owner another record, and `set(null)` removes it. On a saved owner, `set`, `build` and `create` remove the old record by `dependent:`: `"destroy"` destroys it, `"delete"` deletes it, and otherwise its foreign key is set to `null` and it's saved. It's removed in the same atomic batch that writes the new record: at once for `set` and `create`, and for `build` when the owner is saved. An old record that can't be saved with a `null` foreign key throws `RecordNotSaved`, and nothing is written.

  Breaking: `build` and `create` through a saved owner's `hasOne` used to leave the old record as it was. Without `dependent`, its foreign key is now set to `null`, which a `NOT NULL` column refuses; set `dependent: "destroy"` or `"delete"` to remove it instead. Building twice through an unsaved owner's `hasOne` now saves only the last record.

- [#364](https://github.com/forestfuture/active-record/pull/364) [`6c91a98`](https://github.com/forestfuture/active-record/commit/6c91a98371439ed5e4fd6bd6c3b0043d1d43628e) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A new record's changes run from its declared defaults and generated ids ([#41](https://github.com/forestfuture/active-record/issues/41)), as in Rails: `Post.build()` holding only defaults isn't changed, and assigning a default's value isn't a change. Inserts still write them. After a create, `savedChanges()` is what the insert changed plus what the write or the database filled in (a generated key, timestamps), not the defaults the record kept.

  Breaking: code reading a new record's `changes()`, `changed()`, `isChanged()` or `savedChanges()` no longer sees its kept defaults or generated id.

- [#362](https://github.com/forestfuture/active-record/pull/362) [`2cafecb`](https://github.com/forestfuture/active-record/commit/2cafecba5dd7a4bf03fbd1503f431a6fb571b01d) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A `belongsTo` requires its record ([#339](https://github.com/forestfuture/active-record/issues/339)): saving a record whose `belongsTo` points at nothing fails validation with "must exist" (type `required`) on the association. It's checked when the foreign key is `null` or has changed, and the record found stays loaded. A record built through its owner's `hasMany` or `hasOne` points back at the owner, so it passes before either is saved, and `await post.author()` on it is the owner without a query.

  Breaking: add `optional: true` to each `belongsTo` whose foreign key may be `null`: `parent = belongsTo(Category, { optional: true })`.

### Patch Changes

- [#381](https://github.com/forestfuture/active-record/pull/381) [`5ab9d80`](https://github.com/forestfuture/active-record/commit/5ab9d807377d792653ca13956ee0503f6a975579) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `autosave: true` on a `hasMany`, `hasOne` or `belongsTo` ([#37](https://github.com/forestfuture/active-record/issues/37)): saving the owner also saves the association's loaded records that changed, and destroys those marked with `record.markForDestruction()` (`isMarkedForDestruction()` reads the mark, and `reload()` clears it). A changed record's errors are copied onto the owner under the association's name, such as `posts.title` ("Posts title can't be blank"). A marked record is destroyed with its callbacks and `dependent:` strategies, and leaves the loaded association. A `belongsTo`'s marked record is destroyed after the owner stops pointing at it. On the owner's database, it's all one atomic batch when the owner's key is known. If a marked record refuses to be destroyed, nothing is written: `save()` returns `false`, and `saveOrThrow()` throws `RecordNotDestroyed`.

- [#375](https://github.com/forestfuture/active-record/pull/375) [`ca01286`](https://github.com/forestfuture/active-record/commit/ca01286eb92cf326b548e595433a92102b822fb7) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Commit and rollback callbacks ([#341](https://github.com/forestfuture/active-record/issues/341)). `afterCommit`, `afterCreateCommit`, `afterUpdateCommit`, `afterSaveCommit` and `afterDestroyCommit` run last, once a write is kept: after every after-callback of the save, or of every record in a batch, in the order they were declared. `afterRollback` runs for each record whose save or destroy the database refused, such as for a constraint error or another write in its batch. It doesn't run for a failed validation or an `abort()`, since nothing was sent. An error a callback throws while a refused write is handled reaches the caller in place of the database's error, which becomes its `cause`.

- [#367](https://github.com/forestfuture/active-record/pull/367) [`833c750`](https://github.com/forestfuture/active-record/commit/833c7505c4e24914aaab046bb03aaf805c7e3b5f) Thanks [@christopherstyles](https://github.com/christopherstyles)! - The `active-record` command caches the TypeScript it compiles ([#251](https://github.com/forestfuture/active-record/issues/251)), in the project's `node_modules/.cache/jiti`, so `schema`, `g` and the console load the library about ten times faster after their first run. An edited file is compiled again. A project without its own `node_modules` folder isn't cached.

- [#321](https://github.com/forestfuture/active-record/pull/321) [`d64bc40`](https://github.com/forestfuture/active-record/commit/d64bc40d77caa94d4fb922e59f64194f1fc915d4) Thanks [@christopherstyles](https://github.com/christopherstyles)! - An association between Models on different databases now reads and writes the target's database ([#228](https://github.com/forestfuture/active-record/issues/228)), on the same adapter or another. Reads, `includes` (one more round trip for each other database a tree reaches), creating through the association, autosave, and every `dependent:` strategy work across databases, as in Rails: each database's writes are separate, so not atomic together. The JSON Schema describes the setting. `schema` now finds Drizzle's and Prisma's files from each database's config folder, not only the first database's.

- [#374](https://github.com/forestfuture/active-record/pull/374) [`60dc31e`](https://github.com/forestfuture/active-record/commit/60dc31ecd928ebe58ac88c0f5756af8c6b6185bf) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A `hasMany` has collection methods ([#352](https://github.com/forestfuture/active-record/issues/352)): `user.posts().push(post)` sets the post's foreign key and saves it (on a new owner, it's saved with the owner), `delete(post)` removes it by the association's `dependent:` (nullifying by default), `destroy(post)` destroys it with its callbacks, and `clear()` removes every post as `deleteAll()` does. Each keeps a loaded collection in step. They're on the association itself only, typed as `HasManyCollection`.

- [#311](https://github.com/forestfuture/active-record/pull/311) [`2ba5f8c`](https://github.com/forestfuture/active-record/commit/2ba5f8ce03d8ca9640d17a6115f9f814543eca77) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A string in `active-record.jsonc` that holds a comma before `}` or `]` reads as written.

- [#317](https://github.com/forestfuture/active-record/pull/317) [`1625712`](https://github.com/forestfuture/active-record/commit/1625712afbcf2d0692e444162a63538a75f34fc8) Thanks [@christopherstyles](https://github.com/christopherstyles)! - One project can hold databases on different adapters, such as a D1 database and a Postgres one. `active-record.jsonc` names each database's adapter, and every command uses that database's own: `schema` writes each schema through its adapter, and `g`, `migrate` and `console` use the adapter of the database `--database` names. `init --adapter postgresql` adds Hyperdrive bindings to a file that names only D1 databases. - [#372](https://github.com/forestfuture/active-record/pull/372) [`f466f34`](https://github.com/forestfuture/active-record/commit/f466f342d136d93fcaf0cdc46bf129ddc754f9df) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A Model's `modelName` is its name ([#47](https://github.com/forestfuture/active-record/issues/47)): its class name, unless it sets `static override modelName = "BlogPost"`.
