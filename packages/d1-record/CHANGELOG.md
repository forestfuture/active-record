## 0.5.0

### Minor Changes

- [#234](https://github.com/forestfuture/d1-record/pull/234) [`26d65f1`](https://github.com/forestfuture/d1-record/commit/26d65f1c951838ae54488bd7192edc910bbba28a) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A Model now extends your app’s base class with nothing on the `extends` line: `class Post extends ApplicationRecord {}`. Its table comes from its class name, or `static override table = "…"`, and its attributes from the generated schema. `ApplicationRecord` is an abstract class extending `Model` that holds the schema, and `record instanceof ApplicationRecord` is true.

  - `d1-record schema` now loads your Model files too, as the console does, so code at a Model file’s top level runs when it does. Run it after adding or renaming a Model. A Model it hasn’t seen throws `InvalidModel`, and its statics are a compile error. `--check` and `--watch` cover Models.
  - Overrides move into the class: `static override attributes = { available: "boolean" } as const`. `declare status: "draft" | "published"` narrows an attribute’s type.
  - `static abstract = true` marks a class between `ApplicationRecord` and some Models that shares their behavior.
  - Breaking: `modelFor`, `ApplicationRecord("table")`, `Model.Base` (use `Model`), `static binding` (the binding is in the generated schema), and `static tableName` (use `static table`) are gone. `Model({...})` is now `Model.define({...})`, and `ApplicationRecord.define({...})` builds on your base class. Regenerate the schema, and replace `application-record.ts` with the new template.

- [#230](https://github.com/forestfuture/d1-record/pull/230) [`f57ac32`](https://github.com/forestfuture/d1-record/commit/f57ac325a41bb72602410f3a1feac56fc74ab6b4) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `includes()` sends the whole tree with the records' own query, in one round trip, however deep: each association's query finds its owners' keys with a subquery, not with keys bound after the level above comes back. `includes({ posts: "comments" })` was three round trips and is now one, and every level reads the same data. With a `limit` or `offset`, a query with `includes` now ends its order with the primary key, so its preloads find the records it loads. So `take()` and a `limit()` with no order now come back in primary-key order. Each preload runs the query's conditions again, and its order with a `limit` or `offset`, so index what a query with `includes` filters and sorts by. A nested query that would bind more than D1's 100 values takes one more round trip. `paginate()` sends its count, its page and the page's preloads in one batch.

- [#238](https://github.com/forestfuture/d1-record/pull/238) [`d71d63c`](https://github.com/forestfuture/d1-record/commit/d71d63c58d198cb5119dd81b66d74813b37f3464) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `withSession` now answers a request whose bookmark D1 can’t use, such as a forged cookie. D1 rejects that bookmark on the Session’s first statement. The Session then starts again from `start`, the statement is sent again, and the response gets a fresh bookmark. Before, every request carrying the bookmark failed until the cookie changed. A bookmark given to `connect(env.DB, { session })` still throws. In D1’s error, a long bookmark is cut short.

- [#196](https://github.com/forestfuture/d1-record/pull/196) [`e4156b7`](https://github.com/forestfuture/d1-record/commit/e4156b767e63de2d70cfb3c87d01e8132366971a) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A `belongsTo` or `hasOne` read sent before `set`, `build`, `create` or `reload()` (`post.author.set(…)`, `user.profile.build(…)`), and answered after it, no longer replaces what's loaded: the read still resolves to the record it loaded, what `set`, `build` or `create` made stays loaded, and after `reload()` nothing is.

- [#190](https://github.com/forestfuture/d1-record/pull/190) [`b785ed4`](https://github.com/forestfuture/d1-record/commit/b785ed4ee68608d2e57b4ccf944cc8730cf25a87) Thanks [@christopherstyles](https://github.com/christopherstyles)! - A `hasMany` read sent before a write or `create` through it, and answered after, no longer leaves the old rows loaded: the read still resolves to what it loaded, and the next read queries again. - [#223](https://github.com/forestfuture/d1-record/pull/223) [`67dcd60`](https://github.com/forestfuture/d1-record/commit/67dcd60123ae4a17b273b6e972c68bd99b15de27) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `exists()`, `isEmpty()` and `hasAny()` no longer send a Relation's order. Nor do `count()`, `count(attribute)` and `paginate()`'s count, unless the Relation has a `limit` or `offset`. The order can't change their answers, but SQLite still sorted every matching row first, and D1 bills each row read. - [#226](https://github.com/forestfuture/d1-record/pull/226) [`34533e9`](https://github.com/forestfuture/d1-record/commit/34533e915cb93b9b7016ee9ac47f95eb04ef5c6c) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `withSession(request, env.DB, fn)` opens a D1 Session for each request and carries its bookmark to the user's next request, so with read replication a user reads at least as new as their last write. The bookmark travels in a `d1-bookmark` cookie by default. For APIs, `{ header: "x-d1-bookmark" }` carries it in a header instead. `cookie` renames the cookie. `start: "first-primary"` starts a request with no bookmark on the primary. A response whose headers can't change, such as a redirect, is copied to carry it.

### Minor Changes

- [`74a956f`](https://github.com/forestfuture/d1-record/commit/74a956ffe1bd9d6b13da117f3fc9d4605edc5b24) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Associations are declared as record fields, written once: `posts = hasMany(Post, { dependent: "destroy" })`, `author = belongsTo(User)`, `profile = hasOne(Profile)`, imported from the package. - [`e3674a6`](https://github.com/forestfuture/d1-record/commit/e3674a6de6a642dc383b219886ee2e62bfd1def0) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Attribute values are cast to their type when they're assigned or given to a bulk write, and in conditions. Only unambiguous values are accepted: `"false"`, `"0"` and `"off"` are `false` for a boolean, `"42"` is `42` for an integer, and an ISO-8601 string is a `Date`. Anything else throws `TypeError`: `"no"` for a boolean, `"12abc"` or `1.7` for an integer, a number for a string, a time without an offset. Before this, `"false"` was saved as `true`, and `"12abc"` was stored in an integer column.

  A condition value that can't be cast matches nothing, so `find("abc")` on an integer key throws `RecordNotFound`. In a condition, a number matches a string attribute as its digits (`7` finds `"7"`), as `find` does for a text key.

  An override that changes an attribute's `type` without giving a `default` now drops the generated default, so the column's own default applies.

- [`02094f5`](https://github.com/forestfuture/d1-record/commit/02094f5ec51676f25557dee8af67cc08ab04f627) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Queries start from the Model, as in Rails: `User.find(id)`, `User.where(…)`, `User.create(…)`, `User.active()`, and every other Relation method as a typed static. With no setup they use the Model's binding (`static binding = "DB"`, written on your `ApplicationRecord`'s base class by `d1-record schema`). For a D1 Session, per-request `onQuery`, or tests outside a Worker, `withDatabase(connect(env.DB, { … }), fn)` gives a request its own database. `batch([...])` writes atomically on the current database. `db.model(X)` still works as before.

  Scopes are now declared one static each, as Rails' `scope :active, -> { … }`: `static active = this.scope((q) => q.where({ isActive: true }))`, replacing `static scopes = this.defineScopes({...})`. They inherit like any static.

- [`0f4848f`](https://github.com/forestfuture/d1-record/commit/0f4848f1ce64523a0f678f1a8421551d415a96e6) Thanks [@christopherstyles](https://github.com/christopherstyles)! - `onQuery` listeners see the bound values of filtered attributes as `"[FILTERED]"`, as Rails' logs do, and so do cast errors. `static filterAttributes` starts with Rails' default list (`passw`, `email`, `secret`, `token`, `_key`, `crypt`, `salt`, `certificate`, `otp`, `ssn`, `cvv`, `cvc`), matched against each attribute's snake_case name, so passwords, tokens, API keys and emails no longer reach your logs. Replace the list on your app's base class: `static override filterAttributes = [...Model.Base.filterAttributes, "iban"]`, or `[]` to filter nothing. D1 still gets the real values.

- [`4f48758`](https://github.com/forestfuture/d1-record/commit/4f4875802944d87fbe88dbc268fa4f367f4e2d1b) Thanks [@christopherstyles](https://github.com/christopherstyles)! - First release: a Rails-inspired Active Record for Cloudflare Workers and D1. See the guide at https://docs.forestfuture.dev/d1-record/.

- [`dd95b62`](https://github.com/forestfuture/d1-record/commit/dd95b6214e1eebccd333741a9f12ffa2df5c9885) Thanks [@christopherstyles](https://github.com/christopherstyles)! - Bulk writes run when called, as in Rails: `await posts.deleteAll()` and `updateAll(…)` resolve to the number of rows (on `none()`, `0` without a query), and `insert`, `insertAll`, `upsert` and `upsertAll` to D1's `meta`.
